WHAT WENT WRONG ON THE WAY, AND WHY IT MATTERED
============================================================

  Three runs, and neither of the first two was an application fault.

  Run #32  http 429 in 4725ms   FAILURE
    A real provider refusal. NOT converted to a skip - the gate went red, as
    designed. The 4725ms already ruled out BuildHub's own AI limiter, which
    rejects in about a millisecond with no network and a different message.

  Run #33  http 200 in 1343ms   FAILURE (harness)
    The request SUCCEEDED. The harness reported "answer length: 0 chars" on a
    200 whose conversation had grown by 136 characters on screen in the same
    run - lines that contradict each other, which is what gave it away. A 200
    from ai.chat cannot carry empty content; the router throws instead.

    Cause: client/src/main.tsx uses httpBatchLink, so the BROWSER's response
    body is a tRPC batch ARRAY. Reading .result off an array yields undefined.
    The harness's own post() gets the bare object, so the bug only appeared
    once the paid call moved into the browser.

    Nothing changed on the deployment between #32 and #33, which is also what
    establishes #32's 429 as transient provider throttling rather than a
    configuration fault.

  Run #34  http 200 in 3321ms   SUCCESS, 343/343

  The rendering proof no longer depends on that parse at all: it is asserted
  from the DOM first, with the payload cross-check kept as a second,
  independent check.
