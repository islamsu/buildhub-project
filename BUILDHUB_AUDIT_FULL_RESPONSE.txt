1. HEADLINE
================================================================================

The most serious finding was NOT a missing feature.

MessagesPage fabricated four conversations for every user with an empty inbox.
Because messages.send never checked its recipient, replies typed into those
fabricated threads were DELIVERED TO A REAL STRANGER. One of the invented
threads told the reader "Your verification is complete!" over BuildHub's name.

That is the shape of the risk in this codebase: not absent functionality,
which is visible, but PRESENT FUNCTIONALITY THAT IS NOT WHAT IT APPEARS TO BE.

Four of the five findings are of that kind:
  - a link that leads to a 404
  - a question box whose answer can never be written
  - a badge counting to zero forever
  - an authorization check reasoning about a path it never validated

Each one looked finished.

2. THE FIVE DEFECTS, IN FULL

--------------------------------------------------------------------------------
D1 — A FABRICATED INBOX DELIVERING REAL MESSAGES TO REAL STRANGERS      [P1]
--------------------------------------------------------------------------------

WHAT WAS WRONG
  client/src/pages/MessagesPage.tsx line 88:

      conversations = persistedConversations.length > 0
                        ? persistedConversations
                        : MOCK_CONVERSATIONS;

  Any signed-in user with no real conversations was shown four INVENTED
  threads: "Ahmed Hassan (Contractor)", "Sara Khalil (Architect)", "Mohamed
  Supplier", "BuildHub Support" - with invented message bodies, invented unread
  badges, and a green "Online now" dot fed by a field the server hard-codes to
  false.

TWO CONSEQUENCES, THE SECOND BEING THE SERIOUS ONE

  (a) IT FABRICATED A PLATFORM STATEMENT.
      One mock thread contained "Your verification is complete!" attributed to
      "BuildHub Support". A supplier waiting on verification could reasonably
      read that as BuildHub telling them they had been approved.

  (b) IT MISDIRECTED REAL MESSAGES.
      The mock ids were 1-4. selectedConv defaulted to 1. messages.send
      accepted ANY positive integer as receiverId with no check that the
      account existed or was active. So typing into the thread labelled "Ahmed
      Hassan" fired messages.send({ receiverId: 1 }) and delivered the text to
      whichever REAL account holds user id 1.

      The FK on messages.receiverId meant a NON-existent id failed loudly as an
      INTERNAL_SERVER_ERROR. An id that HAPPENED TO EXIST succeeded quietly.
      The quiet path is the worse one.

  (c) AND IT WAS REPORTED AS DELIVERED EITHER WAY.
      appendLocalMessage ran unconditionally rather than in onSuccess, so a
      message the server REFUSED still appeared in the thread as sent.

WHAT WAS FIXED
  - The fabricated conversations and message threads are gone entirely.
  - An empty inbox now says it is empty and says what starts a conversation,
    with a route to the vendor directory. Previously it said "Select a
    conversation to start" when there was nothing to select - an instruction
    the screen could not carry out.
  - messages.send requires a REAL, ACTIVE recipient and refuses self-messages.
    "No such user" and "not active" give the SAME refusal, so the endpoint is
    not a directory of which account ids exist.
  - No optimistic append: a refused message is not shown as sent.
  - `unread` was hard-coded to 0 while the UI rendered a badge from it. A
    counter that always reads zero hides real messages. Now counted from the
    rows already loaded.
  - `online` is REMOVED rather than shipped permanently false, because BuildHub
    has no presence system at all.
  - The voice-call and video-call buttons (which toasted "Coming soon") and the
    overflow button (which had no handler at all) are gone.

NOT DECIDED HERE
  Whether BuildHub should require a PRIOR RELATIONSHIP - a shared RFQ, a
  quotation, a directory enquiry - before one user may message another.
  Existence and active status are integrity and are now enforced. A
  relationship rule is product policy, and the marketplace deliberately lets a
  customer contact a vendor they just found. Recorded as owner decision D6.

TEST      server/messagingIntegrity.test.ts (17 tests)
MUTATIONS 6 killed: removing the guard, allowing inactive recipients, dropping
          the self-check, splitting the two refusals into an oracle, reverting
          unread to 0, restoring the mock fallback.

D2 — THE AI OFFERED CONTRACTORS TWO LINKS TO THE 404 PAGE               [P2]
--------------------------------------------------------------------------------
THIS ONE WAS MINE. I shipped it in the previous phase.

WHAT WAS WRONG
  The opportunity engine built its prepared actions as `/rfq/${id}`. App.tsx
  registers `/rfq` and nothing matches `/rfq/:id`, and the router ends with a
  catch-all NotFound. So both actions the AI offered a contractor - "view the
  RFQ" and "open the enquiry" - fell through to the 404 page.

WHY THE EXISTING TEST DID NOT CATCH IT
  aiRoles.test.ts checks that every ROUTES entry appears in App.tsx. The
  opportunity engine does not use ROUTES - it assembles hrefs from a template -
  so the check never saw them.

  The previous handoff's claim that "every action href is asserted against
  App.tsx" was TRUE OF THAT CONSTANT AND FALSE OF THE PRODUCT.

WHAT WAS FIXED
  - Hrefs now point at routes that exist: `/rfq` (the list) and `/provider`
    (which forwards a signed-in provider to their role platform, where the
    credit-gated enquiry list and the quotation form actually live).
  - server/routeIntegrity.test.ts parses the REAL route table out of App.tsx -
    exact paths plus parameterised patterns - and holds every href-producing
    source against it: ROUTES, all six roles' actions, and every href literal
    in the opportunity engine.
  - It also refuses any href built by interpolating an id into a path, which is
    the SHAPE of the defect rather than the instance.

TEST      server/routeIntegrity.test.ts (47 tests)
MUTATIONS 3 killed: restoring the /rfq/${id} template, pointing an href at a
          plausible-but-unregistered route, removing the provider CTA.

D4 — A SUPPLIER COULD NEVER ANSWER A QUESTION ABOUT THEIR OWN PRODUCT   [P2]
--------------------------------------------------------------------------------

WHAT WAS WRONG
  Half a workflow, shipped as though whole:
    - productQuestions carries `answer` and `answeredAt`
    - marketplace.questions returns both
    - ProductDetail renders the answer when present
    - the ask box says "Question sent to supplier"
    - and NO PROCEDURE COULD EVER WRITE AN ANSWER.

  Every thread was permanently one-sided while the buyer-facing UI implied a
  reply was coming.

WHAT WAS BUILT
  marketplace.answerQuestion and marketplace.myProductQuestions.

  AUTHORIZATION is the half that matters. The owning supplier and nobody else -
  not the asker, not another supplier, not an approved provider in general. The
  check is a JOIN rather than two reads, so there is no window between "this
  question exists" and "this product is mine". Absent, not-mine and delisted
  all give the SAME refusal, so the endpoint is not an oracle for which
  question ids exist or which products belong to whom.

  A question on a DELISTED product cannot be answered, matching askQuestion: a
  withdrawn product and an absent one are the same answer to a buyer, so an
  answer must not appear on nothing.

NOT DECIDED HERE
  Whether a supplier may EDIT an answer once given, and whether answers need
  moderation before they are public. Both are policy. This writes an answer
  once and refuses to overwrite one - the conservative reading, which is easy
  to relax later; the opposite is not. Owner decision D7.

STILL MISSING
  The supplier-facing SCREEN to answer from. The procedure and its
  authorization exist; the UI does not. That is the part that could have been
  got wrong silently, so it was done first.

D5 — THE AUTHORIZATION DECISION WAS ABOUT A PATH NOBODY HAD VALIDATED   [P3]
--------------------------------------------------------------------------------

WHAT WAS WRONG
  Every branch of authorizeStorageKey dispatches on a PREFIX -
  key.startsWith('avatars/'), key.startsWith('rfq-attachments/') - and the same
  string is then handed to the storage adapter. Nothing validated the key in
  between.

  So `avatars/../../something` satisfied the avatars branch, which returns true
  for ANY authenticated user because profile pictures are public, and the
  backend was then asked for a different object entirely.

WHY THIS WAS NOT A VULNERABILITY, STATED PLAINLY
  The only configured backends are S3, where a key is an opaque string and `..`
  is a literal segment that will simply not exist, and an HTTP API. Nothing
  traverses a filesystem today. normalizeKey only ever stripped leading slashes.

WHY IT WAS STILL WORTH FIXING
  The defect is that the authorization layer REASONS ABOUT A PATH IT NEVER
  VALIDATED. That is invisible to whoever later adds a filesystem-backed
  adapter - a perfectly reasonable thing to want for local development - and it
  becomes a real traversal at that moment, in a file they had no reason to
  open. Reporting it as "safe because of the backend we happen to use" would be
  reporting the accident rather than the design.

WHAT WAS FIXED
  isWellFormedStorageKey rejects absolute paths, backslashes, control
  characters, empty segments, and whole "." or ".." segments, with a length
  bound. It runs BEFORE the admin short-circuit: an admin may read any
  legitimate object, which is not the same as reading a path that does not mean
  what it appears to mean.

TEST      server/storageKeyTraversal.test.ts (16 tests)
MUTATIONS 4 killed, INCLUDING AN OVER-STRICT ONE: rejecting any key containing
          the substring ".." breaks a legal filename like `..hidden.png`, so
          the positive controls fail too. A security fix that quietly breaks
          real uploads is a different bug, not a stricter version of the same
          one.

4. WHAT I AUDITED AND FOUND CLEAN
================================================================================

Recorded so this is not a list of only the things that were wrong.

  STORAGE PROXY (categories B-F)
    Each resolves ownership through a DATABASE ROW, not through the key. Fails
    closed by default for anything outside the classified prefixes. RFQ
    attachments are matched by exact string comparison in JS rather than SQL
    LIKE, because `_` is a LIKE wildcard and a legal character in these keys.

  NOTIFICATIONS
    list, unreadCount and markAllRead are ALL scoped by ctx.user.id. There is
    no single-notification read-by-id surface to attack.

  ANALYTICS
    analytics.myStats is approvedProviderProcedure and self-scoped. No
    hard-coded KPIs found. No cross-tenant aggregation.

  PROFILE
    profile.update accepts exactly two fields (bio, location), has NO userId in
    its schema, and writes WHERE users.id = ctx.user.id. No mass-assignment
    surface.

  MESSAGES QUOTATION BRANCH
    The sender must be a PARTY to the quotation - the provider who submitted it
    or the homeowner who owns the RFQ it answers. Not-a-party and
    does-not-exist give the same answer.

  CONSOLE MAILER
    Cannot be selected in production: `ENV.isProduction ? none : console`. Reset
    links cannot reach a production log.

  PUBLIC PROCEDURES
    23 reviewed. The id-taking ones are marketplace listings that are public by
    design.

  LOCALIZATION
    945 distinct keys. EVERY ONE present in both EN and AR. Zero appearing once
    (a missing translation), zero appearing more than twice (a duplicate).
    Measured, not assumed.

  SCHEMA
    55 foreign keys, 63 indexes, 4 unique constraints across 30 tables.

  DEBT MARKERS
    All console.log hits are server-side operational logging (boot messages,
    structured HTTP logging, SMTP readiness). None in client code. None in
    request paths as debug leakage.

  MOCK DATA
    A repo-wide scan found exactly ONE `real.length > 0 ? real : MOCK` fallback
    in the entire client - the MessagesPage one, now removed. No other
    fabricated data reaches any surface.
