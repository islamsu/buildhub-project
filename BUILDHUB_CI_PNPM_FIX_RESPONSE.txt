================================================================================
1. WHAT WAS ACTUALLY WRONG
================================================================================

pnpm/action-setup@v4 aborts with "Multiple versions of pnpm specified" when it
is given a `version` input AND package.json carries a `packageManager` field -
EVEN WHEN THE TWO AGREE. Here they did agree: 10.4.1 in both places. The action
refuses regardless, because it cannot know which declaration is authoritative
and will not guess.

Three workflow steps carried the redundant pin:

  .github/workflows/ci.yml              2 steps  (both failing jobs)
  .github/workflows/deploy-staging.yml  1 step   (would have failed the same way)

Why "Image builds and starts" PASSED while the other two failed: that job never
uses pnpm/action-setup at all. It builds the Docker image, and the Dockerfile
pins pnpm through corepack (`corepack prepare pnpm@10.4.1 --activate`). It was
never exposed to the conflict.

NOT AFFECTED: .github/workflows/staging-qa.yml uses npm, not pnpm, and never
invokes pnpm/action-setup. The 22-point gate was never touched by this bug.


================================================================================
2. THE FIX
================================================================================

Remove the `version:` input from all three steps. package.json's
`packageManager` field becomes the single source of truth - the action reads it
itself, which is the documented supported usage.

  BEFORE                              AFTER
  - uses: pnpm/action-setup@v4        - uses: pnpm/action-setup@v4
    with:
      version: 10.4.1

Nothing else changes: same pnpm 10.4.1, same lockfile, same install, same
resolution. A comment now sits above each step explaining why there is no
version pin there, so nobody helpfully re-adds one.

3. A TEST OF MINE WAS PINNING THE BUG IN PLACE
================================================================================

This is the part worth reading.

server/deploymentPipeline.test.ts contained:

    it('pins pnpm to the version that produced the committed lockfile', () => {
      expect(DOCKERFILE).toContain('corepack prepare pnpm@10.4.1');
      expect(CI_RAW).toContain('version: 10.4.1');        <-- THIS
    });

That second assertion was reaching for "pnpm is pinned." What it actually
REQUIRED was the literal second declaration that breaks the job. The test did
not protect the pin - it protected the defect, and would have failed any
correct fix.

Replaced with the guarantee it was aiming at, plus two that reproduce the
failure mode directly:

  1. packageManager parses as a pinned version, and the Dockerfile's
     `corepack prepare` uses THAT SAME version - derived from packageManager,
     not restated as a literal, so the two cannot drift apart silently.

  2. No workflow step passes a `version` input to pnpm/action-setup.
     Walks the parsed YAML of every workflow, every job, every step.

  3. Every JOB that runs a pnpm command has its own pnpm/action-setup step.
     Scoped per JOB, not per file - see the mutation table below for why.

MUTATION-TESTED. A test that cannot fail is not a test, so each was proven to
catch the thing it claims to catch:

  MUTATION                                      RESULT
  ------------------------------------------    ---------------------------
  Re-add `version: 10.4.1` to ci.yml            FAILS - correct
    -> "ci.yml job \"verify\" pins a pnpm version in the workflow as well as
        in package.json's packageManager field."
  Delete ONE of ci.yml's two setup steps        FAILS - correct
    -> "ci.yml job \"verify\" runs a pnpm command but never sets pnpm up"
  Drift the Dockerfile pin to 10.9.9            FAILS - correct

The middle one matters. My FIRST version of that third test was file-level -
it asserted the workflow file contained the string 'pnpm/action-setup'. It
PASSED the mutation, because ci.yml has two such steps and deleting one leaves
the other still matching. Caught it by running the mutation, rewrote it to walk
jobs individually, re-ran, and it now fails correctly. A file-level check would
have been a decoration.

LEFT ALONE DELIBERATELY, AND YOU SHOULD KNOW ABOUT IT:

  package.json carries `"pnpm": "^10.15.1"` as a DEVDEPENDENCY. That is a third
  latent pnpm version specifier, and it disagrees with the 10.4.1 pin.

  It is NOT the cause of this failure. pnpm/action-setup reads only its own
  `version` input and the `packageManager` field - it never looks at
  dependencies. And no package.json script shells out to `pnpm`, so the
  node_modules/.bin/pnpm shim it installs never shadows the corepack binary at
  runtime. I verified both before concluding this.

  It looks accidental - it sits next to `"add": "^2.0.6"`, which is the classic
  residue of someone typing `npm install add pnpm`. Worth removing eventually,
  but removing it regenerates the lockfile, which perturbs the dependency graph:
  a materially wider blast radius than "fix the pnpm-version conflict only."
  Flagging it rather than doing it. Say the word and I will clean it up as its
  own change, with the full gate re-run behind it.
