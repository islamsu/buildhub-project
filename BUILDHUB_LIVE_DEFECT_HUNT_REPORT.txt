1. THE DEPLOY WORKFLOWS HAD NEVER ONCE STARTED
--------------------------------------------------------------------------------

Both deploy workflows read ${{ secrets.*_BASE_URL }} in environment.url. GitHub
does not expose the `secrets` context to that field. The workflow therefore
failed validation AT STARTUP: zero jobs, zero seconds, and - the part that let it
hide for 83 runs - NO CHECK RUN AT ALL, so it never appeared in a PR's checks.

  PR #1 reported 9/9 green while merging a deploy pipeline that had failed on
  every single push to date.

EVIDENCE - two consecutive pushes to the same branch:

  ab302f2 (before)   ci.yml, deploy-production.yml FAIL 0s, deploy-staging.yml FAIL 0s
  0fae67d (after)    ci.yml only

An invalid workflow produces a run on every push regardless of branch filters,
because GitHub cannot evaluate `on:` on a file it cannot validate. Once valid,
`branches: [main]` applies again and a feature-branch push correctly produces no
deploy run.

CONFIRMED ON main AFTER MERGE - run #84, "Deploy staging", success in 7s:

  Is staging configured?        success   (step: if [ -n "" ] && [ -n "" ])
  Gate on the full CI suite     skipped
  Build and publish the image   skipped
  Migrate and release           skipped

Run #83 by contrast was displayed under its raw file path rather than its name -
GitHub shows the path when it cannot parse the `name:` field. That difference in
the run list was the visible symptom nobody read.

It failed CLOSED, so nothing shipped that should not have. The real cost is that
the pipeline had never executed once, and would not have begun working the moment
someone added the secrets it appeared to be waiting for.

FIX: base URLs are repository VARIABLES. That is the field's actual contract, and
a deployment hostname is not secret material. staging-qa.yml and
BUILDHUB_RENDER_STAGING_RUNBOOK.md already called STAGING_BASE_URL a repository
variable, so this settles a split brain rather than inventing a convention. SSH
host, user and key stay secrets.

New deploymentPipeline §4c walks every workflow for context interpolations and
checks each against an ALLOWLIST of fields GitHub actually exposes that context
to, so an unanticipated position fails closed.

2. A SUCCESSFUL SIGN-IN HANDED BACK A SESSION NOTHING WOULD ACCEPT
--------------------------------------------------------------------------------

Three independent defects sat between "sign-up succeeded" and "the next request
knows who you are".

2a. THE COOKIE BROWSERS REFUSE TO KEEP

    sameSite:"none" was pinned while `secure` was derived per request. Over plain
    HTTP that emits:

      Set-Cookie: app_session_id=...; Path=/; HttpOnly; SameSite=None

    SameSite=None is legal only alongside Secure. Browsers reject the pairing
    outright rather than downgrading it. Observed in Chromium: sign-up returned
    success, the server sent that header, THE BROWSER KEPT ZERO COOKIES.

    Local development could not authenticate in any browser.

    Note: productionHardening A7 already describes this exact hazard in its
    comment - and then pins the production half, which was correct. The broken
    half was the one it did not assert.

2b. THE SERVER REJECTED THE TOKEN IT HAD JUST MINTED

    createSessionToken stamps `appId: ENV.appId`; ENV.appId falls back to "".
    verifySession required appId to be a NON-EMPTY string while never comparing
    it to anything - so the check delivered none of the isolation its presence
    implied, and rejected every session the server issued:

      {"openId":"local_...","appId":"","name":"Debug User"}
      [Auth] Session payload missing required fields

    Render staging sets VITE_APP_ID and was unaffected. That is precisely why
    this survived: .env.example ships VITE_APP_ID empty, so the documented local
    setup could authenticate nobody, and staging QA's authenticated checks were
    among the SKIPs.

    FIX: appId is checked by COMPARISON when configured - strictly stronger, a
    token minted for another app under a shared secret is now rejected rather
    than accepted - and skipped when there is nothing to compare against.
    JWT_SECRET remains the trust boundary either way. `name` no longer gates
    validity; requiring it made createSessionToken(openId), the usage sdk.ts
    documents as its own example, mint a token that could never be redeemed.

2c. SIGN-UP LANDED ON THE LOGIN SCREEN

    useAuth reads auth.me from the React Query cache, still holding the `null`
    fetched when /auth loaded anonymously. goAfterAuth navigated straight to a
    protected route, whose guard saw an anonymous user and bounced to
    /auth?mode=login via window.location.href - a full page load, which discarded
    the refetch too.

    The account existed and a manual reload landed correctly, which is exactly
    what made it look like a login bug rather than a stale-cache one.

    logout already invalidated this query. Sign-in, sign-up and QA-link
    redemption did not.

VERIFIED AFTER FIX, real browser, real MariaDB: registration lands on
/platform/homeowner, the browser keeps the cookie, auth.me returns the user.

3. "PROTECTED" IS NOT "AUTHORIZED" - THE PAID ENQUIRY GATE WAS OPTIONAL
--------------------------------------------------------------------------------

The qualified-enquiry model gates an RFQ's full detail behind approval, declared
categories, a billing entitlement, and one credit per lead enforced by a unique
index in the database. Two procedures beside it handed the same detail out free.

PROVEN with one brand-new, unapproved, free contractor account - one sign-up, no
approval, no payment:

  rfq.eligible      BLOCKED   FORBIDDEN
  rfq.openEnquiry   BLOCKED   FORBIDDEN
  rfq.list          ALLOWED   50 rows, every column
  rfq.get(id)       ALLOWED   any RFQ, entire row

rfq.get had no ownership check at all and no callers in the client. It is now
scoped by requesterId, returning NOT_FOUND rather than FORBIDDEN so it does not
confirm an id exists to someone who cannot see it.

rfq.list keeps its browse role but drops `attachments` and takes an explicit
column allowlist instead of select().from(rfqs). `attachments` holds the URLs of
the requester's own uploads - drawings, BOQs, site photos - and RFQPage renders
them inline for every RFQ in the feed, so every signed-in account held direct
links to every requester's files. Owners still get their own through myList,
which is scoped by requesterId, and parseRfqAttachments treats the absent field
as "none", so the page degrades exactly right.

THIS IS HALF OF A FIX I MADE MYSELF. Slice 9 moved rfq.list from public to
protected because it was serving every column to anonymous callers, and the sweep
stopped there - the comment I left in RFQPage even names the column exposure. The
§2 test asserted the tier and called rfq.get safe because it "had always been
protected", which is precisely the assumption that was wrong.

    openQualifiedEnquiry charges a credit for "full detail" - and narrowing it

4. METRIC LABELS WERE UNREADABLE ON A PHONE, AND WORSE IN ARABIC
--------------------------------------------------------------------------------

The role platform's stat cards sit in a two-column grid below `sm`. Minus a fixed
44px icon, the gap and the padding, the text column got about 63px - and the
label carried `truncate`. Measured in a real browser at 375px:

  "Total Projects"    wanted 72px, had 63px
  "Active Projects"   wanted 79px, had 63px
  "Total Budget"      wanted 67px, had 63px

English degraded to a guessable "Total Projec...". Arabic degraded to
"إجمالي ال..." and "مشاريع ن..." - longer words, and the label is the only thing
naming the number, so what is left identifies nothing.

FIX: the card stacks the icon above the text below `sm` and the label wraps.
Re-measured: zero clipped text nodes in either language, the only remaining one
being the sr-only "Toggle Sidebar", which is meant to be invisible. Arabic now
reads in full: إجمالي المشاريع · مشاريع نشطة · الميزانية الإجمالية · إجمالي الإنفاق

--------------------------------------------------------------------------------
TWO OF MY OWN MISTAKES, CORRECTED IN PLACE
--------------------------------------------------------------------------------

Reporting these because they are the same failure mode as the defects above.

A VACUOUS TEST THAT SURVIVED ITS OWN MUTATION TEST. The first version of the
truncation regression sliced a window around indexOf('{metric.label}'), which
matched `<Card key={metric.label}>` a hundred characters earlier. The window
never contained the className, so the test passed whatever the code said. I
caught it only because I ran the mutation and it did NOT fail. It now matches the
element by regex and asserts the match was found, so it cannot go vacuous
silently.

A DETECTOR THAT FAILED FOR ITS OWN REASONS. The journey harness's crash detector
matched page.content(), which hit React's minified internals
("errorBoundary:e.tag===1?...") inside the bundle and reported a crash on every
healthy page - 8 uniform failures that were entirely my instrumentation. Uniform
failure across cases that obviously work is a signal to doubt the detector. It
reads visible text now.

A NOTE ON WHAT "GREEN" MEANT HERE
--------------------------------------------------------------------------------

Before today: 1,139 tests passing, CI green on every commit, staging QA 160/160.

Also true before today: the deploy pipeline had never executed, first-party login
did not work anywhere VITE_APP_ID was unset, the paid enquiry gate could be
walked around by any free account, and the mobile dashboard's labels were stubs.

Green tests are evidence that the things you thought to check still hold. They
are not evidence that the system works. The only thing that told me any of this
was pointing a browser at it and watching what actually happened.
