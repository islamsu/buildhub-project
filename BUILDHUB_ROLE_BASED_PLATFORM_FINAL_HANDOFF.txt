2. WHAT ELSE WAS FOUND, IN ORDER OF WHAT A REGRESSION WOULD COST
--------------------------------------------------------------------------------

F1  admin.createUser was a SECOND, WEAKER WAY TO MAKE AN ADMINISTRATOR
    (commit a8aeccc)

    shared/adminRoles.ts states the invariant in its own comments: "SUPER_ADMIN
    is the only role holding admins.manage, so it is the only role that can
    create or re-role an administrator." admin.createUser contradicted it. It
    is gated on `users.manage`, which USER_ADMIN holds; its enum accepted
    'admin'; the row it wrote said role='admin'. The AdminDashboard "Create
    account" dialog offered the option.

    THIS IS NOT A PRIVILEGE ESCALATION AND IS NOT REPORTED AS ONE. adminRole is
    left null, hasAdminPermission fails closed on null, and all 38
    adminWith(...) endpoints - superAdminProcedure among them - still refuse the
    account. Established by reading the middleware.

    What it DID produce is a row the platform treats as an administrator
    everywhere it checks `role` rather than `adminRole`:
      - exempt from the frozen-account check in _core/trpc.ts, so a USER_ADMIN
        could create an account that cannot be frozen;
      - rendering the full admin menu;
      - reaching bare adminProcedure (admin.me, admin.changeOwnPassword);
      - created with no adminInvitations row and no `admin_created` audit
        event - the only record that an administrator was ever made.

    FIXED in two halves, the same shape as the updateRole fix: the enum no
    longer offers 'admin', and the insert writes the literal role:'user'
    instead of deriving the authorization column from the request at all.

F2  A QUOTATION COULD BE SUBMITTED AGAINST A CLOSED OR AWARDED RFQ
    (commit 7e6445d)

    rfq.submitQuotation inserted FIRST and looked the RFQ up afterwards, only
    to address the notification. So a requester who had already accepted
    somebody kept receiving new bids. The client filters its pipeline to
    status === 'open', which is why nobody hit it through the UI - and which is
    precisely the reasoning this phase rejects. An RFQ that did not exist came
    back a 500 from the foreign key rather than a 404. price and warranty were
    unbounded against decimal(12,2) and varchar(100), so a NEGATIVE bid was
    accepted.

F3  SEARCH INPUTS - WILDCARDS AND AN UNBOUNDED PUBLIC LIMIT
    (commit 6090a6d)

    NOT SQL injection: Drizzle binds like() as a parameter. But `%` and `_` are
    the pattern language of LIKE and four call sites interpolated raw input, so
    a visitor searching the public catalogue for "%" matched every row. And
    marketplace.list - public, unauthenticated - took
    `limit: z.number().default(24)` with no int, no minimum and no maximum, so
    limit:100000 returned the entire catalogue in one request. Its sibling
    marketplace.vendors already had .int().positive().max(100); this one was
    simply never brought up to it.

F4  THREE ROLE WORKSPACES DESCRIBED WORK BUILDHUB CANNOT DO
    (commit 06387e0)

    "Material Quality Inspection - Audit supplier specifications against
    engineering standards": no button, no data, no backend. A whole workflow
    announced and never built.
    "Validate load requirements and reinforcement schedules": BuildHub
    validates nothing and signs off nothing.
    "Present architectural renderings and client mood boards directly in
    workspace": there is no portfolio hosting anywhere in the product.

    The first two now point at capability that genuinely exists. The third is
    the case PHASE 1B singles out - the capability does not exist, so the card
    SAYS SO, in a dashed panel that names what does exist and takes the
    architect there.

F5  NOTIFICATIONS WERE STORED IN ENGLISH ONLY
    (commit 892da4d, migration 0022)

    notifications.title/.body hold prose rendered at WRITE time, in a product
    whose language is a per-viewer choice made at READ time. An Arabic-speaking
    contractor, in an interface Arabic down to the font, read "You received a
    new quotation for ..." in English. All five writers wrote English.

F6  marketplace.askQuestion LET TEN PRODUCT IDS SKIP VALIDATION
    (commit ea66fe6)

    `if (!product && input.productId > 10)` - a leftover accommodation for the
    static mock catalogue, which the RESTRICT foreign key now turns into a 500
    for exactly those ids. It also never checked `active`, so a question could
    attach to a product the supplier had withdrawn.

F7  "STORAGE NOT CONFIGURED" WAS REPORTED AS A SERVER ERROR
    (commit 1ce211a)

    The /manus-storage/* proxy answered 500 when no backend is configured.
    Nothing failed; the deployment simply has no storage. 500 sends an operator
    hunting a crash and a monitor paging somebody over a missing environment
    variable. Now 503.

--------------------------------------------------------------------------------

Stated explicitly, because "we looked and it was fine" is evidence too.

  - adminProcedure never reads userRole. The authorization column and the
    marketplace column are genuinely separate.
  - Self-service role selection RESETS approval: choosing a provider role sets

    the project to ctx.user.id before touching it - none had a test naming
    them, and now the census does.
  - marketplace.myProducts is SUPPLIER-ONLY, stricter than "provider access
    required" suggests: an approved contractor is refused.

THE CENSUS IS THE ONE WORTH ARGUING ABOUT. PHASE 1B asked for 16 resources x 6
roles x 9 verbs. Written literally that is 864 cases, most of them vacuous, and
the ones that are not would be pinned by a list somebody must remember to
extend. The list is the part that rots. The census instead enumerates the real
surface from source and requires every id-taking procedure to fall into exactly
one of three buckets. The property is not that today's 62 are right; it is that
tomorrow's 63rd cannot be quietly wrong.

6. OPEN - OWNER DECISION, NOT INVENTED HERE
--------------------------------------------------------------------------------

DUPLICATE QUOTATIONS. Nothing stops one provider submitting several quotations
on a single RFQ, and each one notifies the requester again. Whether a second
submission should be REFUSED, or should REPLACE the first as a revision, is a
product decision about how bidding works on BuildHub. It is not inferable from
the schema, so it was left alone and recorded in the code at the point where
the decision would be enforced.

  Refuse:  simplest, and the strongest anti-spam posture. Costs providers the
           ability to correct a mistyped price without contacting support.
  Replace: matches how tendering usually works, and keeps the requester's
           inbox to one notification per bidder. Needs a decision about what
           happens to a revision AFTER the requester has read the original.

Adjacent, and also unresolved: notification bodies for a REVISED quote, and
whether the requester should see the bid history or only the current bid.
