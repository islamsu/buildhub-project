1. THE OWNER DECISION, LOCKED INTO THE CODE
================================================================================

GLOBAL was approved with a definition. That definition is now enforced by the
type system rather than living in a document.

WHAT GLOBAL MEANS
  ROOT / TAXONOMY-WIDE DISCOVERY WITHIN THE APPLICABLE GEOGRAPHIC MARKET.

WHAT IT DOES NOT MEAN
  One worldwide BuildHub placement across every country, forever. The name is
  the only thing about it that sounds global, and that is now said explicitly
  at the top of shared/placement.ts.

THE FOUR DIMENSIONS
  GEOGRAPHIC SCOPE · TAXONOMY SCOPE · SURFACE · TIME
  GLOBAL is a value of the TAXONOMY dimension only.

HOW THE GEOGRAPHIC DIMENSION IS CARRIED WITHOUT BEING BUILT

No market column was invented. BuildHub sells one market today, and adding a
column for a business that does not exist yet would be building a feature out
of a comment.

Instead the dimension is carried STRUCTURALLY. Every scope-matched query now
goes through one typed value:

    export type PlacementScope = {
      taxonomy: string;
      market?: undefined;   // declared, deliberately unused - see below
    };

`market` is declared and always undefined. The day a second market opens, it
becomes part of THIS type, and the compiler points at every site that has to
account for it. A bare `category: string` would let that day arrive silently,
with a Saudi Master and an Egyptian Master quietly contesting one exclusive
slot - which is precisely the failure the owner's definition rules out.

This was a real refactor, not a comment: livePlacementRows, placedProviders and
placedProducts all changed signature, and the test suite caught the change at
runtime (see section 6 for why tsc did not).


================================================================================
2. CP-3 — SPOTLIGHT (Provider and Product)
================================================================================

MASTER AND SPOTLIGHT ARE KEPT STRICTLY APART

  MASTER      root discovery, before a type or category is chosen. ONE slot.
  SPOTLIGHT   after a type or category is chosen. Up to THREE.
  BOOST       among relevant search and results listings.

Blurring them is a commercial error, not a cosmetic one. `spotlightProviders`
and `spotlightProducts` REFUSE a root-scope request rather than falling back to
the Master inventory: answering it from there would sell one advertiser's
exclusive slot as three. A Spotlight request with no category returns nothing.

CAPACITY IS DEFENDED AT RENDER TIME, not only at booking time

The booking engine already refuses to oversell. The resolver does not trust
that: four live bookings in one scope render three, in booking order, and if
the first becomes ineligible the fourth takes the slot. Oversold inventory
truncates rather than overflows - fail-closed, in the buyer's favour.

SCOPE IS MATCHED EXACTLY

A Tiles placement cannot appear under Lighting. A Designer-only placement
cannot appear under Contractors. This is enforced in the WHERE clause, not
filtered afterwards.

UI

Spotlight sits between the category heading and the organic results: prime
position, capped at three, single column on narrow screens so the organic list
stays one short scroll away rather than behind an advertising wall. It
collapses entirely when nothing is booked - no empty premium heading, and no
invented cards.

ONE CARD COMPONENT, NOT TWO

The provider card is now shared by the Master slot and the Spotlight block.
Two card components is how a field ends up on the smaller surface that the
larger one withholds - or how a fabricated field appears where nobody is
looking. The comment claiming this was written first; the refactor that made it
true followed immediately.


================================================================================
3. CP-4 — BOOST
================================================================================

THE RULE THAT MAKES "PAY TO APPEAR IN UNRELATED SEARCHES" IMPOSSIBLE

Master and Spotlight PUT an advertiser onto a surface, so each proves relevance
by matching a scope exactly. Boost is different in kind: it moves an entity UP
a list it was already on. The implementation is built around that difference.

  A boosted entity the organic query did not return cannot be lifted, because
  there is nothing to lift.

Both listings now run their organic query FIRST and hand the result to
applyBoost, which drops every id the query did not return. A Tiles product is
absent from a Lighting result set, so no amount of Boost can put it there. That
is a structural guarantee, not a policy someone has to remember.

THE SECOND GUARD

A provider legitimately listed under both Contractor and Designer appears in
both result sets. If they bought Boost for Contractor, lifting them inside a
Designer-filtered search would sell a scope they did not buy. So when a
category filter is active, the placement's own scope must match it. With no
filter active the visitor is searching everything, and the intersection is the
relevance test on its own.

THE MARKETPLACE STAYS USEFUL

  SHARE CAP     at most a THIRD of a page is boosted. Nine boosted rows in a
                nine-row page yield three lifted, not nine. A three-row page
                yields one.
  SPREAD        boosted rows occupy every third position from the top, so the
                reader meets an organic result immediately after the first
                sponsored one. All-boosted-first is an advertising page with a
                marketplace underneath it.
  DETERMINISTIC applyBoost is a PURE function - no clock, no Math.random. A
                strip that reshuffles while the reader looks at it is unusable,
                and a random one cannot be audited when an advertiser asks
                where their placement appeared.
  LOSSLESS      re-ranking adds nothing and loses nothing.

LABELS

A boosted row is an ordinary card carrying its own honest label, not a separate
section - because Boost changed its position and nothing else. On products the
placement label takes precedence over the catalogue's `featured` flag, which is
a different thing entirely and not a commercial arrangement.

4. CP-5 — PLACEMENT ANALYTICS
================================================================================

FOUR REAL OBSERVATIONS, AND DELIBERATELY NOT A FIFTH

  PLACEMENT_IMPRESSION
  PLACEMENT_ENTITY_VIEW
  PLACEMENT_CTA_CLICK
  PLACEMENT_QUALIFIED_ENQUIRY

There is no SALE, ORDER, REVENUE, GMV or COMMISSION event anywhere in this
change. BuildHub observes none of them while payments are deferred, and an
event type is an invitation to populate it. A test asserts that no such field
appears on a performance row.

The existing analytics framework was reused rather than duplicated - same
recordEvent, same metadata sanitisation, same never-break-the-product rule.

WHAT AN IMPRESSION IS

An API call is NOT an impression. The server answering masterProvider says only
that a page asked the question; it may have been a prefetch, a bot, a
background tab, or React Query refetching on window focus. So the rule is
written down in shared/placementAnalytics.ts and implemented against it:

  Half visible, for one continuous second, at most once per placement per page
  view.

  RENDERED        a fetched-but-undrawn placement was not seen.
  HALF VISIBLE    a sliver at the edge of the viewport was not seen. 50% is the
                  threshold most ad standards settle on; a published convention
                  beats a private one.
  ONE SECOND      a placement scrolled past at speed was not seen.
  ONCE PER VIEW   the defence against rerender inflation. React re-renders for
                  reasons unrelated to the reader - a parent state change, a
                  refetch, a language toggle - and each would otherwise be
                  another billable "view".

It cannot prove a human looked; nothing available to a web page can. It is a
conservative, documented, checkable approximation, written down so that what
BuildHub sells is a DEFINED thing rather than a number of unexplained origin.

Where IntersectionObserver is unavailable the client falls back to
mounted-and-painted after the same dwell - more conservative in every respect
except viewport position, and stated rather than hidden.

WHAT A BROWSER MAY AND MAY NOT ASSERT

This is the one analytics surface an untrusted party can write to, because most
marketplace browsing is anonymous and an advertiser's impressions must not be
limited to signed-in readers. It is narrowed accordingly:

  - the event type is a CLOSED enum, and QUALIFIED_ENQUIRY IS NOT IN IT. A
    visitor who can post their own conversions can manufacture an advertiser's
    performance report. Attribution is written SERVER-SIDE from the enquiry
    record, at the moment the real relationship comes into existence.
  - the placement must EXIST and be LIVE, so a fabricated id records nothing
    and an expired campaign stops accruing.
  - the surface and entity are read from the placement ROW, never from the
    request, so a reporter cannot attribute their event to another booking.
  - nothing personal is stored: no address, no agent, no fingerprint. A test
    asserts the metadata keys are exactly surface, entityType, entityId.
  - it is rate limited by IP, since there is no account to key on - and
    generously, because throttling honest reporting would UNDERSTATE what an
    advertiser received, which is its own kind of dishonesty.

HONEST LIMITATION, RECORDED IN THE MODULE RATHER THAN OMITTED

What remains possible for a determined party is inflating the counts of a
placement that genuinely exists. That is the same exposure any web analytics
has, it is bounded by the checks above, and it is written into
server/placementAnalytics.ts as a known limit rather than described as
prevented.

RATES ARE NULL, NOT ZERO

A placement nobody has seen reports zeros and NULL rates, rendered as a dash.
"0% clicked" asserts that people saw it and chose not to act; with no
impressions the truth is that there is nothing to compute yet. Those are
different facts for anyone deciding whether a campaign is working.

THE FORMULAS ARE PRINTED ON THE SCREEN

  CTR             CTA actions ÷ impressions
  View rate       entity views ÷ impressions
  Conversion      attributed qualified enquiries ÷ entity views

Held as data in shared/placementAnalytics.ts so the Admin screen and the tests
read the SAME definition. A rate computed one way in a report and another way
in a test is how two people end up arguing about a number that means nothing.

ADMIN SURFACE

client/src/components/PlacementPerformance.tsx, mounted beside the bookings it
measures so an administrator need not hold a placement id in their head. Names
the business, not the row id. Zero placements renders a real empty state, not a
demonstration table with plausible numbers in it.

6. THINGS THAT WENT WRONG, AND WERE FIXED BEFORE ANY RESULT WAS REPORTED
================================================================================

SIX PROBE / INSTRUMENT DEFECTS. None of these were platform defects; all were
faults in my own measuring equipment, and each was fixed rather than worked
around.

1. book() read LAST_INSERT_ID() on a SECOND mysql connection. That value is
   per-connection, so it returned 0 and every placement id became NaN. The
   insert and the read now share one statement.

2. Multi-line `-e` queries make the MariaDB client emit a "PAGER set to stdout"
   banner ahead of the result, which silently turned every Number(sql(...))
   into NaN. Queries are now collapsed to one line and the banner is stripped.

3. The row-integrity check hardcoded 6 Lighting products when an earlier
   Spotlight fixture had already created a seventh. It now compares against
   what the database actually holds.

4. The impression observer's ref sat on <Card>. Card forwards its props onto a
   div, so a ref would PROBABLY reach it - but "probably", resting on a React
   version detail, is not a sound foundation for a number an advertiser is
   billed against. It now sits on an explicit wrapper element.

5. An orphaned server process was still holding port 5401 and answering with
   OLD code, briefly making a working endpoint look missing.

6. (From report 1, repeated here because it recurred) a crashed probe run left
   rows behind; the probe purges its own namespace before asserting an empty
   state.

A GUARD OBJECTED, AND WAS RIGHT TO

server/dataIsolationMatrix.test.ts flagged marketplace.recordPlacementEvent for
taking an id without constraining by ctx.user.id. The rule is correct in
general. An advertisement, however, has no owner among its viewers - it is
shown to everyone, most of them anonymous - so owner-scoping it would limit an
advertiser's impressions to signed-in readers.

It is therefore a NAMED exemption with the reasoning recorded in the test file,
not a silenced rule. The entry states what IS constrained (the placement must
exist and be live), that the endpoint reads nothing back, and that the event
worth forging is absent from the client enum entirely.

A LIMITATION OF THE TYPECHECK, WORTH KNOWING

tsconfig excludes `**/*.test.ts`. A clean `tsc --noEmit` therefore does NOT
typecheck test files. When livePlacementRows changed signature, tsc stayed
green and the test RUNTIME caught it. This is recorded so nobody reads "tsc
clean" as broader than it is.
