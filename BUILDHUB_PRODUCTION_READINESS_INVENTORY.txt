HEADLINE FINDING — READ FIRST
--------------------------------------------------------------------------------

There is no production deployment target. Two facts from the repository:

  1. `.github/workflows/deploy-production.yml` deploys over SSH to a Docker
     host at `/srv/buildhub` (docker compose, .image.env, backup-before-release.sh).
     It does NOT deploy to Render.
  2. `render.yaml` provisions only `buildhub-staging` and a private
     `buildhub-staging-mysql`, from branch
     `claude/phase4b-readiness-audit-hardening`, with `autoDeploy: true`.

So the pipeline that is *proven* (Render, git auto-deploy, preDeployCommand
migrations) is not the pipeline production would use, and the pipeline
production would use (SSH + Vultr) has never run — its host does not exist,
none of its six secrets are set, and `PRODUCTION_BASE_URL` is unset.

This is the root of most RED rows below. It is a provisioning gap, not a code
defect.

16E. DOMAIN / HTTPS / COOKIE / CORS
================================================================================

Production domain     : NOT CONFIGURED. No domain appears anywhere in the
                        repository, and I have not invented one. Concrete launch
                        task — see PHASE 2.
HTTPS                 : Assumed by construction in production. `helmet` sets HSTS
                        only when isProduction: max-age 63 072 000 (2 years),
                        includeSubDomains, preload. `upgradeInsecureRequests` is
                        added to the CSP in production only.
Secure cookies        : `secure` is PINNED true in production
                        (`server/_core/cookies.ts`), not derived per request —
                        one proxy hop that looked plain-HTTP would otherwise hand
                        back a cookie the browser discards, logging users out for
                        no visible reason.
SameSite              : `secure ? "none" : "lax"`. Production ⇒ `None; Secure`,
                        which is the only legal pairing. (Pinning "none" while
                        secure derived false was a real defect: browsers dropped
                        the cookie outright and local development could not
                        authenticate in any browser.)
Cookie domain         : NOT SET (the domain-derivation block is commented out),
                        so the cookie is host-only on the exact origin that set
                        it. Correct for a single-origin deployment; if production
                        ever needs `app.` and `www.` to share a session, this is
                        the line that must change.
Cookie path           : `/`
CORS                  : **No CORS middleware exists at all.** Deliberate and
                        correct: the API is same-origin (Express serves the built
                        SPA and mounts tRPC on the same host), so no
                        `Access-Control-Allow-Origin` is needed. The CSP already
                        pins `connectSrc: 'self'` in production. If a separate
                        front-end origin is ever introduced, CORS becomes a new
                        requirement — today its absence is the safe state.
Allowed origins       : CSP `defaultSrc 'self'`; `frameAncestors 'none'`;
                        `objectSrc 'none'`; `baseUri 'self'`; `formAction 'self'`.
                        External hosts permitted: fonts.googleapis.com (styles)
                        and fonts.gstatic.com (fonts) only.
APP_BASE_URL          : Unset for production. Password-reset and invitation links
                        are built from it and NOT from the Host header —
                        deliberately, so an attacker who can set that header
                        cannot have a reset link for their own domain mailed to a
                        victim. Consequence: **until APP_BASE_URL is set,
                        password reset reports itself unavailable.**
OAuth callbacks       : N/A. OAUTH_SERVER_URL is empty; auth.capabilities reports
                        `oauthSignIn: false` and the UI hides that door.
Password-reset URLs   : Derived from APP_BASE_URL. Blocked with SMTP (§16J).
Invitation URLs       : Admin invitations are RELATIVE
                        (`/admin/accept-invitation?token=…`) and are returned to
                        the browser, never emailed — so they carry no host and
                        cannot leak a staging URL into production.
Webhook URLs          : None exist. No webhook endpoint is implemented (§16L).
Staging URL in prod?  : Cannot happen through code. No staging hostname is
                        hard-coded anywhere; every URL is derived from
                        APP_BASE_URL / RENDER_EXTERNAL_URL. The one risk is an
                        operator copying a staging .env — mitigated by the fact
                        that staging's secrets are `generateValue`/`sync: false`

16F. AUTHENTICATION / AUTHORIZATION — FINAL REVIEW
================================================================================

Enforcement is server-side in `server/routers.ts`. The frontend guard in
AdminDashboard is cosmetic; removing it changes what is DRAWN, not what is
PERMITTED.

  adminProcedure   = authenticated  AND role==='admin'  AND isAdminRole(adminRole)
  adminWith(p)     = adminProcedure AND hasAdminPermission(adminRole, p)
  superAdmin       = adminWith('admins.manage')   ← SUPER_ADMIN only

Role coverage (all five roles + normal users):
  SUPER_ADMIN        all 10 permissions incl. admins.manage — verified
  USER_ADMIN         users.read/manage, audit-scoped — verified
  MARKETPLACE_ADMIN  marketplace.manage — verified
  SUPPORT_ADMIN      support.manage, qa.manage — verified
  BILLING_ADMIN      billing.read/manage — verified
  normal users       refused at the door (403) on every admin endpoint

Attack-by-attack:

Privilege escalation   BLOCKED. Only `admins.manage` reaches createAdmin /
                       setAdminRole, and only SUPER_ADMIN holds it. A sub-admin
                       calling either gets FORBIDDEN before any input is read.
Self-promotion         BLOCKED twice over. `setAdminRole` refuses when
                       `input.userId === ctx.user.id` — so "modify your own role"
                       is impossible for EVERYBODY, not only sub-admins. (It also
                       prevents a Super Admin demoting themselves into an
                       unrecoverable platform with nobody able to manage admins.)
Role manipulation      BLOCKED. Permissions are DERIVED from role via a static
                       map; there is no per-user permission record to edit, so
                       there is no row to tamper with.
Unauthorized routes    BLOCKED, proven on LIVE staging (run #12):
                         admin.me      anonymous 401 · customer 403
                         admin.admins  anonymous 401 · customer 403
                         admin.users / commercialKpis / productAnalytics
                                       anonymous 401 · non-admin 403
Revoked admin access   ENFORCED. revokeAdminSessions / setAdminActive(false) /
                       setAdminRole all stamp `sessionsInvalidBefore =
                       revocationCutoff()` (now + 1000 ms). The +1000 ms is not
                       cosmetic: the comparison is whole-second and strict `<`,
                       so a session issued in the SAME second as the revocation
                       previously SURVIVED it. Found by live probing, fixed.
Disabled accounts      ENFORCED at the door: adminSignIn refuses when
                       `accountStatus !== 'active'` or `deactivatedAt` is set —
                       with the SAME 401 as a wrong password.
Invitation reuse       BLOCKED. `usedAt` is stamped on redemption and checked on
                       every attempt. Test-login links go further: the burn is an
                       atomic `UPDATE … WHERE usedAt IS NULL`, so two simultaneous
                       redemptions race and exactly one wins.
Expired invitations    BLOCKED. 48-hour TTL (`ADMIN_INVITE_TTL_HOURS`), checked
                       against `expiresAt` at redemption; also revocable.
Password-reset abuse   BOUNDED. Rate-limited (§16O). `resetAdminPassword` does
                       not set or reveal a password — it invalidates the current
                       credential and issues a fresh single-use invitation, so a
                       stolen reset gains an attacker nothing without the token.
Session invalidation   Per-session via `revokedSessions` (jti); bulk via
                       `sessionsInvalidBefore`. Logout, password change, admin
                       revocation and deactivation all exercised.
Cookie security        httpOnly, Secure (pinned in production), SameSite paired
                       correctly, path=/. §16E.
Cross-user data access BLOCKED at the query, not the response: explicit column
                       allowlists on every client-facing user query (`passwordHash`
                       and `invitationToken` are never in a select list), and
                       `rfq.quotations` is scoped by `requesterId` because a
                       quotation carries a rival vendor's email, price and terms.
IDOR                   Closed on the paths audited in Slice 9: `rfq.get` is scoped
                       `WHERE id = ? AND requesterId = ?` and returns NOT_FOUND
                       (not FORBIDDEN) so it does not confirm an id exists;
                       `rfq.list` drops `attachments`; project sub-resources are
                       owner-scoped. **One residual gap — see 16P/F-1.**

Evidence: 34 authorization tests + 22 invitation tests locally; 1240/1240 total;
9/9 credential-free admin-door checks against live staging in run #12; 5 mutation
reverts on the admin security surface, each caught by its own test. No
destructive test was run against production — there is no production to run one
against.

STATUS: READY.

16H. ADMIN BOOTSTRAP — PRODUCTION PROCEDURE
================================================================================

Confirmed from `server/adminBootstrap.ts`: THE BOOTSTRAP CANNOT MODIFY AN
EXISTING ADMINISTRATOR. Its first action is
`SELECT count(*) FROM users WHERE role='admin'`; any non-zero result returns
`already-exists` and it touches nothing. It cannot promote, re-role, reset a
password, or create a duplicate. It always INSERTS a new account from the
supplied identity rather than elevating a matching one, so pointing it at
someone else's email grants that person nothing. It is never a request handler —
the only trigger is process start.

One correction to state plainly: the bootstrap is **not** environment-gated. It
has no isProduction check and no flag; it runs identically wherever deployed.
Production is protected by deployment isolation (separate host, separate
database) plus the create-only gate — not by a staging-only switch. Running it
in production is the INTENDED path for creating the first production admin.

PROCEDURE (NOT EXECUTED — no credentials requested, none exposed):

  1. On the production host, add to `/srv/buildhub/.env`:
       ADMIN_BOOTSTRAP_EMAIL=<production admin email>
     Format: valid address; trimmed and lowercased before use.
  2.   ADMIN_BOOTSTRAP_USERNAME=<username>
     Format: 3–100 chars, `[a-z0-9._-]` only; trimmed and lowercased — so
     `IslamSu` is stored and typed as `islamsu`.
  3.   ADMIN_BOOTSTRAP_PASSWORD=<generated by a password manager>
     Minimum 12 characters, taken VERBATIM (not trimmed — a stray trailing space
     becomes part of the password). Never typed into chat, a ticket, or a commit.
  4. Restart production so the process re-reads its environment
     (`docker compose --env-file .env --env-file .image.env up -d`).
     No rebuild and no new image are required.
  5. Verify from the logs. Exactly one of:
       [bootstrap] Created the first administrator (<username>). Unset
       ADMIN_BOOTSTRAP_* now - it is inert from here on.
       [bootstrap] An administrator already exists; bootstrap did nothing.
       [bootstrap] ADMIN_BOOTSTRAP_* is set but unusable: <reason>
       [bootstrap] Database unavailable; skipped administrator bootstrap.
     The password appears in none of them, by test.
  6. Log in at  https://<production-domain>/admin/login  with the email OR the
     username plus the password. (Both identifiers were lowercased on the way in,
     so sign-in is case-insensitive.)
  7. Remove all three variables from `.env` and restart. Leaving them set cannot
     reset anybody — but clearing them means production holds no standing admin
     credential in its environment at all.
  8. Verify normal admin login still works after the restart, and confirm
     `/admin/admins` lists exactly one SUPER_ADMIN.

FAILURE MODE TO EXPECT: the bootstrap NEVER throws. A misconfiguration degrades
to "no admin account", never to a boot loop.

16I. ADMIN INVITATION / SUB-ADMIN OPERATIONS
================================================================================

Token cryptographically random?  YES. `randomBytes(32)` → base64url. 256 bits.
                                 Never a user id, an email, a sequence, or a
                                 password in a URL.
Only the hash persisted?         YES. `adminInvitations.tokenHash` is SHA-256,
                                 UNIQUE. The raw token exists only in the response
                                 to the creating Super Admin. Unsalted SHA-256 is
                                 correct here precisely because the input is
                                 already 256 bits of CSPRNG entropy — salting
                                 would buy nothing and break the unique-index
                                 lookup.
Expires?                         YES. 48 hours (`ADMIN_INVITE_TTL_HOURS = 48`).
Single-use?                      YES. `usedAt` stamped and checked.
Invitee selects the password?    YES. The account is created with NO passwordHash
                                 and cannot authenticate until step 4 —
                                 `adminSignIn` treats a null hash as no account.
Visible to the Super Admin?      NEVER. It does not exist until the invitee
                                 chooses it.
Reusable?                        NO — used, expired and revoked are all checked.
Self-escalation?                 NO. §16F.
Only Super Admin manages admins? YES — all eight management endpoints are
                                 `superAdminProcedure`.
Permissions server-side?         YES. §16F.

OPERATIONAL PROCESSES

Create an administrator
  /admin/admins → name, email, username, role → the invitation link is shown
  ONCE. Deliver it out of band (Signal, a phone call, in person). It is NOT
  emailed — SMTP is unconfigured, and administrator credentials should not be
  sent by email regardless. Record only WHO was invited, never the token.

Revoke an administrator
  Immediate:  admin.setAdminActive(userId, false)  → account refused at the door
              AND every live session invalidated in the same write.
  Permanent:  additionally admin.revokeAdminSessions(userId) if the account is
              being kept but locked out.
  Accounts are deactivated, never deleted — the audit trail must keep pointing at
  a real row.

Reset administrator access
  admin.resetAdminPassword(userId). Invalidates the current credential, revokes
  sessions, issues a fresh single-use invitation. No password is set or shown.

Replace an administrator
  Create the successor first and confirm they can sign in; then deactivate the
  predecessor. Never the other way round — with one Super Admin, deactivating
  first strands the platform (and self-deactivation is refused precisely to stop
  that).

Handle an expired invitation
  Do not extend it — there is no extend path by design. Either
  admin.revokeAdminInvitation then admin.createAdmin again, or for an account
  that already exists, admin.resetAdminPassword to mint a fresh 48-hour token.

Areas reviewed clean: authentication (§16F), authorization (§16F), secrets
(§16A), cookies (§16E), CORS (§16E — absent, and correctly so for a same-origin
deployment), database access (parameterised throughout via Drizzle; no string
concatenation into SQL), password handling (§16I), error responses (§16N),
client-side secret exposure (§16A item 4, proven by QA section 21).

THREE ACTIONABLE FINDINGS. None was changed — this phase is evidence-only.

F-1  MEDIUM — `rfq-attachments/` in the storage proxy is broader than the data
     rule it was written to match.
     `authorizeStorageKey` returns TRUE for any `rfq-attachments/` key to any
     authenticated user, and its comment justifies this with: "rfq.get/rfq.list
     already expose full RFQ detail - including these attachments - to any
     authenticated user by design". **Slice 9 made that comment false.**
     `rfq.list` no longer returns attachments and `rfq.get` is owner-scoped, so
     the proxy is now the loosest surface, not the matching one.
     Exploitability: keys are `rfq-attachments/user-<id>/<filename>_<8 hex>.<ext>`.
     The 8-hex suffix is 32 bits, and the user id is a small integer, so an
     attacker needs the original filename plus ~2^32 guesses per file. Not
     practical at scale; not a number to rely on either.
     Recommended fix (one function, not a rewrite): scope `rfq-attachments/` to
     the RFQ's requester plus providers who have opened a qualified enquiry on
     that RFQ — the same rule the credit already buys — resolving the key through
     the owning `rfqs.attachments` row.

F-2  LOW — uploaded objects are never deleted.
     No endpoint removes an object from the bucket, so deleting an RFQ, a message
     or an account leaves its files in storage indefinitely. Cost issue today;
     a right-to-erasure issue the moment real personal data is involved.

F-3  LOW — no per-account upload rate limit (= O-3). Recorded in both places
     because the consequence differs: abuse control here, storage cost there.

NOT FINDINGS, recorded so they are not re-litigated:
  · Absence of CORS middleware is correct for a same-origin app.
  · Unsalted SHA-256 on invitation tokens is correct — the input is already 256
    bits of CSPRNG entropy.
  · The free feed showing description and budget is an accepted product decision
    (§16M), not a vulnerability.
