DEFECT 1 — THE FEATURE I SHIPPED THIS MORNING DID NOT WORK
--------------------------------------------------------------------------------

At 08:23 I committed "Carry the RFQ id from the request page to the response
surface" (33ebc3b). It had 18 tests. 8 mutants applied and killed. The full
suite was green. CI was green.

It did not work.

    `/rfq/:id` sent a provider to `/provider?rfq=<id>`.
    `/provider` is a legacy compatibility shim (ProviderDashboard.tsx) that
    forwards to `/platform/:role`.
    The forward was written as:
        navigate(getRolePlatformPath(userRole))
    which DISCARDS THE QUERY STRING.

So the id was gone before anything could read it. And every one of these was
individually correct:

    the link                 correct — it resolved to a registered route
    the parser               correct — parseLinkedRfqId is exhaustively tested
    the destination          correct — RolePlatform reads ?rfq= properly
    the highlight            correct — QualifiedEnquiries marks the row
    the not-eligible notice  correct — renders when the row is absent

The defect lived in the gap BETWEEN two correct things. No source-reading test
can see a gap like that, because there is no source to read — the fault is that
one component's output stops being another component's input, silently, in a
third component nobody was looking at.

Found by: signing in as a supplier in Chromium, clicking "Continue to respond",
and reading the address bar. It said `/platform/supplier` — no `?rfq=1`.

--------------------------------------------------------------------------------
DEFECT 2 — A DIALOG THAT BLAMED THE USER FOR THE SERVER'S REFUSAL
--------------------------------------------------------------------------------

In the Documents tab I wrote (fd8ceae, 08:31), the upload handler was:

    try {
      const base64 = await readAsBase64(file);
      await upload.mutateAsync({ ... });
    } catch {
      if (!upload.isError) toast.error('That file could not be read.');
    }

`upload.isError` is React state captured at render time. Inside the catch it is
still `false`, because the mutation's error has not been committed to state
yet. So a SERVER refusal produced the message "That file could not be read" —
about a file that had been read perfectly well.

The screenshot from the live run showed it plainly. No unit test would have
found it: the lie is in WHICH of two messages appears, and both messages exist,
and both are correctly worded in isolation.

Fixed by separating the two steps so there is nothing to distinguish: the read
has its own catch that returns; the mutation's catch is deliberately silent
because onError has already shown the server's own message.

--------------------------------------------------------------------------------
WHAT I TAKE FROM THIS
--------------------------------------------------------------------------------

The unit tests were not weak. They were checking the right things, carefully,
on both sides of a gap that existed between them. Mutation testing did not help
either — you cannot mutate code into revealing a defect that lives in the
absence of code.

That is the entire argument for live verification, and it is why every claim in
this document carries a label saying how it was established, and why those
labels are never blurred into the word "passing".

3.1  COMMERCIAL AUDIT TRAIL                                          [166f082]
--------------------------------------------------------------------------------

THE GAP

BuildHub audited ACCOUNTS thoroughly. `userAccountAuditEvents` carries 22
distinct actions written from 29 call sites — creation, role changes, the whole
password-reset lifecycle, every administrative action.

It audited COMMERCE not at all. An RFQ could be created, quoted, awarded and
closed leaving no record of who did what or when.

For a marketplace that intends to carry real money that is the gap that
matters. Account history answers "who is this person". Commercial history
answers "what did they agree to" — and only the second one settles a dispute.

(Note: an earlier handoff of mine claimed no audit trail existed at all. That
was WRONG — `userAccountAuditEvents` was already there and thorough. Corrected
in this session's work and recorded here.)

WHAT WAS BUILT

New table `commercialAuditEvents` (drizzle/schema.ts, migration 0023):

    id           int autoincrement primary key
    actorId      int → users.id  ON DELETE SET NULL, ON UPDATE RESTRICT
    ownerId      int → users.id  ON DELETE SET NULL, ON UPDATE RESTRICT
    subjectType  enum('rfq','quotation','product','document','enquiry','message')
    subjectId    int NOT NULL         — deliberately NOT a foreign key
    action       varchar(64) NOT NULL
    detail       text                 — truncated at 500 chars
    createdAt    timestamp DEFAULT NOW() NOT NULL

    indexes: (subjectType, subjectId), actorId, ownerId, createdAt

`server/_core/commercialAudit.ts` exposes `recordCommercialEvent(db, event)`
with a closed `CommercialAction` union of 21 actions, of which 9 are currently
instrumented.

NINE INSTRUMENTED EVENTS

    rfq_created                 rfqRouter.create
    quotation_submitted         rfqRouter.submitQuotation
    quotation_accepted          rfqRouter.acceptQuotation
    quotation_rejected          rfqRouter.rejectQuotation
    enquiry_opened              rfqRouter.openEnquiry
    product_updated             marketplaceRouter.updateProduct
    product_published           marketplaceRouter.setProductActive (true)
    product_delisted            marketplaceRouter.setProductActive (false)
    product_images_changed      marketplaceRouter.setProductImages
    product_question_answered   marketplaceRouter.answerQuestion

READING THE TRAIL IS ITSELF SCOPED

    audit.mine   protectedProcedure. WHERE actorId = ctx.user.id
                 OR ownerId = ctx.user.id. The projection OMITS actorId —
                 whose account touched somebody else's record is not the
                 caller's business, and returning it would make this a way to
                 learn which accounts touched which records. Bounded by
                 .limit(input?.limit ?? 50), max 100.
    audit.all    adminWith('audit.read'). Bounded, max 200.

Exactly two reads. A third would need its own authorization rule, which is the
thing most likely to be got wrong later, so a test asserts there are two.

FOUR DECISIONS, EACH ONE A TRADE, STATED RATHER THAN ASSUMED

  (1) A FAILED AUDIT WRITE MUST NEVER FAIL THE BUSINESS ACTION.

      If the audit insert throws — a full disk, a lock timeout — the supplier's
      quotation has ALREADY been submitted and the customer is waiting on it.
      Rolling that back to protect the log would be losing the thing in order
      to protect the record of the thing.

      THE HONEST COST: a missing audit row is possible and is silent to the
      user. That is the right trade for THIS product, where the alternative is
      refusing commerce when logging hiccups — but it is a trade, not a free
      win. Which is why the failure is logged loudly for an operator as
      structured JSON with event `commercial_audit_write_failed`, even though
      it is invisible to the customer.

  (2) IT IS CALLED AFTER THE WRITE SUCCEEDS, NEVER BEFORE.

      An audit trail that records intentions rather than outcomes is worse than
      none: it would show quotations that were never submitted and awards that
      never happened, and nobody reading it later could tell which.

  (3) BOTH USER REFERENCES ARE SET NULL.

      RESTRICT would make a user undeletable by virtue of having done work.
      CASCADE would delete the evidence along with the person. SET NULL keeps
      the record and loses only the pointer.

      `subjectId` is deliberately NOT a foreign key at all. An audit row must
      survive its subject being deleted — and that deletion is often the very
      thing worth auditing. A FK would either block it or cascade the evidence
      away.

  (4) DETAIL IS CONTEXT, NOT A PAYLOAD.

      Truncated at 500 characters. The product-patch event records WHICH fields
      changed (`Object.keys(patch)`) and never their values. An audit trail is
      read by more people than the record it describes, so it must not become
      the widest copy of the narrowest data.

EVIDENCE

  LIVE VERIFIED

      nulls `actorId` and the audit row survives — confirmed by SQL, rows

3.2  MAKING subjectId AGREE WITH subjectType                        [3baa3b4]
--------------------------------------------------------------------------------

A DEFECT IN MY OWN FIRST PASS, and the most instructive one in the session
because of HOW it fails.

Three of the nine call sites recorded an id from the wrong table:

    quotation_submitted        recorded the RFQ id under subjectType 'quotation'
    enquiry_opened             recorded the RFQ id under subjectType 'enquiry'
    product_question_answered  recorded the QUESTION id under subjectType 'product'

None of them errored. Nothing looked wrong. The failure mode is worse than a
crash:

    SELECT * FROM commercialAuditEvents
    WHERE subjectType = 'quotation' AND subjectId = 5

returns rows confidently, silently mixing quotation 5 with whatever happened on
RFQ 5. AN AUDIT TRAIL THAT IS PLAUSIBLY WRONG IS MORE DANGEROUS THAN ONE THAT
IS OBVIOUSLY MISSING, because somebody will eventually settle a billing dispute
with the result.

THE RULE NOW HELD EVERYWHERE

    subjectId names a row in the table subjectType names.
    Everything else is `detail`.

Each of the three keeps its context rather than losing it — a quotation audit
row that could not be traced back to what was quoted on would be the opposite
mistake:

    quotation_submitted   detail: `rfq 5, price 400000, 30 days`
    enquiry_opened        detail: `rfq 5, credit charged`
    product_question_...  detail: `question 12`

`openQualifiedEnquiry` now returns the `qualifiedEnquiries` row it granted, so
the enquiry event points at the BILLABLE RECORD ITSELF — which is what a
billing dispute is actually about. In the duplicate-key race path there is no
insertId to capture, so the row is read back rather than reporting null for a
record that plainly exists.

A SECOND DEFECT FOUND WHILE FIXING THE FIRST

Capturing an insertId runs INSIDE the transaction that spends a lead credit. A
driver returning a shape without one would have thrown there and aborted the
grant — the vendor losing a paid lead because an audit id could not be read.
That is the exact inversion this whole trail is designed to avoid.

Both captures are now fully optional-chained:

    enquiryId  = Number(written?.[0]?.insertId) || null
    quotationId = Number(inserted?.[0]?.insertId ?? 0)

and a null id still records the charge. A row saying money changed hands with
the id missing beats no record that it did.

HOW IT WAS CAUGHT: the existing enquiry suite failed 13 tests immediately,
because its insert stub resolves with nothing — the harshest form of the case.
That coverage was ACCIDENTAL, so both paths now assert it deliberately: one
test that a grant survives an insert yielding no id, one that a quotation does.

THE GUARDIAN

A new test enumerates all nine call sites and the id expression each
subjectType may carry:

    product    ['id', 'input.id', 'row.productId']
    rfq        ['rfqId']
    quotation  ['quotationId', 'input.quotationId']
    enquiry    ['result.enquiryId ?? 0']

`input.rfqId` is absent from 'quotation' and 'enquiry' deliberately — that was
the defect. Adding a tenth site means adding a line, which is the point: it
forces the question "is that id really from that table?" at the moment somebody
would otherwise not ask it.

  MUTATIONS  M13–M18 — all killed after M18 exposed a genuinely missing test.

3.3  THE RFQ-TO-RESPONSE HANDOFF                                     [33ebc3b]
--------------------------------------------------------------------------------

THE GAP

Every piece of this journey existed, and the journey did not work.

    `/rfq/:id`    rendered a request (built earlier, commit 4784e8c)
    `/provider`   had a qualified-enquiry inbox and a working quotation form
    the link      threw the id away

"Continue to respond" went to a bare `/provider`, so a provider landed on a
dashboard and had to find, in a list, the request they had been reading a
second earlier. That is the gap between "every screen exists" and "the workflow
works", and no test that checks screens can see it.

WHAT THE ID IS USED FOR — AND ONLY THIS

    1. scroll the matching row in the enquiry inbox into view
    2. mark that row visually
    3. preselect the quotation form's rfqId

WHAT IT DELIBERATELY DOES NOT DO

    FOLLOWING A LINK NEVER OPENS AN ENQUIRY. Auto-opening would read as helpful
    right up to the point where a vendor's monthly allowance drained from
    browsing. The highlight only scrolls and marks; the vendor still presses
    the button that spends the credit. A test asserts the effect body contains
    `scrollIntoView` and does NOT contain `open.mutate`.

    IT NEVER RENDERS A ROW THE SERVER DID NOT RETURN. Inventing eligibility
    client-side would contradict the one authority on it.

THE DEAD END IS NAMED

A provider whose linked request is absent from their eligible list previously
scanned an inbox for something that was never going to be in it, and concluded
the product was broken. They are now told, in both languages. The notice states
BOTH possible reasons — the request is closed, or it falls outside their
declared service categories — because only the server knows which applies and
it is not asked here. Naming one as fact would be inventing a reason.

    EN  'The request you came from is not in your qualified enquiries.
         Qualified enquiries cover open requests that fall inside your declared
         service categories, so it is either closed or outside them.'
    AR  'الطلب الذي أتيت منه غير موجود ضمن طلباتك المؤهلة. الطلبات المؤهلة تشمل
         الطلبات المفتوحة التي تقع ضمن فئات خدماتك المعلنة، لذا فهو إما مغلق أو
         خارج تلك الفئات.'

A test asserts the message never mentions a credit — it is a client-side
observation about a list, not a server verdict about money.

TWO SMALLER DEFECTS FOUND ON THE WAY

    The quotation dialog's only field was "Your price", with nothing saying
    which request the bid was against. A way to bid on the wrong thing with no
    way to notice. It now names the request and its number.

    The submit button was enabled with rfqId 0, which reached the server and
    came back as a BAD_REQUEST toast: safe, and useless.

THE PARSER

`shared/linkedRfq.ts` — `parseLinkedRfqId(search)` — is a real module rather
than an inline coercion, because this is the point where a URL-supplied string
becomes a mutation argument. It is NOT a security boundary; everything
downstream is authorized server-side. But one rule in one place beats coercing
at each use site.

It rejects, with reasons:

    non-digits          `Number()` accepts '1e3', ' 12 ', '0x10', '12.0'
    0 and '00'          0 is the form's "nothing selected" sentinel; accepting
                        it from a URL produces a form that LOOKS targeted and
                        is not — the worst available outcome
    > 2^53−1            Number('9007199254740993') silently becomes
                        ...992, which is a different record
    repeated params     takes the first, asserted rather than assumed

3.4  THE PROJECT DOCUMENTS TAB                                       [fd8ceae]
--------------------------------------------------------------------------------

THE GAP

The Documents tab was a hardcoded panel: an icon, the sentence "Upload
drawings, BOQs, contracts, and invoices", and an Upload Document button with no
handler at all.

Meanwhile `projects.documents` and `projects.uploadDocument` were both complete
on the server — owner-scoped (`WHERE ownerId = ctx.user.id`, FORBIDDEN
otherwise), rate-limited, size-capped at 8MB, and byte-sniffed against the
declared content type.

The capability existed. Only the way to reach it did not.

THIS IS THE HARDEST KIND OF GAP TO SEE. A screen that DESCRIBES a feature is
the most convincing possible evidence that the feature works. Nothing errors,
nothing is obviously missing, and the capability is simply unreachable. No new
server surface was needed for any of it.

TWO ALLOWLISTS THAT DISAGREED

    isAllowedProjectDocumentType    accepted any image/*, any text/*, and PDF
    DOCUMENT_TYPES (the sniffer)    accepts PNG, JPEG, GIF, WebP, PDF

The sniffer runs IMMEDIATELY AFTER the zod refine. So a .txt or an .svg passed
validation, reached the sniffer, and came back rejected. The product advertised
uploads it could never accept, and said so only after the user had chosen a
file.

Narrowed to exactly what is enforceable, which is the honest direction: a
declared type that nothing can verify is not a capability. The two lists are
now held against each other by a test that IMPORTS BOTH:

    expect([...PROJECT_DOCUMENT_CONTENT_TYPES].sort())
      .toEqual([...DOCUMENT_TYPES].sort());

and the file picker's `accept` attribute is generated from the same list, so it
cannot offer a type the upload will reject.

THE CLIENT IS NEVER THE CONTROL

    It does not decide who may upload. The server re-reads the project and
    refuses a non-owner. This component renders the same for anybody and every
    call fails — which is correct. Hiding the button instead would be frontend
    authorization, and a test asserts the component contains no `ownerId`,
    `isOwner` or `user.id ===` check.

    Every refusal message shown is the server's own.

    The size and type pre-checks exist so the answer arrives BEFORE a
    multi-megabyte upload. A test compares both caps by reading each out of its
    own source rather than asserting the number twice — writing `8` in the test
    would let the two drift while it passed.

SMALLER THINGS FIXED ALONGSIDE

    A FileReader failure had no path to the user, because `onError` only covers
    server refusals.

    Empty-with-a-filter and empty-outright now read differently. One empty
    state would make a filter look like data loss.

    `uploadDocument`'s insertId read is defensive: by that line the bytes are
    stored and the row is written, so throwing there would show a failure for
    an upload that succeeded, and the user would try again.

  LIVE VERIFIED     Tab renders; empty state distinguishes "No documents yet"
                    from "No documents of this type"; dialog opens; file
                    selects; name and type set. Screenshot captured.
  BLOCKED BY INFRA  The upload cannot COMPLETE here — no object storage backend
                    is configured and the code correctly refuses. Never claimed
                    as passing at any point.
  MUTATIONS         M27, M27a, M27b, M28–M36 — all killed.

3.6  WHOLE-CLIENT DEAD-LINK SWEEP                                    [bb644b7]
--------------------------------------------------------------------------------

`routeIntegrity.test.ts` exists because a dead link shipped past a test that
was supposed to prevent exactly that. It then checked ROUTES and the
opportunity engine — the two places already under suspicion.

That is the same mistake one level up. Narrowing a link check to where you
expect trouble is how the next dead link ships too.

It now scans every .tsx under client/src for three patterns:

    navigate('...')
    <Link href="..."
    href="/..."

and holds all of them against the route table parsed out of App.tsx, with
interpolated templates checked by SHAPE — `/rfq/${id}` passes, `/quotation/${id}`
would not.

    Result: 28 distinct internal destinations, 0 dead.

The value is not today's zero. It is that the sweep now covers pages nobody
thought to list, including ones that do not exist yet.

ComponentShowcase.tsx is excluded and the reason is recorded in the test: it is
neither routed in App.tsx nor imported anywhere, so it is dead code that never
enters a bundle, and its hundreds of demo links are not destinations the
product offers anybody.

The sweep asserts its own premise first. A regex that stopped matching would
otherwise make every check below it pass on an empty set — and a link test that
passes vacuously is worse than none, because it is why this file exists.

  MUTATIONS  M41–M43 — all killed, including breaking one of the three scan
             patterns.

3.7  UNCONFIGURED OBJECT STORAGE                                     [fdd7051]
--------------------------------------------------------------------------------

THE MOST LAUNCH-RELEVANT FINDING IN THE SESSION.

It only appeared because the product was RUN FOR REAL with a missing
environment variable — which is precisely the state a deployment is in on
launch day when an S3 variable is wrong or absent.

Every upload failed. Both audiences were told something useless:

    THE CUSTOMER   "Something went wrong. Please try again."
                   for a condition that retrying can never fix.

    THE OPERATOR   "[trpc] mutation projects.uploadDocument failed:
                    unclassified - no classification matched - inspect the
                    deployment logs around this line"
                   It WAS the deployment log.

THE FIX ALREADY EXISTED, IN 2 PLACES OUT OF 8

    ai.uploadAttachment    caught ObjectStorageNotConfiguredError → clear 503

This is the same lesson `assertUploadedFileMatches` recorded when it was

WHAT CHANGED

All seven upload sites now go through `storagePutOrUnavailable`, which answers:

    code:    SERVICE_UNAVAILABLE
    message: 'File uploads are not available on this deployment.'

SERVICE_UNAVAILABLE rather than INTERNAL_SERVER_ERROR because that is what it
is: the feature is off on this deployment, the request was fine, and saying so
stops a user retrying into the same wall.

Anything that is NOT a configuration problem still propagates untouched. A
wrapper that swallowed a broken bucket into "the feature is off" would hide a
real outage behind a reassuring message — and a test asserts the `throw error;`
re-raise is still there.

THE CLASSIFIER WAS MATCHING ON PROSE

One word apart. Every upload on an unconfigured deployment logged as
'unclassified'.

      return { category: 'config-missing' };

placed IN FRONT of the regex, not instead of it, so the string-matched cases it
always caught still work. A test proves the name match survives rewording the
message entirely.

Turning the 500 into a 503 fixed the customer's half and SILENTLY REMOVED THE
OPERATOR'S. The tRPC error classifier only reports INTERNAL_SERVER_ERROR — on

To the CALLER. The access log would have shown 503s on every upload and never
said why.
