9. DATABASE MIGRATION STRATEGY - THE EXPLICIT DECISION
================================================================================

You asked for an explicit recommendation rather than a reflex. Here it is.

DO NOT put db:migrate in the container start command. Concretely why:

  CONCURRENCY   Every instance runs the start command. Scale to 2 and two
                processes race the same migration. Drizzle records applied
                migrations in a journal table but does not take an advisory
                lock, so the race is real, not theoretical.
  RESTARTS      A crash-looping container re-runs migrations on every restart.
  FAILURE MODE  A failed migration inside the start command yields a container
                that will not start - so the deploy fails AND the old version
                is already gone.
  ROLLBACK      Nothing distinguishes "migrate then serve" from "serve"; you
                cannot deploy the image without also migrating.

RECOMMENDATION: Render preDeployCommand.

    services:
      - type: web
        name: buildhub-staging
        preDeployCommand: "./node_modules/.bin/drizzle-kit migrate"

Per Render's documentation it runs AFTER the build and BEFORE the start
command, ONCE PER DEPLOY rather than once per instance, and IF IT FAILS RENDER
HALTS THE DEPLOY AND KEEPS THE OLD VERSION SERVING. That single property is
what makes it correct: it converts a broken migration from an outage into a
refused deploy. Available on paid instance types; plan: starter qualifies.

It also matches exactly what was done by hand in the shell, so it formalises
the existing verified state rather than changing behaviour.

THREE THINGS IT DOES NOT SOLVE, which must be stated rather than assumed:

  a) EXPANSION/CONTRACTION DISCIPLINE. preDeployCommand runs before the new
     code is live, so during the deploy the OLD code runs against the NEW
     schema. Every migration must therefore be backward compatible with the
     previous release: add columns nullable, never drop or rename in the same
     release that stops using them. Drops belong in a LATER release. This is a
     review rule, not something a tool enforces.

  b) ROLLBACK. Once a migration is applied, rolling the image back does not
     roll the schema back. With (a) held, an image rollback stays safe because
     the old code still works against the newer schema. Without (a) it is not
     safe. The backup/restore drill already verified in deploy/ is the
     backstop.

  c) LONG MIGRATIONS. A migration that locks a large table blocks the deploy.
     At current data volumes this is theoretical; it stops being theoretical
     after launch.

REJECTED ALTERNATIVES, with reasons:
  Start-command migrate      concurrency + rollback failures above
  Separate one-off job       correct but manual; the ritual problem again
  Migrate in the Dockerfile  build-time DB access; wrong and non-reproducible
  Leave it manual            status quo; it is blocker B3

PRODUCTION NOTE: adopt preDeployCommand on STAGING FIRST and let it run several
deploys before it is anywhere near production. I am not proposing to change
production deploy behaviour in the same step.
