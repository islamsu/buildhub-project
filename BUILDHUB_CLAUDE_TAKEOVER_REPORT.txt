2. THE MOST SERIOUS FINDING — FOUR MIGRATIONS THAT HAD NEVER RUN ANYWHERE
================================================================================

SEVERITY: P0 (deployment-blocking). Discovered during live verification.
STATUS:   FIXED and guarded.

WHAT WAS WRONG
--------------
drizzle-kit hands each migration file to the database driver as ONE query unless
its statements are separated by the breakpoint marker used throughout the
drizzle/ directory. MySQL and MariaDB refuse a multi-statement query outright.

Migrations 0037, 0038 and 0039 contained ZERO breakpoint markers. So:

  0037_referrals.sql                    FAILED on its second statement
  0038_referral_campaigns_and_rewards   never reached (runner stops on failure)
  0039_commercial_placement_fields      never reached
  0040_product_placement                never reached

CONSEQUENCE
-----------
These objects existed in drizzle/schema.ts, in TypeScript, and IN NO DATABASE
ANYWHERE:

  tables   referrals, referralCampaigns, referralRewards
  columns  vendorSponsorships.source
           vendorSponsorships.package
           vendorSponsorships.surface
           vendorSponsorships.entityType
           vendorSponsorships.productId

Every feature built on top of them — the referral engine, the commercial
placement booking engine, product placement — typechecked cleanly and passed its
unit tests, because those tests mock the database driver. None of it could have
worked against a real server.

THIS IS WHY STAGING IS BEHIND. It is not a deploy that was never triggered; the
application cannot migrate.

HOW IT WAS FOUND
----------------
Not by a test. The unit suite was green on this code. It surfaced when the new
Master Discovery endpoint was called against a real local MariaDB and returned
HTTP 500. The server log said "the database rejected or dropped the query"; a
direct driver probe showed the real cause, and `describe vendorSponsorships`
showed the columns simply were not there.

THE FIX
-------
Breakpoint markers added between statements in 0037, 0038 and 0039. 0040 is a
single statement and correctly needed none.

This is NOT rewriting applied migration history. These files had never
successfully executed against any database, so there was no applied state to
rewrite. Confirmed empirically: __drizzle_migrations held 37 rows (0000–0036)
before the fix and 41 after.

VERIFIED
--------
  - All 41 migrations now apply cleanly to a fresh MariaDB 10.11 database.
  - The five placement columns and three referral tables exist and are queryable.
  - The Master Discovery endpoints returned real data end to end afterwards.

PERMANENT GUARD
---------------
server/migrationSyntax.test.ts (3 tests) now fails on:
  - any multi-statement migration missing its delimiters;
  - any drift between drizzle/meta/_journal.json and the .sql files on disk;
  - a vacuous run (it asserts it found migration files at all).

Mutation-tested: stripping the markers back out of 0039 makes it fail, naming
the offending file.

A NOTE ON A MISTAKE MADE AND CORRECTED HERE
-------------------------------------------
The first version of the explanatory comment quoted the breakpoint marker
literally. drizzle's splitter matches that text ANYWHERE in a file, comments
included, so the comment cut itself in half and the migration still failed. The
comment was reworded to describe the marker without naming it, and the note
records why.

4.2 THE THREE RULES, EACH ENFORCED IN THE QUERY
-----------------------------------------------

RULE 1 — TIME IS DERIVED, NEVER SWEPT.
  A row is live only if it is not revoked, has started, and has not ended,
  evaluated against `now` at read time. Scheduled placements are invisible
  early; expired ones vanish on their own. Nothing needs a cron job, so nothing
  breaks when one fails to run.

RULE 2 — A PLACEMENT BUYS A SLOT, NEVER AN EXEMPTION.
  Target eligibility is re-checked at RENDER time against the SAME filter the
  organic listings use. `directoryVisibilityFilter` and `enrichVendorRows` were
  exported and imported rather than restated — two copies of an eligibility rule
  is how one of them ends up laxer. Products carry TWO gates: the product must
  be active AND its supplier must still be an eligible provider, because a
  suspended seller keeps rows with active = 1 and would otherwise go on
  advertising.

RULE 3 — SCOPE IS MATCHED EXACTLY.
  A placement bought for Lighting does not appear under Tiles. A platform-wide
  GLOBAL placement does not leak into a category view, and a category placement
  does not fill the global slot. No wildcard, no fallback.

4.3 THE PUBLIC PAYLOAD
----------------------
Both endpoints return the same card shape the organic listing beside them
already returns, plus a label. They carry NO commercial record: no grantedBy, no
grantedReason, no revokedBy, no startsAt, no endsAt, no priority, no package, no
price paid. That data stays behind marketplace.manage. Product columns are an
explicit allowlist rather than select(), so a future column is not handed to
anonymous readers the day somebody adds one.

4.4 HONESTY PROPERTIES HELD
---------------------------
  - Nothing booked renders NOTHING. No placeholder advertiser is invented for
    the most visible surface in the marketplace.
  - No fabricated ratings, review counts, years in business, project counts,
    certifications or discounts — a placement carries none of those.
  - A provider with no verified reviews shows a NULL rating, not 0 and not a
    plausible 4.8.
  - A product without a price says "Price on request" rather than 0 EGP.
  - `verified` remains compliance review, entirely separate from having bought a
    placement.
  - The label is TEXT plus a distinct icon, in English and Arabic — never colour
    alone, which a colour-blind reader or greyscale print would lose.

5. AN OWNER DECISION EMBEDDED — PLEASE REVIEW
================================================================================

GLOBAL AS A RESERVED SCOPE TOKEN.

Master Discovery is shown BEFORE a visitor chooses a provider type or product
category, so the placement filling it cannot be scoped to one of them. The
`category` column on a placement row is the scope, and GLOBAL is now the
reserved value meaning "the whole marketplace".

The alternative — "no category selected means any Master will do" — was
rejected. Master capacity is one per scope; five category Masters would then be
five candidates for one exclusive slot, and something would have to choose
between them arbitrarily. That is not exclusivity, it is a lottery an advertiser
paid for.

It is NOT a wildcard in either direction, by design.

This is documented in shared/placement.ts and is reversible. If a different
shape is wanted, say so and it changes.
