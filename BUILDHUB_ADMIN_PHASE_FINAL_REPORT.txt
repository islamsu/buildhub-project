1. EXISTING ARCHITECTURE DISCOVERED
================================================================================

Reported before any code was modified, as instructed.

Authentication
  First-party email+password, added in Slice 3. `server/routers.ts` held
  `hashPassword`/`verifyPassword` (scrypt, format `scrypt$<salt>$<key>`,
  compared with `timingSafeEqual`) and a constant `NO_SUCH_ACCOUNT_HASH` used
  to keep the unknown-account path the same cost as the wrong-password path.
  Sessions are JWT (jose, HS256) carrying a `jti`, set as an httpOnly cookie
  by `server/_core/cookies.ts`, verified by `server/_core/sdk.ts`.

Authorization
  tRPC procedure tiers in `server/routers.ts`: `publicProcedure`,
  `protectedProcedure`, `adminProcedure`, `approvedProviderProcedure`,
  `complianceProcedure`. `adminProcedure` was a single boolean gate —
  `ctx.user.role !== 'admin'` → FORBIDDEN. **There was exactly one level of
  administrator.** 37 endpoints sat behind that one gate. Nothing distinguished
  a billing clerk from someone who could delete accounts.

Admin surface
  `client/src/pages/AdminDashboard.tsx`, routed at `/admin` and
  `/admin/:section`. It had no login page of its own: an administrator signed
  in through the ordinary `/auth` customer form and was then recognised by
  role. There was no separate administrator door.

Session revocation
  Already present and reusable: a `revokedSessions` table keyed by `jti`, and
  `users.sessionsInvalidBefore` for bulk invalidation, compared at
  whole-second granularity.

Audit
  A `userAccountAuditEvents` table already existed with (userId, actorId,
  action, source, note, createdAt), written from ~20 sites. No admin-specific
  actions were recorded because there were no admin-specific operations.

What did NOT exist, and therefore had to be built
  - a separate administrator sign-in door
  - any notion of an administrator *role* (all admins were equal)
  - any permission model
  - any way to create a second administrator
  - any way to bootstrap the first one without hand-editing the database
  - any invitation mechanism for administrators
  - any staging QA coverage of the administrator surface

3. DATABASE MIGRATIONS CREATED
================================================================================

`drizzle/0020_tense_triathlon.sql` — additive only. Nothing dropped, nothing
narrowed, no data deleted.

  1. CREATE TABLE `adminInvitations`
       id, tokenHash (varchar(64), UNIQUE), userId, adminRole, invitedBy,
       createdAt, expiresAt, usedAt, revokedAt, revokedBy
       FKs: userId → users ON DELETE CASCADE
            invitedBy → users ON DELETE RESTRICT
            revokedBy → users ON DELETE SET NULL
       Indexes on userId, invitedBy, expiresAt.

  2. ALTER TABLE `users` ADD `adminRole` enum(...) — nullable, no default.

  3. Backfill:
       UPDATE `users` SET `adminRole` = 'SUPER_ADMIN'
        WHERE `role` = 'admin' AND `adminRole` IS NULL;

The backfill is not cosmetic and the reason is worth stating. Every permission
check fails closed on a null adminRole. Without line 3, an administrator who
existed before this migration would authenticate perfectly and then be refused
by every admin endpoint — a self-inflicted lockout with no route back in
through the application. SUPER_ADMIN is the honest value: `role='admin'` has
been all-or-nothing until now, so it names authority they already held. It
widens nobody's access. The `adminRole IS NULL` guard makes it idempotent, so
re-running can never overwrite a role since assigned deliberately.

================================================================================
4. SUPER ADMIN BOOTSTRAP METHOD
================================================================================

`server/adminBootstrap.ts`, invoked once from `server/_core/index.ts` at boot.

Inputs, read from the server process environment only:
    ADMIN_BOOTSTRAP_EMAIL
    ADMIN_BOOTSTRAP_USERNAME
    ADMIN_BOOTSTRAP_PASSWORD

Declared in `render.yaml` with `sync: false` and in `.env.example` with no
value, so the Blueprint documents that they are required without carrying
them. They are never prefixed VITE_, never reach the client bundle, and are
never returned by any API.

Behaviour:
  - Idempotence gate first: `SELECT count(*) FROM users WHERE role='admin'`.
    If > 0, it returns `already-exists` and does nothing at all. It cannot
    recreate, cannot overwrite a password, cannot reset on redeploy, cannot
    create a duplicate.
  - If no admin exists and all three variables are set, it creates one user
    with role='admin', adminRole='SUPER_ADMIN', and the password scrypt-hashed.
  - Minimum password length 12, enforced before anything is written.
  - It never throws. A misconfigured bootstrap must not take the whole service
    down; it logs a reason and the service boots without an admin.
  - It never logs the password, and never logs the hash. Verified by a test
    that captures every console call during a successful bootstrap and asserts
    the password string appears in none of them.

Verified: 15 tests in `server/adminBootstrapEnv.test.ts` plus a live run
against real MariaDB — first boot created the Super Admin, second boot with a
*different* ADMIN_BOOTSTRAP_PASSWORD left the original password working and the
new one refused, which is the property that matters.

7. PERMISSIONS
================================================================================

Ten permissions, mapped per role by `ADMIN_ROLE_PERMISSIONS`:

    admins.manage        users.read          users.manage
    marketplace.manage   support.manage      billing.read
    billing.manage       audit.read          qa.manage
    settings.manage

`hasAdminPermission(role, permission)` **fails closed**: null, undefined, an
unknown string, or a role missing from the map all return false. This is the
property the whole model rests on, so it is asserted directly and was
mutation-tested.

Enforcement is server-side, in `server/routers.ts`:

    const adminProcedure = protectedProcedure.use(({ ctx, next }) => {
      if (ctx.user.role !== 'admin') throw FORBIDDEN;
      if (!isAdminRole(ctx.user.adminRole)) throw FORBIDDEN;   // no role → no entry
      return next({ ctx });
    });

    const adminWith = (permission) => adminProcedure.use(({ ctx, next }) => {
      if (!hasAdminPermission(ctx.user.adminRole, permission)) throw FORBIDDEN;
      return next({ ctx });
    });

    const superAdminProcedure = adminWith('admins.manage');

All 37 pre-existing admin endpoints were rewired from bare `adminProcedure` to
`adminWith('<permission>')`. `admin.me` is the single deliberate exception: it
stays on bare `adminProcedure`, because it is how the UI asks "what am I
allowed to do", and it must answer for every administrator.

The frontend gate in `AdminDashboard.tsx` (`can(permission)`, driven by
`trpc.admin.me`) exists so the UI does not render doors that will slam. It is
cosmetic. Removing it changes what is drawn and changes nothing about what is
permitted.

================================================================================
8. SUB-ADMIN CREATION FLOW
================================================================================

Only a Super Admin can reach any of this — every endpoint below is
`superAdminProcedure`, i.e. `adminWith('admins.manage')`, a permission held by
SUPER_ADMIN alone.

  1. Super Admin opens `/admin/admins` and submits email, username, role.
  2. `admin.createAdmin` creates the account with role='admin' and the chosen
     adminRole, with **no usable password**, and mints an invitation:
     32 bytes from `crypto.randomBytes`, hex-encoded; only its SHA-256 is
     stored in `adminInvitations.tokenHash`. The raw token is returned exactly
     once, in that mutation's response, to the Super Admin's browser.
  3. The Super Admin passes the invitation link to the new administrator
     through whatever channel they consider appropriate. The system does not
     email it (SMTP is not configured, and §13 forbids sending passwords by
     email regardless).
  4. New administrator opens `/admin/accept-invitation?token=…`, sets their own
     password, and the token is burned (`usedAt` stamped).
  5. They sign in at `/admin/login`.

The Super Admin never sees the new administrator's password, because the
password does not exist until step 4 and is chosen by its owner.

Sub-admin containment, as required by §11 — each of these is a server-side
refusal with a test behind it:
  - cannot create administrators at all (no `admins.manage`)
  - therefore cannot create a Super Admin
  - cannot change any role, including their own
  - cannot change permissions (permissions are derived from role, not stored
    per-user, so there is no per-user permission record to edit)
  - cannot read secrets, passwords, or password hashes through any endpoint
  - cannot reach infrastructure or production credentials
  - cannot bypass audit logging: the writes are inside the mutations, not in a
    caller-supplied wrapper

Management endpoints, all Super-Admin-only: `admin.admins`,
`admin.createAdmin`, `admin.setAdminRole`, `admin.setAdminActive`,
`admin.revokeAdminSessions`, `admin.resetAdminPassword`,
`admin.adminInvitations`, `admin.revokeAdminInvitation`.

================================================================================
9. PASSWORD / RESET FLOW
================================================================================

Storage
  scrypt, `scrypt$<salt>$<key>`, per-password random salt, verified with
  `timingSafeEqual`. No custom cryptography was invented (§16); this is the
  same primitive the customer path has used since Slice 3, now shared through
  `server/passwords.ts`.

Reset
  `admin.resetAdminPassword` (Super Admin only) does **not** set a password and
  does not display one. It invalidates the target's current credential and
  issues a fresh single-use invitation token, so the administrator chooses
  their own new password through the same accept-invitation screen. This is
  what satisfies §13: there is no code path in which a permanent password is
  shown to the Super Admin, and none in which a password is emailed.

Self-service
  `admin.changeOwnPassword` requires the current password, and re-issues the
  session cookie so the caller is not logged out by their own change.

Never displayed, never returned, never logged (§12, §17): password, password
hash, session token, raw invitation token, raw reset token, API key, database
password. `admin.admins` returns an explicit column allowlist — id, email,
username, adminRole, active, createdAt — never `passwordHash`. This is asserted
by a test that would fail if the allowlist were replaced with `select()`.

Tokens (§14)
  32 random bytes from a CSPRNG. Never a user id, never an email, never a
  sequential number, never a password in a URL. Stored only as SHA-256 —
  unsalted sha256 is correct here precisely because the input is already 256
  bits of entropy; salting would buy nothing and would break the unique-index
  lookup.

10. SESSION SECURITY
================================================================================

  - JWT (jose, HS256), httpOnly cookie, `path=/`, `secure` in production, and
    `sameSite` chosen to match: `none` only when the request is genuinely
    secure, `lax` otherwise. (A `SameSite=None` cookie without `Secure` is
    dropped by every modern browser — that combination was a live defect found
    and fixed earlier in this engagement.)
  - Each session carries a `jti`. Individual revocation via `revokedSessions`;
    bulk revocation via `users.sessionsInvalidBefore`.
  - `verifySession` rejects a token with no `openId`, and rejects a token
    issued for a different `appId` when an appId is configured.
  - Deactivating an administrator, changing their role, or revoking their
    sessions all invalidate every session they hold, immediately.

One defect found here by live probing, and fixed. `sessionsInvalidBefore` is
compared at whole-second granularity with a strict `<`. A session issued in the
*same second* as the revocation therefore survived it — a real one-second
window in which a just-deactivated administrator kept working. Fixed with

    const revocationCutoff = () => new Date(Date.now() + 1000);

applied at all three revocation sites. `changeOwnPassword` deliberately keeps
`new Date()`, because it re-issues the caller's cookie immediately afterwards
and a forward-dated cutoff would log the caller out of their own password
change.

11. AUDIT LOGGING
================================================================================

Written into the existing `userAccountAuditEvents` table, so administrator
activity lands in the same timeline as everything else and
`admin.fullAuditReport` / `admin.accountAudit` already read it.

Admin actions added this phase:

    admin_signed_in                  admin_created
    admin_role_changed               admin_sessions_revoked
    admin_password_changed           admin_password_reset_requested
    admin_invitation_redeemed        admin_invitation_revoked

Every entry records who acted (`actorId`) and who was acted upon (`userId`).
The note field carries a human-readable description and is asserted never to
carry a token or a password.

Administrator sign-in gets its own action rather than reusing the customer one,
so "who logged into the admin console, and when" is a single query rather than
an inference.

Reading the audit log is itself gated: `audit.read`, held by SUPER_ADMIN only.
