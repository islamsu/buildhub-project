2. ARCHITECTURE
--------------------------------------------------------------------------------
One request path, composed in code rather than in a prompt:

  browser
    └── tRPC ai.chat  (protectedProcedure + 4 rate limiters)
          ├── detectIntent(question)          server/_core/aiIntent.ts
          │     decides, IN CODE: does this need the vendor directory?
          │     does it need live web data?
          ├── buildSystemPrompt(lang, viewer) server/_core/buildhubKnowledge.ts
          │     authoritative BuildHub briefing, derived at request time
          ├── retrieve(question)              server/_core/knowledgeRetrieval.ts
          │     construction corpus, authority-ranked
          ├── recommendProviders(criteria)    server/recommendation.ts
          │     ONLY when the intent router asked for it
          └── generateAIResponse()            server/_core/ai.ts
                OpenAI Responses API, model gpt-5.6-luna

WHY ROUTING IS IN CODE, NOT IN THE PROMPT. Routing decides whether the database
is queried and whether a paid web search runs. A model deciding that is a model
deciding when to spend money and reach for live data, non-deterministically, on
every request. The classifier is small, boring and unit-testable, and when
unsure it prefers the cheap, safe branch.

Provider boundary (server/_core/ai.ts): MAX_RETRIES 2, timeout 60s, reasoning
effort low, max_output_tokens 4096 (8192 with web search), no `temperature`
(GPT-5 family rejects it). Empty model output is a typed `response-empty`
failure, never an empty success.

4. KNOWLEDGE SOURCES AND THE AUTHORITY HIERARCHY
--------------------------------------------------------------------------------
Seven tiers, lower number wins:

  1  BuildHub official product and business rules
  2  Government and regulatory authorities
  3  Building codes and standards organisations
  4  Recognised professional institutions
  5  Manufacturer and technical documentation
  6  Reputable industry sources
  7  General model knowledge

WHAT IS ACTUALLY POPULATED TODAY:

  Tier 1  Derived at request time from BuildHub's own source of truth —
          @shared/billing (plans, prices, trial and grace periods),
          @shared/compliance (documents required for vendor approval),
          @shared/platformRules (7 rules). NOTHING HERE IS HAND-COPIED: the
          briefing reads the same constants the product enforces, so the
          assistant cannot drift from the deployment.
  Tier 6  4 synthesised construction documents (section 5).
  Tiers 2-5  EMPTY. No regulator, code body, institution or manufacturer
          content has been ingested.

Each of the 7 platform rules carries an `enforcementAnchor` naming the code
that enforces it (e.g. `rfq.post.free` → `create: protectedProcedure`;
quotations → `approvedProviderProcedure`), and a test asserts the anchor still
exists. A rule that stops being enforced fails the build rather than becoming a
claim the assistant repeats.

NO BUSINESS RULE WAS INVENTED. Every tier-1 statement traces to a constant the
product already uses.

COPYRIGHT: no standard or code has been reproduced. Tier-3 content, when added,
must be cited and summarised, not copied.

dates make that visible rather than assumed.


--------------------------------------------------------------------------------
6. VECTOR STORE
--------------------------------------------------------------------------------
NONE. Deliberately.

At this corpus size a hosted vector store would add an external dependency, an
ingestion job that can silently fall out of sync with the repository, a second
place for content to live, and a per-request network call — to rank a few dozen
documents that carry hand-written keyword lists. The corpus lives in the
repository, so it is versioned, reviewable in a pull request, and deployed
atomically with the code that reads it. There is no state to re-sync.

The threshold for revisiting is concrete rather than aesthetic: when the corpus
outgrows what keywords can discriminate — roughly a few hundred documents, or
when authors start guessing which keywords to add — move the bodies into a
vector store and keep `knowledgeRetrieval.ts`'s interface. Nothing above that
layer would change.


--------------------------------------------------------------------------------
7. RETRIEVAL
--------------------------------------------------------------------------------
Deterministic keyword scoring. Topic-line hits outweigh incidental body hits.
Zero-score documents are dropped; top 3 are passed.

  - AUTHORITY BREAKS TIES: at equal relevance, tier 1 outranks tier 6.
  - STALENESS is surfaced to the model, not silently ignored.
  - CONFLICTS ARE NAMED, NOT RESOLVED SILENTLY: when retrieved documents sit at
    different authority levels, the block says so and states that the lower
    tier number wins — because a regulator disagreeing with an industry source
    is information the reader wants, not noise to hide.

Every retrieved block states its tier and its source, so the model follows the
hierarchy rather than treating all context as equally true.

8. BUILDHUB LIVE DATA
--------------------------------------------------------------------------------
Two live reads, both narrow and both server-side:

  1. The tier-1 briefing, computed per request from billing/compliance/rules
     constants, plus the caller's OWN role and plan.
  2. The approved-provider directory, via the existing `listDirectoryVendors`,
     and ONLY when the intent router asks for it.

THE MODEL HAS NO DATABASE ACCESS. It never receives a query, a connection, a
schema or a raw row. It receives a formatted block of already-authorized,
already-filtered facts. This was an explicit instruction and it is
architecturally enforced, not merely instructed.

Proof it is live rather than recalled: scenario 5/6 below checks the assistant's
price against the price THE DEPLOYMENT ITSELF serves from `billing.plans`
(499 EGP). A model answering from general knowledge has no way to produce that
number, in either language.


--------------------------------------------------------------------------------
9. RECOMMENDATION ENGINE
--------------------------------------------------------------------------------
Deterministic scoring in code; the model presents, it does not rank.

  categoryMatch    50
  roleMatch        25
  locationMatch    20
  verified         15
  ratingMax        20   (scores ONLY when reviewCount > 0)
  reviewVolumeMax  10   (a confidence signal, capped deliberately low)

Tiebreakers are stable and explainable: score, then review count, then account
age — never whatever order the database happened to return.

BROADENING LADDER, each step reported: exact → drop location → drop category →
`matchQuality: 'none'`.

The candidate block tells the model what BuildHub DOES NOT KNOW — availability,
response time, years of experience, portfolio relevance, current workload,
budget fit — and forbids stating, estimating or implying any of them. It
forbids re-ordering, and forbids "best in Cairo" style superlatives the data
cannot support. On no match it forbids naming any provider and directs the
assistant to the free RFQ route.

NO RATING, REVIEW, PRICE OR ATTRIBUTE IS FABRICATED. A vendor with no reviews
is presented as "no reviews yet" and earns zero rating points.

10. WEB SEARCH
--------------------------------------------------------------------------------
OpenAI's hosted `web_search` tool, enabled PER REQUEST and only when the intent
router sets `wantsCurrentInformation`.

Explicit temporal cues ("current price", "latest", "right now", "market price",
"السعر الحالي") fire regardless of the timeless guard. Weak cues ("price of",
"cost of", "سعر") defer to a guard that suppresses "what is a…", "how do I
calculate…", "ما هو…" — so "how is the price of concrete calculated" costs
nothing while "what is the current price of cement" reaches the web.

Verified live by latency: scenario 9 (web on) took 7,548 ms against 1.3–3.1 s
for the non-search scenarios in the same run.

12. AUTHORIZATION
--------------------------------------------------------------------------------
NO NEW AUTH SYSTEM, NO NEW AUTHZ SYSTEM, NO DUPLICATE MARKETPLACE MODELS. The
knowledge platform reuses what exists.

  - `ai.chat` is `protectedProcedure`: anonymous use is refused 401, and the
    refusal is an auth refusal, not a masked internal error (verified live).
  - Rate limits: user burst 5/10s, user sustained 20/5min, IP burst 10/10s,
    IP sustained 60/5min.
  - The briefing carries the caller's OWN role and plan and states explicitly:

    the same directory function the public marketplace uses.

The assistant cannot reach private user data, private vendor data, admin
information or internal commercial metrics, because those are never placed in
its context — not because it is asked nicely not to look.

18. WHAT CHANGED SINCE THE PREVIOUS RUN
--------------------------------------------------------------------------------
The first live run of the ten-scenario suite (run 32993286246, at 1703eaa)
returned 378/379 with one failure. Both problems it exposed are fixed in
527fade, and they were different in kind — which is the part worth reading.

DEFECT 1 — A REAL ROUTING GAP (product).
Scenario 8 asked "I need a swimming pool specialist contractor in Aswan. Who is
on BuildHub?" The intent router returned false — neither "I need a" nor "who is
on" was a cue — so the directory was never searched, and the assistant answered
"I can't access BuildHub's live vendor directory."

That answer is honest about the model and WRONG ABOUT BUILDHUB. The system
prompt correctly tells the model it cannot look up vendors; a candidate block
supersedes that when the router fires. The model behaved correctly given its
instructions. The router was the only thing at fault.

Fixed: stating a need now counts as asking, as does asking who is listed. The
need must sit within 45 characters of the role word, because "I need a rough
cost estimate for finishing a 120 m² apartment, and what does a contractor
typically charge?" states a need and names a role while being a PRICING
question — routing that to the directory would answer "BuildHub has no listed
contractor" to someone who asked about money. That case is a test, and
un-windowing the cue kills it.

DEFECT 2 — A FALSE FAILURE (harness, mine).
Scenario 10 was reported as a failure the product did not have. The refusal was
correct and complete; the apostrophe was U+2019 and my check spelled "can't"
with an ASCII one. Models write typographic punctuation. Matching now runs on a
folded copy while the printed evidence stays the raw answer. Verified against
the exact string staging returned, and confirmed to still refuse an answer that
really does leak an address.

I am flagging this one explicitly: it was my error, not the product's, and it
would have been easy to report it as an AI failure.

THE ASSERTION THAT WAS MISSING. Scenario 8 PASSED on the first run while giving
a bad answer, because no assertion checked where the answer came from. It now
asserts the no-match answer is BuildHub's own directory result rather than a
model disclaimer — the check that would have caught the routing gap without a
human reading the transcript.

19. KNOWN LIMITATIONS
--------------------------------------------------------------------------------
19.1  CORPUS DEPTH. 4 documents across 4 of 70 domains, all tier 6. Tiers 2-5
      are empty: no regulator, code, institution or manufacturer content has
      been ingested. The platform's SHAPE is complete; its CONTENT is a
      beginning. Do not read 70 domains as 70 domains of coverage.

19.2  UNRECOGNISED QUALIFIERS ARE DROPPED SILENTLY, AND THE RESULT IS LABELLED
      "EXACT". This is the most important limitation in this document and it
      was found by reading scenario 8's answer rather than its green tick.

      "Swimming pool specialist in Aswan" parses to role=contractor only:
      "swimming pool" is not in the category vocabulary and Aswan is not a
      served city, so both are dropped. The engine then searches on role alone,
      finds contractors, and returns matchQuality 'exact' — because from its
      point of view every criterion it knew about was satisfied. The broadening
      ladder never engages, so the answer is never labelled as broadened.

      The result: a generic contractor can be presented as a match for a highly
      specific request, with no signal that two qualifiers were discarded.
      Nothing is fabricated, and no ranking is wrong — but the framing
      overstates the match.

      REMEDY (not implemented; it changes recommendation semantics after the
      verified run, which I judged should be the owner's call rather than a
      last-minute change): have `detectIntent` return the qualifier terms it
      could NOT map, and have `formatCandidatesForModel` state them — "BuildHub
      has no category for 'swimming pool' and does not list Aswan; these
      providers match on role only." I recommend this as the next AI task.

19.3  STAGING'S DIRECTORY CONTAINS QA FIXTURES, NOT REAL VENDORS. Scenario 8's
      answer named "QA contractor" — a fixture the gate itself creates. So the
      POPULATED path of the recommendation engine has been exercised against
      synthetic data, and its EMPTY path against a genuinely empty filter
      (scenario 7). Neither has been exercised against a real approved vendor
      directory, because staging has none. Seeding business data was not
      authorised and was not done.

19.4  EVIDENCE TRUNCATION. The gate prints 120-140 characters of each answer.
      For scenario 8 that stopped at the first line, which is why 19.2 required
      reading the engine's code rather than the log. Widening the printed
      evidence would make future runs self-diagnosing.

19.5  NO AUTOMATED REFRESH. Review dates and staleness reporting exist;
      re-review is manual. Nothing tells an operator a document is due except
      running `staleDocuments()`.

19.6  RETRIEVAL IS KEYWORD-BASED. A question that shares no vocabulary with a
      document's keyword list will not retrieve it, however relevant. Section 6
      states the concrete threshold for revisiting this.

19.7  JURISDICTION IS METADATA, NOT LOGIC. Eight jurisdictions are defined and
      every document is tagged, but all 4 documents are GLOBAL, so
      jurisdiction-specific retrieval has never actually discriminated between
      two documents. It is untested in practice.

19.8  ONE PROVIDER, ONE MODEL. `gpt-5.6-luna` via the OpenAI Responses API. No
      fallback provider. If OpenAI is down, the assistant is down — it fails
      with a typed error and an honest message, but it fails.

20.1  Which domains matter commercially? 66 of 70 are empty and I should not

      20 requests / 5 min / user is a lot of paid tokens at scale.

20.6  Is the refund policy of section 15, scenario 4 a real gap? The assistant correctly
      says BuildHub has not published one. Whether BuildHub SHOULD publish one
      is a business question the assistant surfaced.

20.7  How should unrecognised cities be handled (19.2)? Adding Aswan is a
      one-line change; deciding which cities BuildHub serves is not.
