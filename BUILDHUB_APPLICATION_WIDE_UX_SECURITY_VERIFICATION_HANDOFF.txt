The mandate reads as one large request. Most of it was already built and
live-verified in earlier passes; the honest work of this pass was to find the
part that was NOT, and to prove which was which rather than assert it.

Eleven items were genuinely unmet. TEN were user-experience or workflow gaps.
ONE was a real authorization defect:

  §20  projects.create was `protectedProcedure` with no role check at all.
       Only the homeowner dashboard offered a "Create Project" button, so the
       restriction LOOKED real. It was not a restriction; it was a hidden
       button. Any authenticated account - a supplier, a contractor, anyone -
       could POST to the procedure directly and own a project, and every
       downstream rule (projects.list, projects.get, rfq.create's ownership
       check, the provider-facing directory) assumes a project belongs to the
       customer commissioning the work.

       This is the single finding of the pass that a reviewer reading the UI
       had no way to notice, and it is exactly the class of defect the mandate
       names: "Frontend hiding is never sufficient security."

       VERIFIED BEFORE RESTRICTING, not assumed. Every project in the database
       is owned by a homeowner:

           select u.userRole, count(*) from projects p
             join users u on u.id = p.ownerId group by u.userRole
           -> homeowner  32

       One row. Restricting creation to homeowners therefore removes no
       capability anyone had; it closes a door nobody had walked through.

  §12  RFQ details were already a page. Confirmed, not assumed.

  §21  Listing a product was an inline block inside the workspace. No address,

  CURRENT BEHAVIOUR   Any authenticated account could, via the API. The UI
                      offered the control to homeowners only.
  EVIDENCE            All 32 existing projects are owned by homeowners. No

                      sections inside each role's workspace.

                      (b) a real page hosting the existing components,
                      (c) reimplemented panels.
  RECOMMENDED         (b). (a) leaves the surfaces where they were and adds a
                      second way to reach them; (c) duplicates behaviour that

3. THE UNIT RULE, AND WHY IT IS NOT "REJECT ANYTHING UNKNOWN"
--------------------------------------------------------------------------------

  A NEW unit must come from the shared list.
  An EXISTING unit is preserved even if it is not in the list.

The second half is the part that matters. The column is varchar(50) and
already holds free text on real rows. A supplier who opens one of those sixteen
"tonne" products, changes the PRICE, and saves would - under a strict rule -
have their save refused because of a unit they did not touch and cannot fix
from that form. Tightening a rule must not lock people out of their own
records.

It is not a database enum for the same reason: migrating the column would have
to decide, for every existing product, what its author meant. That decision
belongs to the supplier who wrote it, not to a migration.

Both halves are tested, and both were mutation-tested: removing the legacy
escape hatch kills the suite, and so does accepting an unknown unit on a new
product.

9. INSTRUMENT DEFECTS FOUND AND FIXED (an instrument is not evidence until
   it has been checked itself)
--------------------------------------------------------------------------------

  THE HARNESS COULD ONLY RUN ONCE. zg/nav.mjs deleted `rfqs` in its setup and
  worked exactly once: the run opens a qualified enquiry, and on the second run
  that surviving `qualifiedEnquiries` row made the delete fail on its foreign
  key. A harness that cannot repeat cannot demonstrate repeatability. Teardown
  now clears every referencing table before its parent, and runs again at the
  END so the database is left as it was found. 79/79 twice, and the harness's
  own rows verified gone afterwards.

  A PIPE HID A CRASH. The first re-run was invoked as `node nav.mjs | tail -8`
  and reported exit code 0 - the exit status of `tail`. The run had actually
  died in setup. Nothing was reported from it; the pipe was removed and the
  full output captured to a file.

  A CHECK KEYED ON A VARIABLE NAME. A new staging-gate assertion required each
  browser context to parse a real session cookie, matched as `cookie.split`.
  It reported 5 of 6 - because the attachment composer holds its session in a
  variable named `ai`. The CHECK was wrong, not the code; it now matches the
  idiom rather than the variable, and a placeholder cookie still fails it.

  A SWEEP THAT SPANNED TWO CODE STATES. The sidebar fix landed while the live
  sweep was between roles, so the supplier's leg ran against a hot-reloaded
  client and reported one menu item present but textless and inert - the
  signature of a reload artifact rather than a defect. That reasoning was NOT
  accepted as the answer: a result measured across two versions of the code is
  not evidence either way, so roles.mjs was re-run alone at the committed code.

  MEASURED: the supplier's sidebar is 9/9 in the clean run, and the homeowner's
  is 8/8 where it had been 6/7. The artifact was an artifact and the defect was
  a defect - which is only knowable because the run was repeated rather than
  explained.

  TWO RUNS, ONE DATABASE. Killing that stuck wrapper left the roles.mjs it had
  eventually started still alive, so a second instance began while the first
  was mid-flight. The result was 116 passed / 12 FAILED - and the twelve were
  one triple repeated across four provider roles ("that request belongs to a
  customer this workspace may list", "the customer is notified of the new
  quotation", "the customer sees THAT price"), which is what interleaved RFQ
  and customer seeding looks like.

  Not asserted as contention - shown. Both output files were being written
  within seven seconds of each other, and the SAME code run alone gives
  128/128. Concurrency was the only variable that differed. The 116/12 file is
  discarded; it is recorded here because a discarded run that goes unmentioned
  is indistinguishable from one that was hidden.

  A WAIT-LOOP THAT WAITED ON ITSELF. The script queueing that clean re-run held
  `while pgrep -f "scratchpad/regsweep.sh"; do sleep 20; done`. Its own command
  line contained that string, so it matched itself and waited forever. This is
  the THIRD variant of one mistake in this engagement - the other two were
  `pkill -f` patterns that killed the shell issuing them. The rule that
  prevents all three: never match a pattern that appears in the argv of the
  process doing the matching.

10. A SECOND DEFECT, FOUND BY THE ACCEPTANCE RE-RUN - IN MY OWN WORK
--------------------------------------------------------------------------------

The acceptance suite seeded a product priced per "ton" and got http 400. That
was the new rule working exactly as designed. Following it up found something
that was NOT working as designed:

  `create` and `updateProduct` both sent `unit` through normaliseUnit.
  `importProducts` wrote `row.unit` straight from the CSV.

A supplier could not list ONE product per "ton" through the form, and could
list five hundred through a spreadsheet. The rule was real on the surfaces a
person uses and absent on the one that moves volume - which would have quietly
undone the entire point of having a list.

Fixed, with the refusal reported per line naming the acceptable values, the
same shape as every other import error, so the file can be corrected. Two
mutations confirm it, and the second is the interesting one: listing the unit
errors without COUNTING them still fails the suite, because an import that
reports zero errors and then refuses to run would be worse than either
outcome on its own.

This is the strongest argument in this report for re-running the whole live
suite rather than only testing what changed. Nothing in the unit test suite,
the type checker, the build, or the eighteen mutations covering the new guards
would have found it.
