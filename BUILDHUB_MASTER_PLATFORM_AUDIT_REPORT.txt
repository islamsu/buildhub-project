EXECUTIVE SUMMARY
================================================================================

The platform was audited by reading the actual repository, not the previous
handoffs. Five real defects were found and fixed, and ONE CLAIM IN MY OWN
PREVIOUS HANDOFF WAS WRONG and is corrected below.

The most serious finding was not a missing feature. It was a page that
fabricated four conversations for every new user and, because the send endpoint
never checked its recipient, DELIVERED THEIR REPLIES TO A REAL STRANGER. One of
the fabricated threads told the reader "Your verification is complete!" over
BuildHub's name.

That is the shape of the risk in this codebase right now: not absent
functionality, which is visible, but present functionality that is not what it
appears to be. Four of the five findings are of that kind - a link that leads to
a 404, a question box whose answer can never be written, a badge counting to
zero forever, an authorization check reasoning about a path it never validated.
Each looked finished.

WHAT WAS NOT DONE, stated up front: this is not a 48-hour audit. It is a deep
pass over the areas where the evidence pointed, and several sections of the
brief were verified by reading rather than by live exercise. Every such case is
marked PARTIAL or NOT VERIFIED below rather than being reported as GO.

CORRECTION TO THE PREVIOUS HANDOFF
--------------------------------------------------------------------------------

I previously reported "NO AUDIT TRAIL. There is no audit-log table" as blocker
L1/B8. THAT WAS WRONG.

`userAccountAuditEvents` exists, is FK-protected with SET NULL so the trail
outlives its subject, and carries 22 distinct actions written from 29 call
sites: account creation, OAuth linking, every admin action, role changes,
session revocation, the full password-reset lifecycle, invitation redemption,

The real gap is narrower and is what should have been reported: COMMERCIAL
actions are unaudited - RFQ created/submitted, quotation submitted/accepted/
rejected, product created/changed, document uploaded/deleted, message sent.

SECURITY REPORT
================================================================================

FINDING S1 — MESSAGE MISDIRECTION VIA FABRICATED UI          SEVERITY: HIGH (P1)

  Impact      A signed-in user with no conversations was shown four invented
              threads (ids 1-4). `selectedConv` defaulted to 1. `messages.send`
              accepted ANY positive integer as receiverId with no existence or
              status check. Typing into the thread labelled "Ahmed Hassan
              (Contractor)" delivered the message to whichever REAL account
              holds user id 1. The FK meant a non-existent id failed loudly; an
              id that existed succeeded quietly.
  Root cause  Two independent gaps that were only dangerous together: a client
              fixture pointing at low integers, and a server endpoint that
              trusted an integer.
  Fix         Fabricated conversations removed entirely. messages.send now
              requires a real ACTIVE recipient and refuses self-messages, with
              ONE refusal shared by "no such user" and "not active" so the
              endpoint is not a directory of which ids exist.
  Test        server/messagingIntegrity.test.ts (17)
  Evidence    6 mutations killed, incl. removing the guard, allowing inactive
              recipients, and splitting the refusals into an oracle.

FINDING S2 — AUTHORIZATION REASONED ABOUT AN UNVALIDATED PATH  SEVERITY: LOW (P3)

  Impact      Every authorizeStorageKey branch dispatches on a prefix and hands
              the same string to the adapter. `avatars/../../x` satisfied the
              avatars branch - which allows ANY authenticated user, because
              profile pictures are public - and then fetched a different object.
  NOT EXPLOITABLE TODAY. The only backends are S3, where a key is opaque and
              `..` is a literal segment that will not exist, and an HTTP API.
  Why fixed   The defect is that the authorization layer reasoned about a path
              it never validated. That is invisible to whoever later adds a
              filesystem adapter for local development, and becomes a real
              traversal at that moment in a file they had no reason to open.
  Fix         isWellFormedStorageKey rejects absolute paths, backslashes,
              control characters, empty segments and whole "."/".." segments,
              BEFORE the admin short-circuit.
  Test        server/storageKeyTraversal.test.ts (16)
  Evidence    4 mutations killed, including an OVER-STRICT one: rejecting any
              key containing ".." breaks a legal `..hidden.png`, so a fix that
              quietly breaks real uploads fails too.

AUDITED AND FOUND CLEAN (recorded so this is not a list of only failures):
  - Storage proxy categories B-F: each resolves ownership through a DB row, not
    through the key. Fails closed by default.
  - Notifications: list, unreadCount and markAllRead are all scoped by
    ctx.user.id. No single-notification read-by-id surface to attack.
  - analytics.myStats: approvedProviderProcedure, self-scoped.
  - profile.update: exactly two fields (bio, location), no userId in the schema,
    written WHERE users.id = ctx.user.id. No mass-assignment surface.
  - messages.send quotation branch: sender must be a PARTY to the quotation,
    with not-a-party and does-not-exist giving the same answer.
  - ConsoleMailer: cannot be selected in production
    (`ENV.isProduction ? none : console`), so reset links cannot reach a log.
  - 23 publicProcedures reviewed; the id-taking ones are marketplace listings
    that are public by design.

NOT ATTEMPTED, and therefore not claimed: live IDOR sweeps against the deployed
API for every object type, session fixation, CSRF, and rate-limit abuse.

PRODUCT QUALITY REPORT
================================================================================

FINDING P1 — TWO AI ACTIONS LINKED TO THE 404 PAGE                        (P2)
  The opportunity engine built `/rfq/${id}`. App.tsx registers `/rfq` and
  nothing matches `/rfq/:id`, so both "prepared actions" the AI offered a
  contractor fell through to the catch-all NotFound.
  THIS WAS MINE, shipped in the previous phase, and the route test that should
  have caught it only inspected one constant. The previous handoff's claim that
  "every action href is asserted against App.tsx" was true of that constant and
  false of the product.
  Fixed: hrefs point at real routes; routeIntegrity.test.ts (47) parses the real
  route table and holds EVERY href-producing source against it, including a rule
  against building an href by interpolating an id into a path.

FINDING P2 — A SUPPLIER HAD NOTHING TO DO ON THE RFQ LIST                 (P2)
  Every card's only action was `isOwner && <Compare/>`. A contractor or supplier
  browsing /rfq - the people an RFQ is addressed to - saw no action and no hint
  of where to respond. Fixed with a route to the surface that owns the decision;
  deliberately does NOT fire the credit-spending mutation from a list card.

FINDING P3 — A SUPPLIER COULD NEVER ANSWER A PRODUCT QUESTION             (P2)
  productQuestions carries `answer`/`answeredAt`, the list returns them,
  ProductDetail renders them, the ask box says "Question sent to supplier" - and
  no procedure could write one. Fixed with marketplace.answerQuestion and
  myProductQuestions, owner-only via JOIN, one shared refusal for absent /
  not-mine / delisted. 11 tests, 5 mutations killed.

FINDING P4 — DEAD CONTROLS AND FABRICATED PRESENCE                       (P3)
  Messages header carried a voice-call and a video-call button that toasted
  "Coming soon", and an overflow button with no handler at all. A green "Online
  now" dot was driven by a field the server hard-codes to false. All removed -
  BuildHub has no calling and no presence system.

FINDING P5 — A DEAD-END EMPTY STATE                                      (P3)
  "Select a conversation to start" was shown when there were zero conversations
  to select. Replaced with an empty state that says what happened and what
  starts a conversation.

REMAINING, NOT FIXED:
  - No RFQ detail page (P2). Summary cards plus a credit-gated enquiry is what
    exists. Linking to a detail route as though it existed caused P1.
  - No product image upload surface (P2). `images` is read in three places and
    written by nothing.
  - No supplier-facing surface to answer questions from (P3) - the procedure and
    its authorization exist; the screen does not.
  - No batch upload verification (NOT VERIFIED).
  - No edit/delete surface for several owner-authored records (P3).
  - No export (P4).
  - No provider comparison surface (D4).

  D1  Duplicate quotation / revision model. Undefined in the repository.
  D2  Renovation finishing preset.
  D3  Mandatory product fields. The schema mandates only supplierId, name and
      category; price, images and specs are all nullable.

      quotation should be required before one user may message another is
      policy - the marketplace deliberately lets a customer contact a vendor
      they just found.

      moderation? Currently write-once, which is the conservative reading and
      is easy to relax; the opposite is not.
