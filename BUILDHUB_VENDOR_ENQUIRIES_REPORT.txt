1. WHAT WAS IMPLEMENTED
================================================================================

§1 - THE ELIGIBILITY DRIFT GUARD, AND A REAL DEFECT IN MY OWN GUARD

  countUsableSuperAdmins decides whether the last Super Admin may be removed. It
  is worth only as much as its agreement with auth.adminSignIn, and it did not
  agree: adminSignIn excludes isDummy accounts and the count did not. A QA
  persona carrying role='admin', adminRole='SUPER_ADMIN' and a password hash
  would have been COUNTED as holding the fort while adminSignIn refused it - so
  the guard would have permitted removing the last REAL Super Admin.

  Fixed with ADMIN_SIGN_IN_ELIGIBILITY, one list of columns asserted against
  both sides. The reverse assertion is the one that earns its place:

      adminSignIn gates on NOTHING ELSE

  so a new sign-in rule fails the test until the survival count learns it. It
  immediately caught a defect in its own instrument: the first slice anchored on
  a line that appears FIRST in the ordinary signIn procedure, so it was
  asserting the wrong function.

§2 - THE VOCABULARY CORRECTION

  qualifiedEnquiries was described as a "BILLING FACT" and a "FINANCIAL record".
  That was wrong about the architecture: BuildHub collects no payment on this
  path - no gateway, no invoice, no transaction - and payment is deliberately
  owner-deferred. An entitlement granted by a plan is DRAWN DOWN.

  Corrected everywhere to the ENTITLEMENT / QUALIFIED-ENQUIRY USAGE CONSUMPTION
  RECORD. The old wording invited the next engineer to build reconciliation,
  refunds or revenue reporting on a table that has never seen money.

  "Credit" was KEPT: shared/platformRules.ts already defines rfq.enquiry.credit
  as "one qualified-enquiry credit from the vendor's monthly allowance", and
  that is the vocabulary the vendor's own usage screen uses. It means an
  allowance unit, and the module now says so.

§3/§4 - THE DERIVATION HELD

  Status remains DERIVED from rfqs + rfqSuppliers + qualifiedEnquiries +
  quotations. There is no vendorEnquiries table, no status column, and no
  setEnquiryStatus of any shape - asserted by test.

§5 - THE FIVE VERBS, ANSWERED BEFORE ANY OF THEM WAS BUILT

  A screen with five buttons is easy to build and impossible to unbuild, so each
  was mapped to a real domain operation first
  (server/vendorEnquiryAdminActions.ts):

    create   REAL             INVITE the vendor - existing inviteSupplier(),
                              real rfqSuppliers row, existing invitedBy trail.
    open     NOT IMPLEMENTED  Opening consumes the VENDOR'S allowance for a
                              decision the vendor did not make.
    cancel   NEEDS A DOMAIN   Withdrawing an invitation is real and the enum
             CHANGE           cannot express it. Deleting the row would erase
                              the invitation from the investigation timeline;
                              reusing 'declined' would attribute the platform's
                              decision to the vendor.
    close    REAL             CLOSE THE RFQ (closeRfqSecure). There is no
                              per-vendor close, and the screen says what it is
                              really doing.
    reopen   NOT IMPLEMENTED  A decline records the vendor's own decision and is
                              not an administrator's to rewrite.
    adjust   REAL             vendorEntitlementOverrides - the existing dated,
    allowance                 reasoned, revocable architecture. Never a written
                              remaining count; no qualifiedEnquiries row is
                              created, altered or removed.

  Every claim in that catalogue is asserted against the real codebase.

§6 - ADMIN_COMPLIMENTARY IS NOT NEEDED. A FINDING, NOT A DEFERRAL.

  BuildHub already has the operation it was meant to solve for: an INVITED
  supplier opens for free. openQualifiedEnquiry returns byInvitation, writes NO
  qualifiedEnquiries row, and the trail records "opened by invitation, exempt
  from the allowance". So "give this vendor free access to this RFQ" is
  INVITE_VENDOR - real, audited, visible to the vendor as an invitation, and it
  leaves the decision to open with the vendor. A second exemption mechanism
  would have the same effect with none of the history. The §6 constraints are
  preserved as ADMIN_COMPLIMENTARY_RULES in case the owner ever wants one that
  is genuinely distinct.

§7 - THE HUMAN REFERENCE, REVIEWED BEFORE FINALISING

  An RFQ has no reference column and no slug: every screen renders `RFQ #<id>`
  and /rfq/:id is canonical. A vendor has no slug: /vendor/:id is canonical. So
  ENQ-<rfqId>-<vendorId> composes two identifiers BuildHub already prints and
  already puts in URLs. Rejected on inspection: users.openId is the SESSION
  identifier and must never appear in a quotable reference; users.username is
  nullable, so a reference built from it would be missing for exactly the
  accounts most likely to need support.

§8 - THE OVERVIEW, COUNTED IN THE DATABASE

  AVAILABLE is not a record. It is every eligible vendor against every open RFQ
  - a cartesian product whose count jumps when a vendor signs up. So the
  countable universe is the union of the three tables that record something
  HAPPENING: rfqSuppliers UNION qualifiedEnquiries UNION quotations. AVAILABLE
  can never appear in the counts, and the payload declares it excluded rather
  than leaving a permanent zero unexplained.

  Counting in Node is a dashboard that times out at real scale; counting in SQL
  is a SECOND precedence ladder. So the ladder is now DATA
  (ENQUIRY_STATE_RULES) and both renderings are generated from it:
  deriveEnquiryState walks the array, enquiryStateSql emits a CASE from the same
  array in the same order. A test fails if a rung is ever hand-written.

§9 - THE LIST

  Filtering, sorting and paging happen in the DATABASE. Filtering on a DERIVED
  state in SQL is only possible because the ladder is generated, so the filter
  and the badge cannot disagree about what INVITED means. The sort is an
  ALLOWLIST because ORDER BY takes an expression, not a value - the one input
  that cannot be a bound parameter. A pasted ENQ-501-10 or "RFQ #501" finds the
  thing it names.

§11 - THE DETAIL

  One enquiry with the context needed to act: the RFQ, the vendor, the
  entitlement, and a timeline built only from stored timestamps - an event with
  no timestamp produces no entry rather than a guess. The allowance comes from
  getEnquiryUsage, the SAME engine the vendor's own usage screen reads.

  THE PRIVACY BOUNDARY IS THE PLATFORM'S, NOT A JUDGEMENT CALL MADE HERE.
  admin.rfqInvestigation is a superAdminProcedure precisely because it "crosses
  every ownership boundary in the product at once: two parties' messages, every
  competing bid's price, the whole audit trail". These endpoints are
  marketplace.manage. Putting a bid in one would hand every marketplace
  administrator the reach the platform reserved for a Super Admin, through a
  different door. So the list and the detail report WHETHER the vendor answered
  and WHEN. The RFQ budget is out for the same reason at smaller scale.

§12 - INTERNAL NOTES, WITHOUT INVENTING A PLACE TO PUT THEM

  An enquiry is a PAIR and adminNotes addresses one subject. Rather than add a
  second subject column, the screen shows the RFQ's notes and the vendor's notes
  side by side, each labelled, and filing one requires choosing the scope. A
  vendor note is stored as subjectType 'user', not 'vendor', so a person's notes
  stay in one list - the same one their user detail page shows.

  Notes on a PERSON keep the permission they have always needed (users.read to
  read, users.manage to write), so the enquiry screen does not become a second
  door to the user directory. When the caller may not see them the response SAYS
  SO rather than returning an empty list that reads as "there are none".

§13 - ASSIGNMENT, AND WHY IT GETS A TABLE WHEN THE STATUS DID NOT

  The state is derived because everything it means is already recorded. An
  assignment records nothing that exists - no row in the domain says which
  administrator is working an enquiry, and none can, because every existing row
  is about customers, vendors and requests rather than the platform's own
  operators. Refusing storage would mean inventing a derivation that does not
  exist. So it is stored (migration 0041), APPEND-ONLY: an unassignment is a row
  with a null assigneeId, not a deletion, so "who took this off Rana, and when?"
  has an answer. The current assignee for a whole page is ONE query via a window
  function, not one per row.

  Assignable = administrators who could actually sign in, using the same
  ADMIN_SIGN_IN_ELIGIBILITY as the survival count. A queue assigned to a
  deactivated account is a queue nobody is working. Refused server-side, not
  merely hidden.

§14 - NOTIFICATIONS

  Through the existing engine, with a messageKey so the sentence is translated
  rather than an English string stored in the row. Only a real new assignee is
  told; an unassignment notifies nobody, and re-assigning to whoever already
  holds it writes nothing at all.

  A PER-ENQUIRY URL, FOUND BY AN EXISTING GUARD. The notification first linked
  to '/admin/enquiries' and notificationDestinations.test.ts rejected it,
  correctly: a notification about ENQ-501-10 that lands on a list leaves the
  recipient hunting for the row. An enquiry has no id of its own, but its
  reference is derived from the pair, so the URL can be too.
  /admin/enquiries/ENQ-7-3 now opens that enquiry directly.

THE SCREENS

  A /admin/enquiries section, in the admin menu - not a URL only someone who
  already knows it can reach. KPI tiles that drill down, a filterable and
  paginated table, and a detail view with timeline, entitlement, assignment and
  notes. Zero data renders a real sentence saying what would appear there.
  Bilingual EN/AR with RTL; 375px verified.

3. WHAT THE VERIFICATION FOUND THAT THE TESTS DID NOT
================================================================================

1. MY OWN GUARD WAS WRONG (§1). countUsableSuperAdmins omitted isDummy. Found by
   reading the real adminSignIn source line by line rather than trusting the
   comment above my own function.

2. A MUTATION SURVIVED, AND THE TEST WAS STRENGTHENED. The notes permission
   check was asserted by looking for its text in the router source; wrapping the
   condition in `if (false && ...)` left the string intact and the test passed
   while the guard did nothing. The rule now lives in callable functions
   (mayReadPersonNotes / mayWritePersonNotes) and the mutation is killed. A
   source-text assertion is a test of a spelling.

3. MY PROBE EXPECTED THE WRONG THING about MARKETPLACE_ADMIN. It asserted that
   role cannot read a person's notes; the endpoint returned them and was right -
   every non-super role carries users.read. The false branch is unreachable for
   every role that exists today, so it is exercised by a unit test instead, and
   KEPT, because deleting it would mean a future role added without users.read
   silently receives a person's notes.

4. TWO HAND-WRITTEN LIVE EXPECTATIONS WERE WRONG AND THE CODE WAS RIGHT. The
   fixture expects a state per row, written by reading the rules - never by
   calling deriveEnquiryState, which would only prove the code agrees with
   itself. The terminal-RFQ rung correctly outranks the invitation rungs. The
   combination is additionally unreachable in production, because
   markInvitationResponded is called only from the quotation-submit path.

5. SQL AND JAVASCRIPT GENUINELY DISAGREE IN ONE PLACE. MariaDB's default
   collation is case-insensitive, so `invitationStatus = 'declined'` matches a
   stored 'DECLINED' where === would not. Unreachable because both status
   columns are ENUMs whose members are all lowercase - now ASSERTED live against
   information_schema, not assumed.

6. `rows` IS A RESERVED WORD in MariaDB 10.11. The obvious subquery alias was a
   syntax error, caught by testing it against the real server.

7. AN EXISTING GUARD CAUGHT A REAL PRODUCT GAP. The assignment notification
   linked to a list; notificationDestinations.test.ts refused it. The fix was a
   per-enquiry URL, which is better product than the link that was rejected.

8. THE PROBES WERE TRIPPING BUILDHUB'S OWN AUTH RATE LIMITER by signing in on
   every run. The limiter is right; the probes now obtain a session once and
   reuse it, and still detect a stale cookie and sign in again.

INSTRUMENT DEFECTS FOUND AND FIXED BEFORE THEY COULD MISLEAD (all mine)
   - the drift-guard slice asserted the wrong function (see 1);
   - the drizzle SQL-shape collector guessed internals again: a StringChunk's
     `value` is an ARRAY and bound values are raw primitives, not Param objects;
   - a table's name lives under Symbol(drizzle:Name), not `_.name`;
   - a unit-test fake dispatched reads BY CALL ORDER and broke when a code path
     skipped one;
   - the browser probe looked for an <a href> in a menu built from BUTTONS;
   - the browser probe asserted against a single-page app three times before its
     query had resolved, reporting working screens as broken;
   - the browser probe checked the assignment panel AFTER clicking Back;
   - the "URL opens the enquiry" check passed while the panel still said
     "Loading…" - it proved the header echoes the URL, which is nearly a
     tautology. It now waits for content loaded from the server.
