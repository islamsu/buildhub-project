1. WHAT WAS IMPLEMENTED
================================================================================

§1 - THE ELIGIBILITY DRIFT GUARD, AND A REAL DEFECT IN MY OWN GUARD

  Milestone A shipped countUsableSuperAdmins, which decides whether the last
  Super Admin may be removed. Its value depends entirely on agreeing with
  auth.adminSignIn about what "usable" means, and it did not:

    adminSignIn excludes isDummy accounts.  countUsableSuperAdmins did not.

  A QA persona carrying role='admin', adminRole='SUPER_ADMIN' and a password
  hash would have been COUNTED as holding the fort while adminSignIn refused it
  outright - so the guard would have permitted removing the last REAL Super
  Admin because a test account appeared to be standing in for one.

  Fixed with ADMIN_SIGN_IN_ELIGIBILITY, one list of columns asserted against
  BOTH sides. The forward direction ("every declared rule is applied") is the
  obvious half. The reverse direction is the one that earns its place:

    adminSignIn gates on NOTHING ELSE.

  so adding a new sign-in rule fails the test until the survival count learns
  it. That assertion immediately caught a defect in its own instrument: the
  first slice anchored on `const candidate = target && !target.isDummy`, which
  appears FIRST in the ordinary signIn procedure, so it was asserting the wrong
  function entirely.

§2 - THE VOCABULARY CORRECTION

  qualifiedEnquiries was described in server/vendorEnquiry.ts and in report 3 as
  a "BILLING FACT" and a "FINANCIAL record". That was wrong about the
  architecture. BuildHub collects no payment on this path - no gateway, no
  invoice, no transaction - and payment is deliberately owner-deferred. What
  happens is that an entitlement granted by a plan is DRAWN DOWN.

  Corrected everywhere to: the ENTITLEMENT / QUALIFIED-ENQUIRY USAGE
  CONSUMPTION RECORD. The risk in the old wording was concrete: it invites the
  next engineer to build reconciliation, refunds or revenue reporting on a table
  that has never seen money.

  "Credit" was KEPT, deliberately. shared/platformRules.ts already defines
  rfq.enquiry.credit as "one qualified-enquiry credit from the vendor's monthly
  allowance", and that is the word the vendor's own usage screen uses. It means
  an allowance unit, and the module now says so.

§3/§4 - THE DERIVATION HELD

  Status remains DERIVED from rfqs + rfqSuppliers + qualifiedEnquiries +
  quotations. There is no vendorEnquiries table, no status column, and no
  setEnquiryStatus of any shape - asserted by test.

§5 - THE FIVE VERBS, ANSWERED BEFORE ANY OF THEM WAS BUILT

  The brief listed create / open / cancel / close / reopen. A screen with five
  buttons is easy to build and impossible to unbuild, so each was mapped to a
  real domain operation FIRST (server/vendorEnquiryAdminActions.ts):

    create   REAL           INVITE the vendor. Existing inviteSupplier(), real
                            rfqSuppliers row, existing invitedBy trail.
    open     NOT IMPLEMENTED  Opening consumes the VENDOR'S allowance for a
                            decision the vendor did not make.
    cancel   NEEDS A DOMAIN  Withdrawing an invitation is real and the enum
             CHANGE         cannot express it. Deleting the row would erase the
                            invitation from the investigation timeline; reusing
                            'declined' would attribute the platform's decision
                            to the vendor.
    close    REAL           CLOSE THE RFQ (closeRfqSecure). There is no
                            per-vendor close, and the screen must say what it is
                            really doing - every vendor on that RFQ is affected.
    reopen   NOT IMPLEMENTED  No per-vendor reopen. A decline records the
                            vendor's own decision and is not an administrator's
                            to rewrite.

    adjust   REAL           vendorEntitlementOverrides - the existing dated,
    allowance               reasoned, revocable architecture. Never a written
                            remaining count, and no qualifiedEnquiries row is
                            created, altered or removed.

  Every claim in that catalogue is asserted against the real codebase, so a
  claim that stops being true fails a test instead of misleading a reader.

§6 - ADMIN_COMPLIMENTARY IS NOT NEEDED. THIS IS A FINDING, NOT A DEFERRAL.

  The mandate anticipated a complimentary admin-granted open that must not
  decrement the normal allowance. BuildHub already has the operation it was
  meant to solve for: an INVITED supplier opens for free. openQualifiedEnquiry
  returns byInvitation, writes NO qualifiedEnquiries row, and the commercial
  trail records "opened by invitation, exempt from the allowance".

  So "give this vendor access to this RFQ at no cost" is INVITE_VENDOR - real,
  already audited, visible to the vendor as an invitation rather than as an
  inexplicable act, and it leaves the decision to open with the vendor.

  A second exemption mechanism would have the same effect with none of the
  history, and would teach the vendor's own usage screen a new usageReason for
  no gain. The §6 constraints are preserved verbatim as
  ADMIN_COMPLIMENTARY_RULES in case the owner ever wants one that is genuinely
  distinct from an invitation.

§7 - THE HUMAN REFERENCE, REVIEWED BEFORE FINALISING

  Checked whether public human-safe references already exist for the two halves.
  They do, and they are exactly these numbers:

    RFQ     no reference column, no slug. Every screen renders `RFQ #<id>` and
            /rfq/:id is the canonical route. The id IS the public reference.
    Vendor  no slug. /vendor/:id is the canonical provider profile route.

  ENQ-<rfqId>-<vendorId> therefore composes two identifiers BuildHub already
  prints and already puts in URLs. Rejected on inspection: users.openId is the
  SESSION identifier and must never appear in a quotable reference, and
  users.username is nullable - a reference built from it would be missing for
  exactly the accounts most likely to need support.

§8 - THE OVERVIEW, COUNTED IN THE DATABASE

  AVAILABLE is not a record. It is every eligible vendor against every open RFQ
  - a cartesian product whose count jumps when a vendor signs up and has nothing
  to do with enquiries. So the universe an administrator can count is the union
  of the three tables that record something HAPPENING:

    rfqSuppliers  UNION  qualifiedEnquiries  UNION  quotations

  AVAILABLE can never appear in those counts, and the payload declares it as
  excluded rather than leaving a permanent zero unexplained.

  Counting in Node is one round trip and a dashboard that times out at real
  scale. Counting in SQL is a SECOND precedence ladder - the exact drift this
  module exists to prevent. So the ladder is now DATA (ENQUIRY_STATE_RULES) and
  both renderings are generated from it: deriveEnquiryState walks the array,
  enquiryStateSql emits a CASE from the same array in the same order. A test
  fails if a rung is ever hand-written into the SQL.

  admin.enquiryOverview is gated on marketplace.manage, decided server-side, and
  returns COUNTS ONLY - no vendor identity, no RFQ content, no quotation figure.

3. WHAT THE VERIFICATION FOUND THAT THE TESTS DID NOT
================================================================================

Three findings, all from live work, none visible to a green suite.

1. MY OWN GUARD WAS WRONG (§1). countUsableSuperAdmins omitted isDummy. Found by
   reading the real adminSignIn source line by line rather than trusting the
   comment I had written above my own function.

2. MY TEST WAS ASSERTING THE WRONG FUNCTION. The drift guard's first slice
   anchored on a line that appears in the ordinary signIn procedure before the
   admin one. It reported adminSignIn as having lost its role checks. The
   reverse assertion caught it - which is precisely why the reverse assertion is
   there.

3. TWO OF MY HAND-WRITTEN EXPECTATIONS WERE WRONG AND THE CODE WAS RIGHT. The
   live fixture expects a state per row, written out by hand from the rules -
   never by calling deriveEnquiryState, which would only prove the code agrees
   with itself. Two rows disagreed. On investigation the terminal-RFQ rung
   correctly outranks the invitation rungs: an awarded RFQ closes an enquiry
   that produced no quotation, whatever the invitation says, because the vendor
   cannot act. The combination is additionally unreachable in production -
   markInvitationResponded is called only from the quotation-submit path, so a
   'responded' invitation always has a quotation beside it in real data.

4. SQL AND JAVASCRIPT GENUINELY DISAGREE IN ONE PLACE. MariaDB's default
   collation is case-insensitive, so `invitationStatus = 'declined'` matches a
   stored 'DECLINED' where === would not. Unreachable because both status
   columns are ENUMs whose members are all lowercase - and that is now ASSERTED
   live against information_schema, not assumed, because a future migration
   adding a mixed-case member would make the divergence real and silent.
