5. MIGRATION DECISION - EXPLICIT, AS YOU ASKED
================================================================================

RENDER preDeployCommand. NOT THE START COMMAND.

    preDeployCommand: "./node_modules/.bin/drizzle-kit migrate"

Start-command migration fails on four counts:

    CONCURRENCY   every instance runs the start command; scale to 2 and two
                  processes race the same migration. Drizzle journals applied
                  migrations but takes no advisory lock, so the race is real.
    RESTARTS      a crash-looping container re-runs migrations every restart.
    FAILURE MODE  a failed migration yields a container that will not start -
                  the deploy fails AND the old version is already gone.
    ROLLBACK      you can never deploy the image without also migrating.

preDeployCommand runs once per deploy rather than once per instance, and A
FAILURE HALTS THE DEPLOY WITH THE OLD VERSION STILL SERVING. That single
property is what makes it correct: it converts a broken migration from an
outage into a refused deploy.

It is also exactly what was done by hand in the Render shell, so it FORMALISES
the verified state rather than changing behaviour. Available on paid instance
types; plan: starter qualifies.

THREE THINGS IT DOES NOT SOLVE, stated rather than glossed:

    a) EXPANSION/CONTRACTION DISCIPLINE. The command runs before the new code
       is live, so during a deploy the OLD code runs against the NEW schema.
       Every migration must be backward compatible with the previous release:
       add columns nullable, never drop or rename in the same release that
       stops using them. This is a review rule, not a tool guarantee.
    b) SCHEMA ROLLBACK. Rolling the image back does not roll the schema back.
       With (a) held, image rollback stays safe. Without it, it does not.
    c) LONG MIGRATIONS. A migration that locks a large table blocks the deploy.
       Theoretical at current volumes; not theoretical after launch.

Staging first, several deploys, before this goes anywhere near production. I am
not proposing to change production deploy behaviour in the same step.

6. TWO DECISIONS I WILL NOT MAKE SILENTLY
================================================================================

Q1 - ADMIN BOOTSTRAP.

  Every convenient fix is a backdoor. An env-var auto-admin, a "first user
  becomes admin" rule, or a bootstrap endpoint are each a privilege-escalation
  primitive that ships to production and stays there.

  MY RECOMMENDATION is the boring one: a one-time, operator-run, idempotent
  script executed out-of-band against the database, creating exactly one admin,
  password supplied at run time, never stored in the repo. It leaves NO code
  path in the running application that can mint an admin.

  Do you accept that, or do you want something in-application?

Q2 - IS PASSWORD RESET IN LAUNCH SCOPE?

  If YES, H1 becomes a blocker and I need staging SMTP credentials
  (SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASSWORD, SMTP_FROM, plus
  APP_BASE_URL - auth.capabilities gates on both).

  If NO, I record it as a named, accepted production-readiness gap with an
  owner, rather than letting it sit as a quiet SKIP.

  The token machinery already exists and is correct: passwordResetToken +
  passwordResetExpiresAt, cleared on use (routers.ts:354, 391-403). Only
  credentials are missing. Nothing is faked.
