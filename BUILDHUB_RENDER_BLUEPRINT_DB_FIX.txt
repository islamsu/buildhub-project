2. HOW THE WEB SERVICE GETS THE REAL PASSWORD
================================================================================

IT CANNOT GET IT AUTOMATICALLY. fromService IS THE WRONG TOOL AND THERE IS NO
RIGHT ONE.

You asked me to determine the correct fromService wiring. The honest answer is
that it does not exist for this case, and I would rather say so than ship a
second clever-looking construction that also does not work.

  fromService COPIES a value. It cannot COMPOSE one.

Render's own documentation shows fromService copying a password verbatim into a
password variable - the MinIO example:

    - key: MINIO_PASSWORD
      fromService:
        name: minio
        type: pserv
        envVarKey: MINIO_ROOT_PASSWORD

That works because both sides are the bare secret. A connection URI is
different: the password has to be INTERPOLATED INTO A LARGER STRING, and no
field in the Blueprint spec performs string composition. `value:` is literal.
There is no $VAR expansion. fromService/fromDatabase/fromGroup all copy whole
values.

WHY THE OLD WIRING LOOKED PLAUSIBLE AND WAS NOT. The previous revision papered
over the gap by defining a DATABASE_URL on the MySQL service and copying it
across with fromService. The copy mechanism was fine. The value being copied was
the same non-interpolated fiction. And the mysql:8.0 entrypoint never reads
DATABASE_URL at all, so that variable did nothing whatsoever except feed a
broken string to the web service.

That is why it is DELETED rather than repaired: repairing it would have required
the same impossible interpolation, one service further away.

SO THE PASSWORD REACHES THE APP THROUGH A ONE-TIME DASHBOARD ENTRY, and the
blueprint now says so plainly instead of pretending otherwise:

    mysql://buildhub:<URL-ENCODED PASSWORD>@buildhub-staging-mysql:3306/buildhub

THE ALTERNATIVE I CONSIDERED AND REJECTED: pass the password to the web service
as its own variable via fromService - which IS supported - and compose the URI
at container start. That genuinely works. But it means changing either
server/db.ts, which reads process.env.DATABASE_URL, or the Dockerfile
entrypoint. Application code and production configuration respectively, both of
which you excluded. So it is recorded here as an option rather than taken.

3. A SECOND DEFECT FOUND WHILE TESTING THE FIX
================================================================================

This one would have burned another deploy cycle, so it is worth stopping on.

generateValue EMITS BASE64, WHICH CONTAINS  /  +  AND  = .

A raw "/" terminates the authority section of a URI. Embedding the generated
password directly does not merely fail to authenticate - THE STRING FAILS TO
PARSE, and it fails in a way that looks like a completely different bug.

Verified against real MySQL 8 through the actual getDb() from server/db.ts,
using a password of exactly the shape generateValue produces:

  PASSWORD IN URI            RESULT
  ------------------------   -------------------------------------------------
  raw base64                 [Database] Failed to connect: TypeError: Invalid
                             URL   (code ERR_INVALID_URL)
                             getDb() returns null
                             -> 503, AND NO "[health] Database probe failed"
                                LINE AT ALL

  percent-encoded            200 {"status":"ready","checks":{"database":true}}

Note the asymmetry in the logs. The wrong-password failure logs
"[health] Database probe failed: ... ER_ACCESS_DENIED_ERROR". The unencoded-URL
failure logs "[Database] Failed to connect: TypeError: Invalid URL" and never
reaches the health probe's catch block. Same 503, same JSON body, different
cause, different log line.

TO PRODUCE THE ENCODED VALUE:

    node -e 'console.log(encodeURIComponent(process.argv[1]))' '<the password>'

This requirement is written into render.yaml beside the variable, not left in a
commit message, precisely because the failure it prevents is so misleading.

4. WILL SYNCING THE BLUEPRINT UPDATE THE EXISTING VARIABLE?
================================================================================

NO. A ONE-TIME DASHBOARD UPDATE IS REQUIRED.

From Render's Blueprint documentation, verbatim:

    "When you update an existing Blueprint, Render ignores any environment
     variables with sync: false. Render prompts you for these values only
     during the initial Blueprint creation flow."

Your blueprint already exists. The current broken DATABASE_URL will therefore
sit there untouched no matter how many times you sync. Pushing this commit alone
changes nothing on the running service.

SET IT BY HAND:

  1. Render -> buildhub-staging-mysql -> Environment
     Copy the MYSQL_PASSWORD value.

  2. Percent-encode it:
     node -e 'console.log(encodeURIComponent(process.argv[1]))' '<password>'

  3. Render -> buildhub-staging -> Environment
     Set DATABASE_URL to:
     mysql://buildhub:<ENCODED>@buildhub-staging-mysql:3306/buildhub

  4. Save. Render redeploys automatically.

THIS DOES NOT ROTATE THE PASSWORD. Render generates a value for a
`generateValue` variable only when that variable does not already exist, so the
live password survives every re-sync. Step 1 READS it; nothing replaces it. That
was your requirement 5 and it is met by construction, not by care.
