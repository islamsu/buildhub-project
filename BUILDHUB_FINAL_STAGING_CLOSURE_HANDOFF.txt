ADMIN:
============================================================
All of the following are real-browser results from section 26, driving
Chromium against staging - not API calls, and not inferred from HTTP
status codes.

- Super Admin browser login
  VERIFIED. The Super Admin signs in through the rendered /admin/login
  form and lands on /admin.

- Admin dashboard
  VERIFIED. The navigation renders Users, Fraud Detection and Settings;
  the Users tab renders the user-management surface; the rendered
  dashboard carries no credential material.

- Administrators page
  VERIFIED. /admin/admins renders the administrator table with all eight
  columns (Name, Username, Email, Role, Status, Created, Last login,
  Actions). The bootstrapped administrator displays its role and status.
  A real Super Admin is not shown the Super-Admin-only refusal. The table
  renders no credential material.

- Invitation lifecycle
  VERIFIED end to end in the browser. The invitation modal opens and asks
  for Full name, Username and Email (each asserted as exactly one field,
  by DOM count, because placeholders never appear in innerText); it
  offers to issue a one-time link; it states that the Super Admin will
  never see the password. A QA sub-administrator is created (http 200),
  redeems its invitation and sets its own password (http 200), then signs
  in through the browser form and reaches /admin.
  Token strength is asserted separately: 43 characters, and the
  invitation audit record exposes neither the raw token nor its hash.

- Role management
  VERIFIED. The role selector renders exactly five options - Super Admin,
  User Admin, Marketplace Admin, Support Admin, Billing Admin. A Super
  Admin promotes the QA sub-administrator (http 200) and the promotion
  reaches the existing browser session with no re-login. A Super Admin
  then demotes it (http 200) and access is withdrawn immediately, not
  deferred.

  Why that is the correct expectation, and why it was wrong in an earlier
  draft: authenticateRequest re-reads the user row from the database on
  every request, so ctx.user.adminRole is always live and never cached in
  the JWT. Only setAdminActive(false), revokeAdminSessions and
  resetAdminPassword stamp sessionsInvalidBefore. setAdminRole does not.
  An earlier version of section 25 asserted that a role change kills the
  session and produced three live failures. The harness was wrong, not
  the application. It now asserts what the design actually guarantees:
  the session survives, the authority changes immediately.

- Permission boundaries
  VERIFIED, and verified discriminatingly. A SUPPORT_ADMIN reaches the
  admin surface rather than Access Denied, is refused /admin/admins in
  the browser, and is not offered the invite control.
  The section 25 matrix is chained - each role's allowed endpoint is the
  next role's denied endpoint - so a blanket allow or a blanket deny
  cannot pass it:

    USER_ADMIN        allow admin.fullAuditReport   deny admin.commercialKpis
    MARKETPLACE_ADMIN allow admin.complianceQueue   deny admin.fullAuditReport
    SUPPORT_ADMIN     allow admin.disputes          deny admin.complianceQueue
    BILLING_ADMIN     allow admin.commercialKpis    deny admin.disputes

  The matrix is cross-checked against ADMIN_ROLE_PERMISSIONS by unit
  test, and deliberately avoids users.read, which all five roles hold and
  which therefore discriminates nothing.

- Browser authorization
  VERIFIED. The refusals above are what the browser actually renders, not
  an API 403 assumed to imply a correct UI. A deactivated administrator
  cannot sign in through the browser and is returned to /admin/login.
  No first-party console or request errors on either the admin surface or
  the sub-admin surface.

- Cleanup
  The QA sub-administrator created for the UI pass is deactivated at the
  end of the run (http 200) and its inability to sign in is then asserted
  through the browser. Test administrators remain identifiable as QA
  data. The existing Super Admin was not modified.

  VERIFIED. The token is 43 characters. The invitation audit record
  exposes neither the raw token nor its hash. The token reaches the

- Cookie security
  VERIFIED on the live response:
    PASS  21. the session cookie is HttpOnly
    PASS  21. the session cookie is Secure
          - Path=/; HttpOnly; Secure; SameSite=None

  SameSite=None is deliberate and is a known trade-off, not an oversight:
  it is what makes the cookie usable from the separately-origined
  preview/browser contexts this project is tested from. It is paired with
  Secure, so the cookie is HTTPS-only. Worth ChatGPT's independent view
  before production, since a production deployment on a single origin
  could tighten this to Lax.

- Authentication hardening (adjacent, verified in the same run)
  Wrong password and unknown user are indistinguishable (401, identical
  message), and that check is itself asserted to be testing auth rather
  than rate limiting.
