1. MILESTONE A — THE FINDING THAT MATTERED MOST
================================================================================

SEVERITY: P0-adjacent. Reachable by a real, legitimately-created administrator.
STATUS:   FIXED, mutation-tested, and proven live over authenticated HTTP.

WHAT WAS WRONG

`admin.setUserFrozen` is gated on `users.manage` — a permission USER_ADMIN
holds. It accepted any `userId` and refused only the caller's own account.

So a USER_ADMIN could freeze every Super Admin in turn. Afterwards nobody could
create an administrator, change a role, or unfreeze the people who could,
because all three need `admins.manage` and every holder of it was frozen.
Recovery would have required direct database access.

`admin.verifyUser` had the same shape with a smaller blast radius.

This was not on the brief's list. It was found by asking the question a feature
checklist does not ask: what is the worst sequence of individually reasonable
actions?

THE SECOND ROUTE TO THE SAME PLACE

Two Super Admins demoting each other. Each call is legal on its own, and the
existing self-check — "you cannot change your own role" — cannot see the pair.
One demotes the other, the survivor is demoted by a third party or by a second
pass, and the role empties.

TWO INVARIANTS, HELD IN ONE MODULE

server/adminAuthority.ts, so adding an endpoint cannot quietly break one
somewhere else.

  1. ADMINISTRATORS ARE MANAGED IN ADMIN MANAGEMENT.
     `users.manage` runs the USER directory — verifying accounts, freezing a
     fraudulent vendor. It is not authority over the platform's own operators.
     Acting on an account whose role is 'admin' now requires `admins.manage`.

     THIS IS NOT A BLANKET DENIAL, and both a unit test and a live check prove
     it: a USER_ADMIN can still freeze an ordinary user, which is exactly what
     the permission exists for. A guard that broke the thing it protects would
     be a worse outcome than the hole.

  2. AT LEAST ONE SUPER ADMIN MUST REMAIN ABLE TO SIGN IN.
     Demotion, deactivation and freezing are three words for the same
     consequence when applied to the last one, so all three share a single
     check and the last always fails whichever path it arrives by.

THE SUBTLE PART: "ABLE TO SIGN IN", NOT "EXISTS"

An invited Super Admin who has never redeemed their link has no password hash,
and `adminSignIn` treats a null hash as no account at all. Counting them would
allow removing the last WORKING Super Admin while a dormant invitation sat in
the table — locked out, with the guard reporting success.

The count therefore requires accountStatus active, no deactivatedAt, and a
non-null passwordHash. Verified live rather than argued: at one point in the
probe a naive count reads 2 where the real one reads 1.

WHAT WAS ALREADY RIGHT, AND WAS DELIBERATELY LEFT ALONE

Much of §2–§9 already existed and was correct:

  - invitation-based creation. The account is created with NO password; the
    invitee sets one by redeeming a single-use, expiring, hashed token. There
    is no moment at which a plaintext password exists for a Super Admin to see.
  - role change, deactivate-with-session-revocation, session revocation,
    reset-link issuance, invitation revocation — all present, all
    superAdminProcedure.
  - §8 session safety: VERIFIED, not assumed. `db.getUserByOpenId` runs on
    every request, so `ctx.user.adminRole` is always fresh and a demotion takes
    effect on the next call without needing a session sweep.

The role→permission map stays in code rather than becoming three database
tables. Its rationale is written in shared/adminRoles.ts and is sound: a
permission grant should be a diff someone approves, not a row someone can
INSERT at 2am. The brief's §3 asked for capabilities over rigid roles; the
repository already models capabilities, with roles as named bundles of them.
No new roles were invented to match names in the prompt.

2. MILESTONE B FOUNDATION — THE RECONCILIATION (§11)
================================================================================

The brief asked for this first, and it was the right instruction: the answer
decides whether a second enquiry system gets built by accident.

THE ANSWER

There is NO `vendorEnquiries` table, and there should not be one.

A vendor enquiry is not a record. It is the RELATIONSHIP between one vendor and
one RFQ, and BuildHub already stores every part of it across four tables, each
answering a different question:

  rfqs                the CUSTOMER'S REQUEST — scope, budget, deadline, status
  rfqSuppliers        a TARGETED INVITATION, with its own small lifecycle:
                      invited / viewed / responded / declined
  qualifiedEnquiries  the ENTITLEMENT USAGE CONSUMPTION RECORD: one allowance
                      unit was consumed. Unique on (userId, rfqId). No status
                      column. NOT a financial record - BuildHub collects no
                      payment on this path; an entitlement is drawn down.
  quotations          the vendor's ANSWER

So the lifecycle an Admin screen needs is DERIVED from those four, not stored a
fifth time. Three reasons, in order of how expensive the mistake would be:

  - qualifiedEnquiries is the ENTITLEMENT CONSUMPTION LEDGER. Giving it a
    workflow status would put allowance usage and a conversation in the same
    row, and the first "just reset the status" would destroy the record of what
    a vendor's allowance was spent on. A test now asserts that table has no
    status column. (An earlier draft of this report and of the module called it
    a billing/financial record. That was wrong about the architecture: payment
    is owner-deferred and there is no gateway, invoice or transaction on this
    path. The wording is corrected here and in server/vendorEnquiry.ts.)
  - two sources for "has this vendor responded?" is precisely how an Admin
    screen and a vendor screen come to disagree about the same RFQ — and the
    one that disagrees will be the one nobody is watching.
  - a fifth table needs writing on every event the other four already record,
    and is wrong the first time one of those writes fails.

SEVEN STATES, EVERY ONE EVIDENCED

  AVAILABLE · INVITED · VIEWED · OPENED · RESPONDED · DECLINED · CLOSED

The brief listed ten candidates. DRAFT, PENDING, IN_PROGRESS and EXPIRED are
absent because BuildHub cannot evidence them from stored data today, and a
state nothing can produce is a filter that always returns nothing and a badge
nobody ever sees. A test proves every state that IS declared is reachable from
some real evidence — the guard against the opposite mistake.

TWO ORDERING DECISIONS WORTH NAMING

  - A submitted quotation outranks everything, including a closed or awarded
    RFQ. An administrator looking at an awarded RFQ still needs to see WHICH
    vendors answered it; collapsing them all to CLOSED erases the most useful
    fact on the page.
  - A declined invitation likewise survives closure. "They said no" and "it
    ended" are different outcomes and must not render identically.

A SCHEMA-DRIFT GUARD

The terminal RFQ set is ['closed', 'awarded'] — exactly what the enum holds.
The first draft also listed 'cancelled', 'completed' and 'expired', which the
column cannot store. That was the same fault this module's own comments warn
about, caught before it shipped. A test now compares the module's assumption
against the schema, so if the enum gains a terminal value the test fails until
the derivation learns it — rather than a closed enquiry silently reading as
AVAILABLE.

HUMAN REFERENCES (§14)

`ENQ-<rfqId>-<vendorId>`. An enquiry has no id of its own — it is a pair — so
its reference is built from the pair. Derivable in both directions, needs no new
column or sequence to allocate, and an administrator reading it in a support
ticket can tell which RFQ it concerns. Parsing rejects anything malformed rather
than guessing.

BATCHED READS

Four queries per page whatever the page size, with de-duplicated id lists. One
query per row is fine on the twelve rows a demo has and unopenable on the
thousands a working marketplace has.

USAGE ATTRIBUTION (§28)

VENDOR_OPEN / INVITATION_EXEMPT / NOT_OPENED — labels over evidence that already
exists. Nothing here writes a counter. ADMIN_COMPLIMENTARY is documented as
anticipated but deliberately not returned, because no admin-open path exists
yet and returning a value nothing can produce would be a fabricated fact.

4. WHAT WENT WRONG, AND WAS FIXED BEFORE ANY RESULT WAS REPORTED
================================================================================

4.1 FOUR VACUOUS PASSES — the most important item in this section

The live probe's first run reported four PASSES on the attack checks. They were
worthless.

A scrypt hash looks like `scrypt$N$r$p$salt$hash`. The probe passed SQL to the
MySQL client via `-e ${JSON.stringify(...)}`, which produces a DOUBLE-quoted
shell argument — and bash expands `$N`, `$r` and `$p` inside double quotes
before MySQL ever sees the string. The seeded credential was silently corrupted,
every sign-in returned 401, and each attack check "passed" because the attacker
had never been authenticated at all.

A 401 meaning "you are not signed in" is not evidence that a guard refused you.

Two fixes, both structural rather than cosmetic:
  - SQL now goes to the client over STDIN, where there is no shell quoting to
    get wrong. Not a cleverer escape — a mechanism with no escaping in it.
  - the probe now REFUSES to attempt the attack unless the attacker session is
    proven first, so that failure mode cannot recur silently.

4.2 A PRODUCT BEHAVIOUR MISTAKEN FOR A DEFECT

One check failed with "Please login" after an administrator was reactivated.
That is correct behaviour, not a bug: `revocationCutoff()` is deliberately
`Date.now() + 1000`, because session `iat` has second granularity and rounding
the cutoff UP is what guarantees a token minted in the same second as a
revocation cannot survive it. The cost is a sub-second window in which even a
legitimate fresh sign-in is refused — the right trade, and already asserted in
adminAuthorization.test.ts. The probe was signing in inside that window.

Reported here rather than quietly patched, because "the probe was impatient" and
"the product is broken" are different findings.

4.3 A MUTATION THAT SURVIVED, AND WHAT I DID ABOUT IT

The de-duplication mutation (E3) survived its first attempt. The honest reading
was that my test claimed more than it checked: counting queries says nothing
about what is bound inside them, and duplicate ids in an IN list return
identical rows, so the mutation was not even a correctness defect.

Rather than record a survivor and move on, the test now inspects the ids
actually handed to the driver, which pins a genuine scale property — a fifty-row
page about one vendor should not bind that vendor's id fifty times, three times
over. The mutation is now killed.

Getting there required reading drizzle's real condition shape off a live object:
`inArray` renders an array of Param objects, not a `number[]`. My first
collector guessed the latter, found nothing, and the test failed on its own
instrument rather than on the code.

4.4 A TEST FIXTURE THAT NEEDED EXTENDING, NOT ADAPTING

`setUserFrozen` now READS its target before writing — it has to, because the
target decides which authority the action needs. The existing fake had no
`select`, so admin.test.ts was extended: the fake answers the lookup, and three
new cases cover a missing target and the last-Super-Admin refusal. Nothing was
weakened to accommodate the change.

4.5 A COMMENT THAT BROKE ITS OWN TEST

The first version of the endpoint-wiring test sliced routers.ts on the bare
string `setUserFrozen:` — which matched a COMMENT inside verifyUser that
mentions setUserFrozen by name. The slice ended before the code it was meant to
inspect, and a correctly-guarded endpoint was reported as unguarded. The
boundary is now a declaration pattern rather than a name. Same class of mistake
as the migration-delimiter comment in report 1.
