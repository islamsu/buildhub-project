# BuildHub — Render Staging Runbook

A temporary, isolated staging environment. It does **not** replace the planned
Vultr production architecture and shares nothing with it.

---

## What I could and could not do

Render is unreachable from my sandbox — `api.render.com`, `dashboard.render.com`
and `render.com` all fail, on the same strict egress allowlist that blocks Vultr
and `example.com`. Outbound SSH is blocked entirely. So I could not create the
account, authorise GitHub, or call Render's API, and I could not have deployed
even with credentials.

What I did instead: **built the exact artefact Render will build and ran it**,
in the exact topology `render.yaml` declares — the real Docker image, a private
MySQL 8, migrations applied from inside the image, HTTPS in front, and 127
browser QA checks against it. Everything below is verified against that.

The one thing genuinely unverified is Render's own platform behaviour: its
builder, its TLS, its private networking, its disks.

---

## Your steps

**1. Connect and deploy.** In Render: **New → Blueprint**, pick this repository
and branch `claude/phase4b-readiness-audit-hardening`. Render reads
`render.yaml` and provisions the web service and the private MySQL service.
Nothing is clicked together by hand.

**2. Let it build.** The Dockerfile is the one in the repo. First build takes a
few minutes.

**3. Run migrations once.** In the web service's **Shell**:

```
npx drizzle-kit migrate
```

This works offline from the image — `drizzle-kit` is a runtime dependency now,
which it was not until this work.

**4. Verify.**

```
node scripts/smoke.mjs https://buildhub-staging.onrender.com
```

Expect 9/9. If `readiness` fails, the app cannot reach MySQL — check
`DATABASE_URL` resolved from the private service.

**5. Optional, in the dashboard.** Set `SMTP_*` against a staging sender to
enable password reset, and `S3_*` against a **staging** bucket to enable
uploads. Leave them unset and both features report themselves unavailable
rather than failing silently.

Then work through `BUILDHUB_STAGING_QA_CHECKLIST.md` (98 checks).

## Decisions I made, and why

**MySQL is a private service, not a managed database.** Render's managed
offering is PostgreSQL. BuildHub is MySQL — 19 migrations, a schema verified
against 8.0.46. Porting to Postgres would be the architecture redesign this
deployment exists to avoid, and would make staging a test of something
production will never run. The trade-off is real and stated: a private service
with a disk has no managed backups, no failover, no patching. Acceptable for
temporary staging holding test data; **not** acceptable for production, which is
why production stays on Vultr Managed Databases.

**`healthCheckPath` is `/healthz`, not `/readyz`.** Liveness, deliberately. A
database blip must not make Render kill and restart the container — it would
restart forever while the database is the thing that is down. `/readyz` does the
real `SELECT 1` and is what the smoke suite checks.

**`DATABASE_SSL=disable` on this hop only.** The database is a private service
that never leaves Render's network. Production sets `require` against a managed
instance reached across a network, and that default is enforced in code.

**Secrets are generated by Render, not chosen by me.** `JWT_SECRET` and the
MySQL passwords use `generateValue`, so nobody ever holds them and a staging
secret cannot be reused in production.

**`OAUTH_SERVER_URL` is deliberately empty.** `auth.capabilities` then reports
OAuth as unavailable and the UI hides that door. First-party email and password
sign-in has been the primary path since Slice 3.

## Defects this deployment found

Five, all fixed and regression-tested. Three would have broken the first deploy
on **either** Render or Vultr.

**The container could not start at all.** `server/_core/vite.ts` imported `vite`
at the top level; esbuild bundles with `--packages=external`, so it survived
into `dist/index.js` and Node resolved it at startup — in production too, where
`pnpm prune --prod` has removed it. `ERR_MODULE_NOT_FOUND` before binding a
port. Invisible from a host, where `node_modules` still has vite.

**Migrations downloaded themselves at deploy time.** `drizzle-kit` was a
devDependency, pruned from the image, yet both deploy workflows run it there.
`npx` fetched it from npm mid-deploy — fragile, and it means the tool applying
migrations to a production database need not be the one that generated them.

**The public marketplace showed fictional inventory.** Ten hardcoded products
with invented brands, prices and ratings, rendered unconditionally; the real
endpoint was never called. Their Manus-era images 401'd for signed-out
visitors, so every card was broken. Now database-backed.

**`marketplace.list` ignored `category` and `search`.** Accepted both, applied
neither — unnoticed because the page filtered a hardcoded array on the client.

**The rate limiter would have locked out real users.** 10 auth attempts per
minute per IP. Egyptian mobile carriers run carrier-grade NAT; thousands of
subscribers share one address, as do offices and site offices. One busy NAT
locks out everyone behind it. Raised to 60/minute with per-account brute force
unchanged at 10 per 15 minutes — that is the limit that actually protects a
password.

## What staging cannot tell you

- **Uploads** until `S3_*` is set. The adapter is written; no bucket is attached.
- **Password reset** until `SMTP_*` is set.
- **Real Egypt latency.** Render's Frankfurt is the nearest region; the Vultr
  region decision still needs the measurement procedure in the infrastructure
  report.
- **Payments.** Paymob is not started and nothing simulates it.

---

## When you are done

Render staging is temporary. Delete the Blueprint when Vultr staging exists —
two staging environments is one more than anyone maintains.

## Verifying the real deployment — the 22-point gate

I cannot reach Render from the engineering sandbox. Re-measured at the start of
this session, and it is an explicit policy denial rather than an outage:

```
render.com                    403 CONNECT (policy denial)
api.render.com                403 CONNECT (policy denial)
dashboard.render.com          403 CONNECT (policy denial)
buildhub-staging.onrender.com 403 CONNECT (policy denial)
example.com                   403 CONNECT   <- an allowlist, not a Render rule
github.com                    reachable
outbound SSH, any host        blocked
```

No credential changes an egress allowlist. So the verification runs where it
can actually reach the deployment: **a GitHub Actions runner**.

### Run it

Actions → **Staging QA** → Run workflow → paste the staging URL.

Or set the repository variable `STAGING_BASE_URL` once and it also runs weekly,
so staging drift is caught rather than discovered.

It runs `scripts/smoke.mjs` first (cheap, and its failure invalidates
everything else), then `scripts/staging-qa.mjs` — all 22 points, in a real
Chromium, at 1440px and 375px, in English and Arabic.

### Give it a staging admin

Several checks need one: admin billing visibility, the trial/cancel/resume
lifecycle, and the approved-provider quotation path (approving a vendor is an
admin action). Set two repository **secrets**:

```
STAGING_ADMIN_USER
STAGING_ADMIN_PASSWORD
```

Without them the gate runs 149 checks and skips 6, naming what each needs.
With them it runs 163. **Skips are counted separately and are never reported as
passes.**

To create the admin: register normally on staging, then promote that one row in
the staging database. It is a staging-only account and must not share a password
with anything else.

### Safety

The harness registers accounts, so it **refuses any URL that does not look like
staging** — the guard is in both the script and the workflow. Never point it at
production.

### What it proved locally

Run against the identical container topology before being handed over:
**163/163 with an admin, 149/149 without**, both with honest skips. That
validates the harness. It does not validate Render, which is the entire point of
running it there.
