============================================================
A. PROVIDER
============================================================

Provider:
  OpenAI, directly. No gateway, no proxy, no intermediary.

Model:
  gpt-5.6-luna, via ENV.openAiModel (OPENAI_MODEL), which defaults to that
  value when unset.

  The explicit Luna id is used deliberately: the bare "gpt-5.6" alias routes
  to Sol, a different and more expensive model. Luna is the cost/performance
  tier documented for high-volume workloads, which is what BuildHub AI is.

  I did not substitute a different model. The one you specified is what is
  configured and what the request sends.

API architecture:
  The Responses API, through the official `openai` npm SDK (7.5.0, current
  latest). Responses rather than Chat Completions because that is the
  interface OpenAI documents for reasoning models - Chat Completions still
  works but is no longer where the model behaviour is best.

  Request shape actually sent:
    model              ENV.openAiModel
    instructions       BuildHub's system prompt (the system-role messages)
    input              the conversation turns
    max_output_tokens  4096
    reasoning          { effort: 'low' }
    NO temperature     (see B)

  Response read via the SDK's `output_text` helper, which concatenates the
  text out of the typed output array. Reading that rather than indexing
  output[0] matters: a response whose first item is a reasoning item would
  otherwise read as empty.

Active endpoint:
  https://api.openai.com/v1/responses
  Authorization: Bearer $OPENAI_API_KEY, server-side only.
  OPENAI_BASE_URL exists but is unset, so the official endpoint is used.

Two details verified against the official documentation rather than assumed.
Both would have broken the feature:

  1. GPT-5 family models are REASONING models and reject `temperature`.
     Sending it turns every request into a 400. Nothing sends it, and a test
     fails if anything starts to.

  2. Reasoning tokens are billed as output tokens and counted INSIDE
     max_output_tokens. Set the ceiling too low and the model can spend the
     whole budget thinking, returning status "incomplete" with an EMPTY
     output_text - billed, with nothing to show the user. That case is
     classified as a failure, never returned as an empty success.

  A note on how this was verified: platform.openai.com and
  developers.openai.com are both blocked by this environment's egress proxy,
  so I could not fetch the docs pages directly. The details above come from
  official-documentation search results (developers.openai.com,
  platform.openai.com, openai.com), and the SDK version from the npm registry.
  I am flagging that rather than implying I read the pages.

B. ROOT CAUSE / MIGRATION
============================================================

Old provider:
  The Manus Forge gateway. `invokeLLM` in server/_core/llm.ts posted to
  ${BUILT_IN_FORGE_API_URL}/v1/chat/completions, defaulting to
  https://forge.manus.im/v1/chat/completions, authenticated with
  BUILT_IN_FORGE_API_KEY.

Why it was removed:
  BUILT_IN_FORGE_API_KEY was never set on staging, so the assistant failed
  for every user. BuildHub has otherwise migrated off the Manus platform, and
  you decided not to obtain a Forge credential. Keeping a dependency on the
  platform the project left - for its most visible feature - was the thing
  being removed, not merely a missing variable.

New provider:
  OpenAI direct, as above.

Why this architecture was chosen:
  A single provider boundary, because this is the SECOND provider this
  feature has had and there will probably be a third. The first version put
  the provider inside the router: URL construction, auth header, retry loop
  and response parsing all sat next to the tRPC procedure. That is why the
  original failure was hard to see and why migrating meant touching the
  router at all.

  Now server/_core/ai.ts owns everything about talking to a model and exposes
  exactly one function - generateAIResponse({ messages }) -> { text } - plus
  isAiConfigured(). The router has no URL, no header, no SDK, no key and no
  provider-specific parsing. Changing provider again is a change to one file.

Confirmed, each by an executed check:

  - API key never exposed
      The delivered /ai page contains no OPENAI_API_KEY, no api.openai.com,
      no "Bearer ", and no API-key-shaped string. The client bundle was also
      grepped after build: no api.openai.com, no OPENAI_API_KEY, no
      openAiApiKey anywhere under dist/public.
  - API key never logged
      The error classifier logs a category and a numeric status and never the
      underlying message. A test throws an APIError whose message embeds a
      fake key and asserts the log line contains neither the key nor "Bearer".
  - Authorization header never logged
      Constructed by the SDK, never touched by application code, never
      rendered, returned or logged.
  - Stack trace never exposed
      The error formatter strips shape.data.stack unconditionally; section 21
      asserts errors carry no stack trace or filesystem path.
  - Prompt not logged
      Deliberate: the provider error string interpolates the response body,
      and a provider that echoes the request would put project details and
      budgets into the deployment log. Two tests assert this using a fixture
      containing a fake budget figure.
  - Provider errors sanitized
      Ten categories, each mapped to a sentence written for the caller. A
      test throws "Incorrect API key provided: sk-test-SECRET123" and asserts
      the surfaced message contains none of it.
  - Browser contains no secret
      PASS 28/13 × 4 leak checks, plus no credential in console output.

  One honest note on method: an initial bundle grep for the bare substring
  "sk-" matched dist/public assets. Inspected rather than assumed: the hits
  were Tailwind mask-image custom properties ("sk-image-conic-from-pos") and
  emacs-lisp grammar symbols ("sk-user-about-large-file"). No credential. The
  browser check now uses a key SHAPE (/\bsk-[A-Za-z0-9]{20,}/) instead, because
  a false alarm on this exact check is how a real one gets ignored.
