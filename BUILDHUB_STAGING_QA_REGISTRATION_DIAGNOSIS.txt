2. WHY IT NEVER REGISTERED
================================================================================

The three registered workflows share a single creation timestamp: the first
push that created .github/workflows/. GitHub indexed the entire new directory
in one pass. staging-qa.yml arrived a day later, in commit 56e9b90.

BEST-SUPPORTED EXPLANATION: GitHub registers a workflow from a push when the
pushed file carries a trigger that could match THAT event.

  ci.yml                on: push (all branches), pull_request, workflow_dispatch
  deploy-staging.yml    on: push [main], workflow_dispatch
  deploy-production.yml on: workflow_dispatch ONLY
  staging-qa.yml        on: workflow_dispatch + schedule ONLY

staging-qa.yml's only two triggers - workflow_dispatch and schedule - are both
evaluated ONLY on the default branch. So when it was pushed to a feature
branch, there was nothing about it for GitHub to evaluate, and no workflow
entity was created.

deploy-production.yml is also dispatch-only and DID register - but it rode in
on the initial directory-creation index, which is a different code path. That
is consistent with all four data points.

WHAT I CANNOT VERIFY: GitHub's exact indexing rule is not documented at this
granularity. I am confident about the MECHANISM you are hitting - unregistered
-> 404 -> absent from the list - because I measured it directly. I am INFERRING
the reason it failed to register. The recommendation in section 4 does not
depend on that inference being correct.

5. TWO DECISIONS I WANT FROM YOU FIRST
================================================================================

DECISION 1 - THE WEEKLY CRON.

  The file currently carries:  schedule: - cron: "0 6 * * 1"

  That is inert on a feature branch. It becomes LIVE the moment the file lands
  on main. With no STAGING_BASE_URL repository variable set, my "Resolve the
  target" step fails by design - so you would collect a red X every Monday
  morning, forever, for a job that was never going to work.

  MY RECOMMENDATION: drop `schedule:` from the copy that goes on main and keep
  it dispatch-only. Nothing tests for it - server/stagingGate.test.ts asserts
  on the staging-URL guard, the smoke-before-browser ordering, the runner, the
  playwright install, and the secret handling, but never on `schedule` - so
  removing it breaks no test, now or on a later sync. Re-add it when staging is
  permanent and STAGING_BASE_URL is set.

DECISION 2 - THE `staging` ENVIRONMENT.

  The workflow declares:  environment: name: staging

  If a `staging` environment WITH REQUIRED REVIEWERS already exists under
  Settings -> Environments, the job will PAUSE for approval rather than run,
  and it will look like nothing is happening. If no such environment exists,
  GitHub creates it implicitly and the job proceeds normally.

  Worth one glance before you run it. I would KEEP the declaration - it is what
  scopes the STAGING_ADMIN_* secrets to this workflow.
