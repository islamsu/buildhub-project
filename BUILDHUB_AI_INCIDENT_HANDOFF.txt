============================================================
B. ROOT CAUSE
============================================================

Exact root cause:
  BUILT_IN_FORGE_API_KEY is not set on the staging deployment. `invokeLLM`
  calls `assertApiKey()` first, which throws before any network activity. The
  AI provider was NEVER CONTACTED and is not implicated in this incident.

Evidence:
  Reproduced against live staging from a GitHub runner (this engineering
  sandbox is on an egress allowlist that returns 403 for every Render host,
  so the probe runs where it can actually reach the deployment).

  Run #28, before any fix:

    INFO  27. ai.chat -> http 500 INTERNAL_SERVER_ERROR in 154ms
    FAIL  27. an authenticated AI request succeeds - http 500 INTERNAL_SERVER_ERROR in 154ms

  THE 154 MILLISECONDS ARE THE FINDING. `fetchWithBackoff` makes up to five
  attempts (RETRY_MAX_RETRIES = 4) and sleeps between them:

    computeBackoffDelay(attempt) = jitter over [cap/2, cap], cap = 500 * 2^attempt

  so the FLOOR on sleeping alone, before counting five network attempts, is
  250 + 500 + 1000 + 2000 = 3750 ms. No failure that reached the provider can
  return in 154 ms - and 154 ms is barely more than the runner-to-Frankfurt
  round trip. The request therefore died BEFORE the first fetch.

  Corroborated locally against the same code path with the variable unset and
  then set to a dummy value:

    key absent          Error: "…is not configured"        1 ms, no network
    key present, bad    TypeError: fetch failed         5,805 ms, 4 retries logged

  Two clean signatures, ~1 ms versus ~5.8 s. The live 154 ms sits with the
  first. Independently confirmed after the fix: the deployment now publishes
  its own answer, `"aiAssistant": false`.

  Ruled out by the same evidence:
  - NOT the provider (never contacted).
  - NOT a regression. `git log server/_core/llm.ts` returns exactly one
    commit, "Initial project bootstrap". The AI path has never been changed
    and has never been configured for a non-Manus deployment. Nothing in the
    recent merges (#11, #12, #13) touched it.
  - NOT authentication. Anonymous callers get "Please login (10001)"; the
    owner saw the generic message, which proves the request passed auth and
    the rate limiter and reached the mutation body.
  - NOT rate limiting (that returns 429 with its own message).

Affected code path:
  /ai (client/src/pages/AIAssistantPage.tsx, route "/ai" in App.tsx:66)
    -> AI_MODES card onClick -> handleSend
    -> trpc.ai.chat.useMutation
    -> POST /api/trpc/ai.chat
    -> aiChatProcedure (server/routers.ts:2912) = protectedProcedure + 4 rate limiters
    -> aiRouter.chat (server/routers.ts:2929)
    -> invokeLLM (server/_core/llm.ts:342)
    -> assertApiKey() -> THREW HERE
    -> [never reached] fetchWithBackoff -> POST ${forgeApiUrl}/v1/chat/completions
    -> tRPC classifies a bare Error as INTERNAL_SERVER_ERROR
    -> errorFormatter (server/_core/trpc.ts) replaces the message with
       GENERIC_INTERNAL_MESSAGE = "Something went wrong. Please try again."
    -> AIAssistantPage onError -> toast.error(e.message)

  That last chain is why the message was uninformative, and the masking is
  CORRECT - it exists to stop internal messages like
  "set BUILT_IN_FORGE_API_URL and BUILT_IN_FORGE_API_KEY" reaching browsers.
  The defect was throwing an unexpected-error type for an entirely expected
  condition.

Configuration involved:

  No secret value was retrieved, printed, logged or echoed at any point.

Provider involved:
  None was reached. For the record, the code's provider is the MANUS FORGE
  gateway: `resolveApiUrl()` returns ${BUILT_IN_FORGE_API_URL}/v1/chat/completions
  and defaults to https://forge.manus.im/v1/chat/completions when the URL is
  empty. Authentication is `authorization: Bearer ${BUILT_IN_FORGE_API_KEY}`.
  No model is sent unless a caller supplies one, and ai.chat does not - the
  gateway picks. Timeout: none set on the fetch; retries: 5 attempts, jittered
  exponential backoff honouring Retry-After, capped at 30 s.

  This matters for the decision below: BuildHub has deliberately migrated OFF
  the Manus platform, but its AI feature is still wired to that platform's LLM
  proxy.

============================================================
C. FIX
============================================================

Code changed:
  Configuration is the root cause and only you can supply a credential. But
  four code defects are the reason it took an external timing probe to
  establish that, and those are fixed.

  1. server/_core/llm.ts - the guard named the WRONG VARIABLE.
     It threw "OPENAI_API_KEY is not configured" while testing
     ENV.forgeApiKey (BUILT_IN_FORGE_API_KEY). Anyone acting on that message
     configured a variable this path never reads - and somebody already had:
     render.yaml carried an OPENAI_API_KEY entry and no FORGE key at all. It
     now names the variable it actually checks. Also exports isLlmConfigured()
     so callers can ask instead of guessing.

  2. server/routers.ts - ai.chat now REFUSES DELIBERATELY.
     `throw new TRPCError({ code: 'SERVICE_UNAVAILABLE', message: 'The AI
     assistant is not available on this deployment.' })` when unconfigured.
     Server-authored messages for expected conditions pass the error formatter
     untouched, so the caller learns the truth while the generic mask stays in
     place for genuine crashes. The message names no variable, provider or
     endpoint. It also short-circuits BEFORE invokeLLM, so an unconfigured
     deployment never burns five attempts and 3.75 s proving what the process
     already knew.

  3. auth.capabilities + /ai - the page now ASKS BEFORE IT OFFERS.
     `aiAssistant: isLlmConfigured()` joins passwordReset and oauthSignIn in
     the capability document, and AIAssistantPage renders an honest bilingual
     notice with the eight cards inert (pointer-events-none) and the composer
     disabled. Written as `=== false`, not `!capabilities?.aiAssistant`, so a
     healthy deployment is not disabled during the first render while the
     query is still in flight.

  4. server/_core/trpcErrorLog.ts (new) - the deployment now WRITES SOMETHING
     DOWN. No onError handler was mounted on the tRPC express middleware at
     all, so staging logged nothing while this failed for every user. Errors
     are classified: config-missing, provider-auth, provider-quota,
     provider-unavailable, provider-bad-request, provider-network,
     response-parse, database, unclassified.

Configuration changed:
  NONE on any running system. No Render environment variable was added,
  changed or read. render.yaml and .env.example were corrected as SOURCE
  FILES: render.yaml now declares BUILT_IN_FORGE_API_KEY and
  BUILT_IN_FORGE_API_URL, and .env.example no longer claims that
  OPENAI_API_KEY "Enables the AI assistant. Absent = the feature reports
  itself unavailable." Both halves of that sentence were false. The second
  half is now true.
