PART 1 - WHERE IT STARTED
================================================================================

BuildHub arrived as a Manus-platform checkpoint application:

  Client   React 19, Vite 7, Tailwind v4, Radix/shadcn, wouter
  Server   Express 4, tRPC 11, a single monolithic server/routers.ts
  Data     Drizzle ORM 0.44, mysql2, MariaDB 10.11
  Tests    Vitest 2.1

Feature surface at takeover: bilingual AR/EN throughout, six user roles
(homeowner, contractor, engineer, architect, supplier, project manager), a
marketplace, an RFQ engine with quotation comparison, an AI assistant, real-time
messaging, notifications, an admin portal, and a compliance onboarding flow with
role-specific document requirements.

THE PROBLEM WITH THE STARTING POSITION

Prior work had declared the platform launch-ready. The repository contained
FINAL_LAUNCH_GATE_REPORT.md, a "50-item matrix", claims of "38/38 tests passed",
and a frozen BUILDHUB_BASELINE.md dated 18 August 2026.

That framing did not survive contact with the code. The takeover audit found
authorization holes in the core commercial workflow, a database with no foreign
keys, fabricated data rendered as real metrics, and credentials returned to the
browser on the single most-called endpoint in the application.

Everything that follows was verified against a running database rather than
against the previous report. That distinction produced most of the findings in
this document.

PART 2 - SECURITY PHASES 1-3
================================================================================

--------------------------------------------------------------------------------
PHASE 1  fb7fd09   Quotation accept/reject IDOR and race condition
--------------------------------------------------------------------------------

The core commercial workflow - a homeowner accepting a contractor's bid - had no
ownership check. Any authenticated user could accept or reject any quotation on
any RFQ, including ones belonging to strangers. A concurrent-accept race could
also mark two quotations accepted on the same RFQ.

Fixed with an ownership check against the RFQ's requester plus a transactional
guard so only one quotation can win.

--------------------------------------------------------------------------------
PHASE 2  26d2d08   Projects IDOR, storage auth, review forgery, AI abuse
--------------------------------------------------------------------------------

Four separate issues:

  - Projects endpoints accepted a project id with no ownership verification.
  - Storage downloads were reachable without authentication - any file key that
    could be guessed or leaked returned the file.
  - Reviews could be forged: nothing verified the reviewer had actually
    transacted with the person being reviewed.
  - The AI assistant had no abuse controls.

--------------------------------------------------------------------------------
PHASE 3A  30d101f   Localization, data minimization, review rules, notifications
--------------------------------------------------------------------------------

Directory endpoints returned more user data than the page needed. Review
participation rules were tightened. Localization gaps closed. Notification
delivery corrected.

--------------------------------------------------------------------------------
PHASE 3B.1  542760e   Infrastructure discovery (read-only)
--------------------------------------------------------------------------------

Read-only survey of what the deployment actually depends on. First identification
of the Manus platform coupling (OAUTH_SERVER_URL, BUILT_IN_FORGE_API_*) and of
the %VITE_ANALYTICS_ENDPOINT% template markers that a publish pipeline was
expected to substitute and never had.

--------------------------------------------------------------------------------
PHASE 3C  ed3dc25   Database integrity
--------------------------------------------------------------------------------

THE FINDING: 42 relationships in the schema were foreign keys in intent and
plain integers in fact. Nothing at the database level prevented a quotation
pointing at a deleted RFQ, or a message pointing at a deleted user.

THE APPROACH: the migration was written RESTRICT-favouring rather than CASCADE -
deleting a user with history should fail loudly, not silently erase the history.
It was then tested twice:

  1. Against a database deliberately seeded WITH orphans. The migration had to
     FAIL, safely, without partial application. It did.
  2. Against a cleaned database. It had to succeed. It did.

EXPLAIN plans were captured before and after on the heavy-query columns to
confirm the new indexes were actually used.

Deliverables: BUILDHUB_DATABASE_INTEGRITY_REPORT.md and
BUILDHUB_DATABASE_MIGRATION_RUNBOOK.md.

--------------------------------------------------------------------------------
PHASE 3C.1  3e874f7   Real-data audit - BLOCKED
--------------------------------------------------------------------------------

The brief asked for an audit of real production data. No staging or production
access exists, and none could be manufactured.

Reported as BLOCKED rather than simulated against seed data and presented as if
it were real. This is the first of several points in this engagement where the
honest answer was "I cannot do this and here is exactly why".

--------------------------------------------------------------------------------
4B.1  cfb1553   Provider-agnostic billing domain
--------------------------------------------------------------------------------

The billing domain depends on a PaymentProvider INTERFACE and never imports a
provider SDK. The interface is shaped from BuildHub's own approved commercial
lifecycle - deliberately not from any single provider's API surface - so adding
Paymob, or replacing it with Stripe or a GCC provider later, is a new file
implementing the interface rather than a rewrite.

NullPaymentProvider is the active implementation. Every operation throws
PaymentProviderNotConfiguredError. It fails LOUDLY on purpose: a billing system
that quietly no-ops is far more dangerous than one that refuses.

shared/billing.ts became the single source of truth for every commercial value:

  Professional   EGP 499/month, 4,990/year
  Premium        EGP 999/month, 9,990/year
  Founder        EGP 299 and 699/month, 6 months, MONTHLY ONLY
  Trial          30 days
  Grace period   7 days

Annual founder pricing was never approved by the business, so founder.year is
null on every plan and a founder-priced annual subscription is REJECTED rather
than guessed at.

--------------------------------------------------------------------------------
4B.2  bbf4dd4   Server-authoritative entitlement engine
--------------------------------------------------------------------------------

Entitlements are resolved server-side from stored subscription state. Nothing a
client sends can influence a plan, a status, an allowance, or a capability.

THE ENTITLEMENT_ENFORCEMENT HONESTY LEDGER

A per-entitlement record naming which phase actually implements enforcement.
Its stated purpose, written into the file:

  "so no report, UI, or plan-comparison page can claim a capability works when
   nothing enforces it"

At the end of Phase 4B.2 only three of nine entitlements were live. The pricing
page reads this ledger and badges everything else "coming soon" rather than
advertising it. A vendor being asked for EGP 499-999 a month is entitled to know
which of the things on the list actually works today.

--------------------------------------------------------------------------------
4B.3  01fe3b7   Real vendor directory, RFQ targeting, qualified enquiries
--------------------------------------------------------------------------------

Replaced a hard-coded array of fictional vendors with real, database-backed
provider accounts. Added vendor service-category declarations, RFQ targeting
based on them, and transactional monthly metering of qualified enquiries.

THE CONSTRAINT SET HERE, referred to throughout the rest of this report as
Phase 4B.3 section 13:

  A PAID PLAN MUST NEVER BUY A HIGHER ORGANIC POSITION IN THE DIRECTORY.

Directory ranking reads no billing state at all. Paid placement was deferred as

Two new tables (vendorCategories, qualifiedEnquiries) in migration 0015 - purely

--------------------------------------------------------------------------------
4B.4  df6e540   Subscription lifecycle
--------------------------------------------------------------------------------

Nine lifecycle states, all transitions pure and testable, orchestration wrapped
in transactions with SELECT ... FOR UPDATE row locks and UNIQUE constraints
catching ER_DUP_ENTRY. Every operation returns applied / noop / rejected, and
noop is a SUCCESS at the API layer - repeating a transition you already
completed is the idempotent behaviour the lifecycle guarantees.

TWO PRE-EXISTING DEFECTS FOUND BY PROBING, NOT BY READING

  1. awaitingRenewalSync GRANTED PAID ACCESS INDEFINITELY.

     Probing deriveBillingState directly showed isPaid = true TEN YEARS past
     the period end. A subscription that stopped paying kept every paid
     capability forever, as long as the provider sync never arrived - which,
     with no provider connected, it never would.

     Fixed with RENEWAL_SYNC_WINDOW_DAYS, reusing the already-approved 7-day
     grace value rather than inventing a new number.

  2. startTrial WIPED THE FOUNDER-PRICE STAMP.

     It emitted founderPriceUsedAt: null for every non-founder subscription,
     destroying the write-once guard that stops a vendor claiming the founder
     offer twice. Caught by a test I wrote for a different property.

     Fixed by omitting the key rather than writing null - the stamp is now
     only ever WRITTEN, never cleared.

A HOLE I NEARLY INTRODUCED MYSELF

  startPaidTrial allowed unlimited repeat trials after a lapse: cancel, lapse,
  start another 30-day trial, forever. Closed with a write-once trialStartedAt
  before it shipped.

SLICE 1  472e3b4   Critical production hardening (A1-A9)
--------------------------------------------------------------------------------

A1  EMPTY JWT_SECRET BOOTED SILENTLY
    JWT_SECRET defaulted to "" and getSessionSecret() happily returned an
    encoded empty string. A production deployment missing the variable would
    start normally and sign every session token with a zero-length key. Nothing
    reported it.
    Fixed: findEnvProblems() / assertEnvOrExit(). Production refuses to start;
    development warns. Called from startServer(), never at module load, so
    importing the module in tests can never throw.

A2  SESSION REVOCATION FAILED OPEN
    isSessionRevoked() returned false when the database was unreachable. A
    database blip silently re-validated every revoked session.
    Fixed: returns true. An unreachable database cannot prove a session is
    still valid.

A3  STACK TRACES REACHED END USERS
    Internal errors serialised their stack into the tRPC response. Fixed with an
    errorFormatter that strips the stack and replaces INTERNAL_SERVER_ERROR
    messages with a generic string. The React ErrorBoundary was also rendering
    the stack in a <pre> block for every user; it now logs to
    componentDidCatch and shows something actionable instead.

A5  NO RATE LIMITING ON AUTHENTICATION
    Added a three-limiter scheme (IP burst, IP sustained, identifier sustained)
    applied before any credential comparison, so a blocked request never reaches
    password verification and cannot become a timing oracle.

A6  EVERY AVATAR WAS BROKEN
    storageProxy classified storage keys by prefix. The avatars/ branch was
    missing entirely, so every avatar request fell through to the fail-closed
    default and returned 403 to every non-admin.

A7  COOKIE AND PROXY CORRECTNESS
    trust proxy enabled in production; the session cookie's secure flag pinned
    true in production rather than derived per-request, because sameSite:"none"
    is rejected without it and one plain-HTTP-looking hop would hand back a
    cookie the browser silently discards.

A8  PORT BINDING
    Development scans for a free port; production binds the configured port or
    exits. Silently landing on a different port leaves health checks and routing
    pointing at nothing.

A9  Startup failures now exit non-zero.

SLICE 3  1801fbe   First-party email and password authentication
--------------------------------------------------------------------------------

THE LAUNCH BLOCKER.

Real users could not sign in without OAUTH_SERVER_URL, a Manus-platform service.
auth.signInDummy accepts only accounts with isDummy = true. On infrastructure
you control, with Manus gone, NOBODY COULD LOG IN.

Classification: C - MIGRATION REQUIRED.

The migration used primitives that already existed: scrypt hashPassword /
verifyPassword, the users.passwordHash column, the session JWT minted by
sdk.createSessionToken, the existing cookie helper, and the audit-event table.
New accounts get openId = local_<uuid> so every existing consumer is untouched.

The OAuth callback is unchanged and still works wherever OAUTH_SERVER_URL is
reachable. It is simply no longer the only door.

A PRE-EXISTING DEAD END, CLOSED

  Admin-created accounts could set a password through the invitation flow and
  then had NO endpoint that would accept it. signInDummy requires isDummy.
  auth.signIn now accepts any non-dummy account holding a passwordHash, which
  covers both self-registered and admin-invited users.

SESSION INVALIDATION ON PASSWORD RESET

  revokedSessions revokes one jti at a time and cannot express "log this account
  out everywhere" - which is exactly what a reset must do, since the whole point
  is that someone else may hold a valid session. Added
  users.sessionsInvalidBefore, checked against the token's iat. Tokens issued
  before a reset are refused; tokens with no iat at all fail closed.

EMAIL DELIVERY

  BuildHub had never sent an email. admin.createUser RETURNS the invitation link
  in its API response for an admin to copy by hand.

  Added a Mailer adapter mirroring the payment-provider seam. NullMailer throws
  rather than resolving. auth.capabilities reports whether reset can be offered,
  so the UI never shows "check your inbox" when no message was sent.

  Configuring a real sender is one new class and your credentials.

SLICE 7  41cb5e8   Analytics event stream and commercial KPIs
--------------------------------------------------------------------------------

BuildHub had no event stream. Every business metric was an ad-hoc SQL aggregate
over whatever timestamp column happened to be nearby - which answers "how many"
but never "how many got from here to there". There was also no MRR, no ARR, no
churn and no ARPV anywhere: the owner of a subscription business could not see
the subscription business.

TWO SOURCES OF TRUTH, DELIBERATELY KEPT APART

  THE FUNNEL comes from the new analyticsEvents table. Eight stages:
  registration, profile completion, submission for review, verification, first
  enquiry, first quotation, trial, subscription. Each defined by a named event
  in a CLOSED catalogue rather than whatever string a call site passed.

  REVENUE comes from vendorSubscriptions, priced by resolvePrice from
  shared/billing.ts. NEVER from the event stream: a stream is allowed to drop a
  write, and an owner reporting revenue to an investor cannot be working from
  something that is allowed to be lossy. No price literal appears anywhere in
  the KPI module, and a test asserts that.

THREE PROPERTIES THE KPI CODE IS BUILT AROUND

  1. A TRIAL CONTRIBUTES ZERO TO MRR. Counting trials as revenue is the most
     common way a subscription business lies to itself.
  2. REVENUE IS TIME-DERIVED through deriveBillingState, so a row still marked
     active whose period ended last month contributes nothing, and a lifecycle
     sweep that has not run cannot inflate MRR.
  3. EMPTY MEANS NULL, NOT ZERO. ARPV, churn rate and the median-days figures
     return null with no basis, and the dashboard renders an em dash. "0% churn"
     reads as perfect retention; "no paid subscriptions to measure" is what is
     actually true.

SAFETY: recordEvent swallows every failure, so a missing table or a database
blip cannot fail a signup. Metadata is filtered against a forbidden-key list,
nested objects dropped entirely, values truncated, key count bounded - a log is
copied, shipped and retained far more casually than the database is.

The subscription half of the funnel is emitted from recordBillingEvent, the
single choke point every commercial transition already passes through, rather
than from eight lifecycle call sites which would have been eight places to
forget.

LIVE PROOF: two real accounts driven through the real endpoints. A trialing
vendor showed MRR 0 and ARPV null. Making the subscription genuinely paid moved
MRR to 499 - matching the catalogue price read back from the API - with ARR
5,988. Pushing the period end into the past dropped MRR to 0 while the row still
said active. Every metadata value written during the run was printed and
inspected: plan, role, category, status and transition names only.

SLICE 8  b9c6ee7   Featured placement
--------------------------------------------------------------------------------

featuredPlacementEligible had sat in the plan table since 4B.1 granting premium
subscribers nothing at all.

THE SHAPE IS THE WHOLE DESIGN.

Featured placement is a SEPARATE SPONSORED STRIP, not a reordering:

  - The organic directory still ranks by verification and recency. A paid plan
    still cannot buy a higher position there. Phase 4B.3 section 13 stands.
  - Featured vendors appear in their own labelled section AND ALSO in the
    organic list, in their organic position. Removing them would have been a
    hidden penalty for paying.

TWO THINGS A VENDOR STILL CANNOT BUY: trust and position. The strip is labelled
"Sponsored" / "إعلان مموّل" with a note stating plainly that it is paid
placement, rendered by the SAME card component as the organic list so the only
difference is the label - not a bigger card, not a brighter border, not a
better-looking rating. A test asserts the sponsored copy contains none of
"verified", "trusted", "recommended", "best", "top-rated" or "endorsed".

ELIGIBILITY IS TIME-DERIVED, never read off the plan column: a row still saying
premium/active whose period ended is not featured. A malformed subscription
fails closed to FREE and buys nothing.

SLOTS ROTATE BY DAY. Ordering by id and taking the first six would have handed
the earliest subscriber a permanent slot while later premium subscribers paid
for nothing. Deterministic within a day - a strip that reshuffles while you read
it is unusable - and over 40 days every vendor's appearance count stays within
one of every other's.

PART 7 - METHOD, AND MY OWN MISTAKES
================================================================================

--------------------------------------------------------------------------------
THE VERIFICATION STANDARD
--------------------------------------------------------------------------------

Every phase ran the same gate: vitest with no weakened assertions, tsc --noEmit,
both builds, then LIVE verification against a real MariaDB instance and - where
there was a user-facing surface - a real Chromium session in English and Arabic
at 1440px and 375px. Fixtures torn down to the exact baseline after each run.

A local HTTPS terminator was built for the browser runs because the session
cookie is SameSite=None, which Chromium rejects without Secure. Solving it that
way rather than weakening the cookie code was deliberate.

The live harness is what caught the pricing-page redirect, the awaitingRenewalSync
indefinite grant, and the founder-stamp wipe. Unit tests missed all three.

--------------------------------------------------------------------------------
MISTAKES I MADE AND CORRECTED RATHER THAN SHIPPED
--------------------------------------------------------------------------------

  1. I rewrote VendorsDirectory.tsx using inline ar ? '...' : '...' ternaries,
     violating an existing localization contract test. I FIXED THE UI, NOT THE
     TEST - added 30 translation keys and removed a redundant per-page dir
     attribute.

  2. I claimed Forge backed five subsystems. Tracing importers showed four were
     dead scaffold. Corrected the claim before the report shipped.

  3. I ran an A2 end-to-end test (login, stop MariaDB, session rejected), then
     checked whether it ISOLATED the change. It did not - getUserByOpenId also
     fails on database loss, so auth.me would return null either way. Said so
     plainly in the commit rather than letting the green result stand as proof.

  4. A stale dev server from the previous slice still held port 3500, so the
     first Slice 9 run was probing pre-change code and reported 12 failures
     against fixes that were already correct. Chased it instead of accepting the
     numbers. The harness now binds an explicitly free port and aborts on
     fallback.

  5. A harness probed registration.uploadDocument when appRouter mounts that
     router as compliance.* - it was testing a 404 and would have reported a
     confident pass. The mount point is now pinned by a test.

  6. A browser harness set the language via localStorage 'buildhub-lang' where
     the app reads 'buildhub_lang', so four Arabic assertions were silently
     passing against an English page. It now asserts <html lang> matches the
     language under test FIRST, so that class of mistake fails loudly.

  7. Several times a test failed on the codebase's own explanatory comments
     containing the forbidden string it was scanning for. Fixed the scanner, not
     the assertion.

  8. My Arabic numeral assertions searched for ASCII digits. The product was
     correct; the test was wrong.
