1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------

Four capabilities the mandate names as REQUIRED did not exist. They were built,
tested, mutation-tested and driven in a real browser. Two defects were found -
both by using the product, neither by reading it, and neither visible to a green
test suite.

WHAT DID NOT EXIST BEFORE THIS PASS

  Part 45  A vendor's qualified-enquiry allowance could not be moved. It came
           from the plan constant, and the only lever an administrator had was
           to change the vendor's PLAN - which rewrites what that vendor is
           recorded as having agreed to pay and hands them every other
           capability of the tier.

  Part 46  No individual entitlement override existed, so there was no way to
           grant capacity without the shortcut above.

  Parts    No old -> new values were recorded anywhere. The commercial audit
  42-44    trail deliberately keeps field NAMES and not their values, so
           "what was the price before it changed" had no answer.

  Parts    A dispute could not be reconstructed. Every fragment existed
  41,52    separately; nothing joined them.

  Part 48  There was no way to turn a name or an email address into a record
           id - and the dispute investigation above demands one. It was
           reachable only by an administrator who already knew the answer.

  Part 49  Nothing answered "what is wrong with the data right now". The
           underlying facts were all queryable; no screen asked the questions.

  Part 50  Nothing told an operator whether this deployment was working.
           /healthz, /readyz and /version exist for machines; the console had
           no operational view at all.

WHAT WAS BROKEN

  An engineer or architect could submit a priced commercial bid and had nowhere
  in their own workspace to see it. They are offered "Create Quotation", the
  server accepts it, myQuotations was fetched for them - and the result was
  discarded, because only two of the five provider workspaces rendered it.

  A price change that never happened. Saving a product twice recorded
  "price 1720.00 -> 1720". A DECIMAL column reads back with scale while the
  patch supplies a bare number, and the comparison was === on the strings. The
  history an administrator reads in a dispute was manufacturing changes.

  A console tab that could never answer. "Fraud Detection" rendered a permanent
  empty state - there is no detector and no signals table behind it, so no data
  could ever appear there. It has been REMOVED rather than furnished with an
  invented detector, and automated fraud detection is recorded as NOT
  IMPLEMENTED. A tab that can never answer teaches an administrator to stop
  reading the console.

WHAT WAS DELIBERATELY NOT BUILT

  The owner's instruction was to build the capabilities with real data behind
  them. Three had it and were built. Orders, order value and revenue do not
  exist in this build - there is no order entity - and a fraud detector has no
  signal to detect. Those are stated as absent rather than mocked up, here and
  on the screens themselves.

  A duplicate is a PAIR, so seeding one new account makes TWO rows offending.
  Expecting +1 there was the harness being wrong about the domain; the check
  was right. Recorded because it is the kind of "failure" that gets a correct
  implementation changed.

  IDS, NEVER VALUES. The read is audit.read, which USER_ADMIN holds. A
  duplicate-email check that returned the addresses would be a way to enumerate
  account emails through a screen that is not the user directory. Asserted
  against the response bytes: the customer's email, their phone number and the
  seeded product and request titles are all absent from a 1,146-byte payload
  that names them by id.

  ZERO IS ZERO, NOT "HEALTHY", AND A FAILED CHECK IS NOT ZERO. A check whose
  query throws reports null and renders "could not be checked" in the
  destructive colour. A broken query and a clean platform must never be the
  same pixel.

  SEEDED QA DATA IS EXCLUDED BY DEFAULT, proven both ways: a defect on an
  isDummy account did not move the count with the toggle off, moved it by
  exactly one with the toggle on, and its id appeared only in the inclusive
  sample.

  ON duplicate_account_email BEING REACHABLE AT ALL: users.email carries a
  UNIQUE index. That was checked rather than assumed - MariaDB compares the
  stored bytes, so ' a@b.test' and 'a@b.test' both insert cleanly and are the
  same address to a person. The check normalises with trim() and lower() and
  finds exactly the pairs the index lets through. It is also the guard that
  survives if the constraint is ever dropped.
